Look for a newer task checkpoint before acting on an old one. [ADR-0016.7](../../../../docs/adr/0016.7-budget-d1-reads-and-cache-public-reports.md) owns the D1/cache decision.

### Operational evidence and session handoffs

- **Resume from evidence.** Before repeating an investigation, read its task, latest dated handoff, and saved captures. The [September 9 analytics and agent-research checkpoint](../../../../docs/handoffs/2026-09-09-analytics-and-agent-research-checkpoint.md) records the completed Matomo/protocol research, accepted referrer release, HN evidence, and proposed follow-ups. The [newsletter handoff](../../../../packages/blog/drafts/research/newsletter-reliability/14-handoff.md) owns its separate current state. The [September 7 publication checkpoint](../../../../docs/handoffs/2026-09-07-publication-checkpoint.md) preserves article 024's frozen provenance, social copy, and older worktree recovery; the [reliability checkpoint](../../../../docs/handoffs/2026-09-07-reliability-checkpoint.md) is historical. Treat capture timestamps as historical observations, not live service-health checks.
- **Finish research with a saved result.** A task records the requested outcome and acceptance criteria; creating it is followed by executing the authorized research, saving a readable cited artifact and relevant receipts, linking them from the task, and checking completion. Reuse existing tasks instead of creating a new record for every follow-up idea. Mark the requested work done when its criteria are met, and lead the completion message with its status and artifact link. Label proposed experiments separately: they do not silently reopen completed research or become scheduled work. Keep research, implementation, deployment, and measured acceptance distinguishable. This clarifies the task-status confusion raised September 9 UTC; it adds no approval step to work already authorized.
- **Name the unit and window.** D1 `rows_read` measures cumulative query read work. The same data can be read again by another statement; it does not count distinct stored observations, visitors, or returned rows. Record per-statement values and their report total, source/window, sampling, and unknown caller attribution. The old report's 182,388 reads came from nine statements; see [ADR-0016.7](../../../../docs/adr/0016.7-budget-d1-reads-and-cache-public-reports.md).
- **Budget production investigation.** Dashboard and CLI SQL also consume D1 reads. Inspect saved evidence and service metadata first, test fixtures locally, then run only the bounded production checks needed to resolve an open question. After a quota rejection, stop retrying expensive queries and recheck access and allowance through metadata. Fewer statements or lower local latency does not establish lower metered reads.
- **Budget the whole report.** Record all statements' metered reads and their total, then compare cost with cold report requests, other account activity, and the current plan. Share a bounded production-query plan across delegated workers and reuse captures. Inspect the saved GraphQL query and variables before comparing windows; rolling totals, UTC-day totals, and adaptive query profiles are separate evidence. Machine-shared CLI logs do not identify the responsible task or person without a link to that work.
- **Preserve the report cache contract.** Stats use one shared assessment and Worker Cache API entries for at most one hour, capped at UTC midnight. Keys include validated filters, the referral-policy hash, and `STATS_REPORT_VERSION`; bump the latter for changed report semantics, public selection, or storage binding. Preserve calculation time on cache reuse and verify expiry, errors, and a real hit. Cache storage is per data center and coalescing per isolate, so neither guarantees a global read budget. Execute SQL through local D1 before a bounded production check; Node SQLite can accept SQL that D1 rejects.
- **Separate implementation from acceptance.** Record code commit, deployment activation, local checks, and successful production behavior separately. A homepage response, accepted deployment, or one small successful database read does not verify subscription completion, an analytics report, cache reuse, or account-wide quota recovery.
- **Bound recovery claims.** Report which stores and fields were inspected and which histories remain inaccessible. A request rejected before persistence has no subscriber row from that attempt; this does not establish that no older provider record exists. Error counts and shared browser properties do not identify people. Keep addresses and tokens out of public evidence and ordinary diagnostics.
- **Leave a usable checkpoint.** Before a break, update the worklist with completed evidence, remaining checks, concrete access blockers, artifact locations, and the next bounded action. Keep unfinished tasks unfinished; an `in_progress` status records work to resume, not a claim that an agent is still running. Preserve complete shaping prompts under the existing provenance rules, keep private captures outside Git, and commit/push the authorized changes without disturbing concurrent work.
- **Preserve working copies.** When work spans checkouts, inspect linked worktrees as well as the current branch. Preserve uncommitted work outside temporary storage with its base commit, file manifest, and verified hashes. Record how to recover it in a fresh checkout and compare it with current `main`; an archive is not evidence that an old patch should be merged. Keep private logs private, and keep later housekeeping outside a released article's frozen footprint.
- **Isolate builds from active development.** Before a production build that cleans `dist`, check whether another session's development server is writing there. Use an isolated checkout when output directories would conflict. Do not stop another session's server to make a build pass. Article 025's shared-checkout build hit `ENOTEMPTY`; its isolated build and published-byte verification passed.
