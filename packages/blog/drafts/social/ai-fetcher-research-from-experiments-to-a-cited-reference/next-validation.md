# Next validation that would change a reader's decision

November 1, 2026. These are proposed experiments, not new findings or scheduled work. The accepted [service and native evidence](../../research/fetcher-study-v2/23-expanded-publication-acceptance.md) stays complete. A supplied-URL trial measures retrieval and task performance; it does not measure organic discovery or citation ranking.

## 1. Does the answer use the new page body?

The current request/receipt/row chain establishes captured delivery. A correct quote from an existing public article is a content check, but it does not isolate whether the answer used a newly retrieved body. The next useful result is an independently checkable freshness test.

Prepare one dedicated public test page with a random marker sentence that appears only in its body. Keep the marker out of the prompt, title, URL, metadata and public research notes until capture ends. Keep assigned labels private during the trial too. Record the actual served body hash and publication time; distinguish that from a deployment acknowledgement. Establish how these deliberate trials are excluded from audience interpretation before execution.

Start with six real UI tasks: ChatGPT and Grok, three conditions each, fresh chats and the visible configuration recorded:

1. Fetch body version A and ask for its marker sentence.
2. Publish and verify version B, then ask through the same assigned URL in a fresh chat.
3. Ask for version B through a separately labelled query URL.

Freeze the order and exact prompts before running. Preserve cache policy and available response/version evidence. The third condition changes the URL as well as the cache opportunity; it must remain a separately reported condition. Never open an assistant's assigned URL as an operator control.

For each task, record answer marker/H1, visible tool result, request/response time, invocation/acknowledgement/exact-row chain, exposed mode/model, and failures. An old marker after a fresh response is a failed freshness task; it does not identify which component cached, extracted or answered incorrectly. A missing origin match stays unavailable evidence. Six trials are a pilot, not a vendor reliability rate.

**Decision changed:** whether a developer can rely on this interface for newly published or changed content, and which retrieval/freshness distinction the maintained reference needs to teach. Stop after the frozen six tasks or an access/quota/challenge barrier; no protection bypass or background repeats.

## 2. Does an explicit Markdown URL fix this H1 task?

Grok's actual answer returned the document title as the H1, while its source panel contained both that title and the body heading. The internal cause remains unknown. This gives a concrete representation question rather than a generic claim that Markdown is better for agents.

Use the same dedicated content revision with deliberately different document title and body H1. Keep the requested answer out of the URL/prompt. Compare the HTML URL with its explicit Markdown twin, interleaving order across fresh chats. A first bounded design is three available products × two representations × three runs: 18 tasks. Freeze eligibility and exact visible modes first; unavailable products are reported rather than replaced silently.

Score body-H1 accuracy and the exact requested sentence/marker separately. Keep missing tools, access failures, origin matches and answer errors distinct. Each product/mode retains its own denominator. Route, representation, source-body revision, source panel and retained-header limits belong beside the result. Do not infer the model identifier behind Auto or Medium.

**Decision changed:** whether to recommend an explicit Markdown link for this known-site task or revise the title/heading presentation. It would establish task performance under the tested conditions, not an SEO or organic-citation benefit.

## 3. Can another operator reproduce the chain?

The [minimal Worker example](https://github.com/gkoreli/blog/tree/main/packages/analytics/examples/minimal-worker) already has local portability checks. Our own second deployment would still be our deployment. The new evidence needs a willing outside operator, their own account/domain and a real decision they want the analytics to support.

Package the existing example, frozen prompt/label instructions and one compact result schema. The kit should help the operator use an actual assistant interface, capture the invocation and acknowledged insert, and compare the exact stored row. Do not replace that step with manufactured vendor headers. Record setup failures and operating cost as well as successful collection. Publish minimized results only; raw addresses, references, signatures, credentials and account captures stay with the operator.

Use an inbound invitation or a reader who volunteers. No unsolicited issue promotion or mass direct messages are part of the plan. An independent successful install and a reported use of its result would establish more than our existing local harness; neither is claimed yet.

**Decision changed:** which blog-specific assumptions need removing before the analytics is useful to other sites.

## 4. How often do verified operator types share the same category?

Repeat a fixed task across dates and exposed modes, with operator identity known from the controlled procedure. Add consenting human-operated controls only if evaluating a person-versus-agent decision. Do not use User-Agent, an IP flag or `Sec-Fetch-User: ?1` as the ground-truth label.

Browser is currently a request classification. An agent receiving that category is not automatically a classifier defect. Define the decision being evaluated before reporting false-positive/false-negative rates; preserve per-cohort denominators and method/version changes. A small controlled cohort cannot estimate the composition of all site traffic.

**Decision changed:** how to present verified agents, declared agents and unattributed browser-like requests, and whether a proposed stronger identity claim has any measured basis.
