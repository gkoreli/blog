The publishing coordinator owns server changes, the article and frozen queue, integrated release checks, and the overarching worklist. ## Failures established before the repair

Three regression cases failed against the preceding client before implementation: a repeated provider-ready signal created another widget while a signup POST was pending; a callback from that new widget could abort the pending signup; and an `execute()` exception after a synchronous successful callback could abort a request already handed off. The before-run capture is private. These are reproducible ordering failures, not evidence of their production frequency or of lost customers.

Further review found that status 202 alone confirmed acceptance, response bodies had no client-side byte/read budget, and cleanup from a render returning late could clear a replacement widget if native removal threw. These cases now have focused regression coverage. An idle form now creates no provider widget, so a provider session cannot be mistaken for a submitted signup before there is an attempt.

## Domain and adapters

[`SubscriptionAttempt`](../../../src/client/subscription-attempt.ts) owns identity, verification steps, absolute deadlines, one recovery, token handoff and settlement. It contains no DOM, provider API, fetch, email, attribution or logging. A single handoff changes verification to sending; verification callbacks cannot settle or revive the sending attempt. Commands check the clock themselves, because background tabs can delay timer callbacks.

[`subscribe.ts`](../../../src/client/subscribe.ts) coordinates private captured intent and attempt-owned resources. Each widget has a separate lease. Retiring a lease precedes provider cleanup; callbacks from retired leases are ignored. Whole-slot cleanup additionally checks the current widget lease, including when an old `render()` returns after replacement. Terminal UI and ownership changes precede cleanup/reporting so reentrant effects cannot overwrite a newer attempt. Each form owns its own current attempt. Initialization uses a `WeakSet`, rather than trusting a copied DOM marker.

[`turnstile-adapter.ts`](../../../src/client/turnstile-adapter.ts) checks the native API surface and subscribes to loader events only while a submitted attempt waits. [`subscription-request.ts`](../../../src/client/subscription-request.ts) bounds actual encoded JSON at 4096 bytes, preserving the existing `{email,turnstile,source}` contract. Optional attribution yields first. It does not normalize email or change server admission rules. An envelope that still cannot fit fails before handoff or POST. [`subscription-response.ts`](../../../src/client/subscription-response.ts) confirms only direct HTTP 202 with a JSON media type and a bounded `{ok:true}` envelope. Empty, HTML, malformed, oversized or unreadable bodies remain unconfirmed; no automatic signup POST replay is introduced.

This is a small attempt model and explicit adapters, not a new application framework. The installed `@nisli/core` README and native implementation describe `resource()` as asynchronous derivation with stale work abortion, refresh and disposal. A mail-triggering POST has uncertain completion after client cancellation; it is not interchangeable with a derived value that can simply be refetched. The native SSG renderer remains responsible for form snapshots, and the standard form remains readable with JavaScript unavailable.

## Provider and timing decisions

The current official [rendering documentation](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/), [configuration reference](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/), [client-error guide](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/) and [testing guide](https://developers.cloudflare.com/turnstile/troubleshooting/testing/) were checked alongside the actual provider script. Native `api.js` captured at 06:18:30 UTC: **86,756 bytes**, SHA256 **f81aea26170f33b3fc344bcfcdfc5f578b90008ea7fd1366d77a99964cf8ae58**. The raw script/readable transform stay outside Git.

Native inspection confirmed three relevant behaviors: `ready()` rejects deferred/async loading with 3857; `execute()` can synchronously call the success callback with an existing token; and a handled error callback does not independently disable native automatic retry. Consequently, the deferred named-onload contract stays in place, execution state changes precede `execute()`, and recovery now uses **`retry:'never'` plus at most one application-owned fresh widget**. The replacement keeps the same attempt ID and absolute deadline. The handler returns `true`, and recovery is restricted to the existing selected retryable code families; no undocumented suffix is interpreted as a cause.

Verification gets 30 seconds. The first interactive callback can grant one 120-second window; repeated before/after callbacks update the current UI without extending it again. A recovered widget retains that deadline. Sending keeps its existing 35-second absolute budget, including body consumption. This allows the current nominal maximum 29 seconds of provider waits (two 5-second Siteverify attempts, two 8-second email attempts, up to 3 seconds of rate-limit waiting) about 6 seconds of headroom; database/network work has no implied hard guarantee. Changing that budget requires considering the server policy, not only a browser timeout.

Browser fetch uses `redirect:'error'`. Native browser testing rejected a 302 without requesting the target. The server workstream separately established that Workers at the configured compatibility date needs `redirect:'manual'` plus explicit 3xx rejection. Runtime-specific behavior matters; browser acceptance does not establish workerd behavior.

## Acceptance so far

- **98 focused cases pass**, covering the actual initializer, generated invalid domain-command orders, stale/reentrant callbacks, absolute deadlines without timer execution, outgoing UTF-8/JSON byte costs, bounded streamed responses and cancellation that never finishes. Blog source/worker typecheck passes. The actual SSG/DOM tests cover unique label/status targets, native input validity, overlapping forms, and clones carrying a copied initialization marker.
- A loopback-only [native browser fixture](../../../test/fixtures/subscription-browser.ts) bundles the actual subscription initializer and default logger, renders the actual SSG forms/bootstrap, and fetches Cloudflare's native script from its official URL. Its controlled receiver accepts only the official dummy token and an `@example.invalid` address. It sends no email and uses no production credentials. It is a browser/provider acceptance fixture, not proof of newsletter-server admission, production hostname/action checks or delivery.
- In the native in-app browser, two valid dummy-key forms stayed pending concurrently across a repeated provider-ready signal. The receiver saw exactly two signup POSTs with distinct attempt IDs, then both forms accepted direct 202 JSON after release. There were no idle or final leftover iframes and no diagnostics in that controlled success case.
- The official always-fail key produced two `600010` callback reports under one attempt ID: first `automatic-retry`, then `manual-retry`. Both were verifying/not-started; the receiver saw zero signup POSTs, the final button was usable, and the native console had no warning/error messages. This supports the selected recovery policy under the documented dummy behavior, not the cause of production `300031`.
- An actual 202 HTML response remained unconfirmed with check-inbox guidance. Its default-logger report preserved status 202, response request ID, attempt ID and sending/removed phase while excluding body text. A native 302 produced one signup POST and zero redirect-target requests, with an uncertain network result in the client.
- Enforced fixture CSP blocked the actual provider URL: bootstrap recorded the script/CSP stages, and submission immediately reported unavailable/verifying/not-started. A missing main bundle left both SSG form buttons disabled and displayed bootstrap guidance on both forms. That latter UI observation does not by itself confirm diagnostic storage.

An early loader fixture used a different local missing-script URL; it did not exercise the provider resource classifier and was replaced by the enforced-CSP case above. A loopback CLI receipt read was denied by the sandbox; browser DOM/receiver evidence was saved for the measured cases, and no native-storage claim is made for the main-bundle case. No production signup, real-person email, or production row mutation occurred in these browser checks. All owned local fixture servers were stopped.
