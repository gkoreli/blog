# Widget errors do not count attempted subscriptions

October 29, 2026 UTC. Follows the [rendered-key repair](17-rendered-sitekey-regression.md) and the [readership audit](../analytics-retrospective/94-reader-growth-and-editorial-decisions.md). The question is whether retained diagnostics establish the repair's historical impact. They do not, but they expose which evidence we need next.

## What the bounded read found

One frozen Wrangler `--command` SELECT reads only the `subscribe_form` component, with a 1,001-row sentinel and a maximum accepted scope of 1,000. The [SQL](subscription-error-audit.sql) returns aggregate counts/days and fourteen current stage names or `other-stage`. It returns no paths, raw messages, build values, user agents, referrers, addresses, tokens, stacks or row identifiers.

The [result](subscription-error-audit-production.json) contains 45 retained component reports. Of those, **35 have ingestion timestamps from October 1 at 00:00:00 through October 29 before 22:59:00 UTC**; ten are outside that window. No timestamp is malformed. All 35 window reports have the generic `subscribe_widget_error` stage and no build ID. Their ingestion dates span October 1–21. There are **zero stored missing-configuration reports** in the window. No raw diagnostic record is exported.

The one agent/provider attempt costs **341 reported reads and zero diagnostic writes**. These are query-work meters, not counts of people or failed signups. There is no site visit, report calculation, production POST, email, migration or configuration change in this slice. The underlying logger's retention code deletes records older than thirty days; this query does not verify each cleanup execution or reconstruct earlier history.

## Why this cannot measure lost subscribers

The current initializer renders the widget before a submit. Its error callback emits the same static stage whether an attempt is active or not. A new [counterexample test](../../../test/subscribe.test.ts) invokes that callback with an empty field and no submit: one widget-error report, zero challenge executions and zero signup requests. Missing-key/slot controls also assert that initialization alone emits no report; a valid-input submit emits the configuration stage. These are controlled client labels, not historical event labels or vendor/browser accuracy measurements.

Cloudflare documents [multiple causes of the callback](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/), including connectivity, compatibility, configuration and challenge errors. Its [error-code reference](https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/) distinguishes invalid keys, unauthorized hostnames, iframe-load errors and other failures. Our callback discards the provider code and operation phase. The retained generic stage cannot identify which cause occurred, whether an attempt began, whether a retry later succeeded, or whether the operator was human. Do not relabel these 35 reports as 35 lost subscriptions or 35 bots.

Zero configuration reports does not establish zero affected attempts. The [Beacon draft](https://www.w3.org/TR/beacon/#return-value) specifies that `true` means queued, without information about transfer success. Our fallback fetch ignores HTTP status; the logger swallows transport failures. The [Worker handler](../../../../client-observability/src/server.ts) returns 204 while a caught D1 write runs under `waitUntil`. Cloudflare [documents that background lifetime](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil); it is not a persistence acknowledgment. The parser accepts `occurredAt`, but [storage](../../../../client-observability/src/db.ts) omits it. The query therefore uses server ingestion time. These are inspected implementation gaps, not measured causes of loss for this cohort.

## Checks and next implementation

Native D1 tests use the actual migration and confirm the component index. Twelve fixture records cover exact endpoints, repeated reports, arbitrary-message folding, unexpected event type and invalid timestamps; eight malformed response controls fail closed. Adding 4,096 unrelated-component records leaves results and the 73-read local meter unchanged. The 1,001 matching-row sentinel is rejected after 7,992 local reads. The 15,000-read review threshold is a post-execution check, not a database cap. [Native receipt](subscription-error-audit-native.json). An initial sandbox loopback denial occurs before fixture execution; the authorized native run passes and disposes its runtime. All 129 site tests and workspace types pass. No production runtime changes or new publication acceptance are claimed.

Next, add bounded operation-phase and provider-error metadata with explicit missing/unknown states. Preserve exact occurrence/build identity and make acknowledgment semantics truthful through the existing TASK-0125/0126 work. Do not reuse HTTP status for a provider code, store arbitrary callback text, or retrospectively fill absent fields. OpenTelemetry's [development guidance on recording errors](https://opentelemetry.io/docs/specs/semconv/general/recording-errors/) offers a useful design reference: define the operation, distinguish recovered errors from its final result, and use consistent error types. This is borrowed guidance, not an adopted SDK or an implemented conversion denominator.

The broader analytics goal remains open. This evidence qualifies conversion interpretation; it supplies no human-growth, search-intent or article-usefulness measurement. Search Console sign-in and Duck.ai terms approval remain pending; human trials remain deferred. Article 023/030 prose and existing traffic counts are unchanged.
