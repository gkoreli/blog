## Hermes Agent

**State:** selected; consequential source paths partly understood; no local execution. MIT. Released source **v0.23.2**, [`ae2a81ccc00e9b7c06301523e5bb09608397149c`](https://github.com/NousResearch/hermes-agent/tree/ae2a81ccc00e9b7c06301523e5bb09608397149c). [README](https://github.com/NousResearch/hermes-agent/blob/ae2a81ccc00e9b7c06301523e5bb09608397149c/README.md).

**User and stake.** A CLI/gateway agent that retains curated knowledge, recalls sessions and creates reusable skills. The useful question is which kind of continuity survives a new session and what curation the operator still owes it. Its own curated memory, session retrieval, skill files and optional external providers must be assessed separately. An existing coding agent plus maintained instructions and scripts is a relevant alternative; no comparative task result exists yet.

**Called source inspected.** [Memory tool](https://github.com/NousResearch/hermes-agent/blob/ae2a81ccc00e9b7c06301523e5bb09608397149c/tools/memory_tool.py), [store](https://github.com/NousResearch/hermes-agent/blob/ae2a81ccc00e9b7c06301523e5bb09608397149c/tools/memory_tool_store.py), [provider resolution](https://github.com/NousResearch/hermes-agent/blob/ae2a81ccc00e9b7c06301523e5bb09608397149c/agent/memory_provider.py) and [agent initialization](https://github.com/NousResearch/hermes-agent/blob/ae2a81ccc00e9b7c06301523e5bb09608397149c/agent/agent_init_memory_provider.py). Tool mutations reach bounded file-backed `MEMORY.md`/`USER.md` entries separated by `§`; writes take a separate lock and use atomic replacement. Existing unreadable files and destructive external drift have refusal paths. Load builds a frozen system-prompt snapshot. Threat scanning affects that snapshot; the raw live entries remain available. These protections are inspected, not independently exercised.

The provider resolver distinguishes built-in memory from plugins and emits warnings rather than silently dropping a missing configured provider. Startup recovery can fetch/install a provider, so importing and starting the whole agent is not a neutral memory test. No installer, gateway, external provider, profile or shell configuration was changed.

**History and people.** Recent store history includes budget/removal corrections on October 25 and a hosted-scope gate on November 11. These concern ordinary memory maintenance, not evidence that task success improves with use. [Issue #156389](https://github.com/NousResearch/hermes-agent/issues/156389), by `menhguin` through his agent, reports a benign strict-scan match hiding an entire hand-maintained profile from the prompt. The reported setup was v0.23.0 with local commits; its scanner check used later main, and the author explicitly did not claim a clean end-to-end main run. A [contributor's fork experiment](https://github.com/NousResearch/hermes-agent/issues/156389#issuecomment-6915759949) reports line-level masking for large profiles; that is not an accepted upstream fix or our reproduction.

**Claim → evidence → consequence.** The pinned store explains the reported mechanism: without delimiters, prose is one entry; one match can replace that whole entry in the prompt snapshot. Loading alone does **not** erase the on-disk profile. The distinction between lost prompt context and lost disk data matters. Curated persistence is concrete; better reasoning, successful automatic skill reuse and learning by changing model weights have not been demonstrated by this work.

**Proposed trial, not run.** Use an owned Hermes home and actual store/scanner/writer dependencies. Compare a clean profile, a mixed prose profile containing a benign scanner match, and the same content split into entries. Inspect both disk bytes and the rendered prompt after reload. Add concurrent writers, lower-budget removal and external drift only where they change advice. Then trace actual skill creation/retrieval and test reuse on a second representative task against a no-skill control. Do not count a stored file as successful reuse.

**Take so far / next action.** Worth deeper review because its continuity mechanisms are inspectable and operationally different. First execute the real store load/mutation/reopen path; follow the skill path before accepting the broad continuity proposition. No adoption recommendation yet.

## NemoClaw

**State:** selected; orchestration/policy boundary partly understood; live runtime untested. Apache-2.0. Default-branch snapshot [`1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d`](https://github.com/NVIDIA/NemoClaw/tree/1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d), not an ordinary stable release. [README](https://github.com/NVIDIA/NemoClaw/blob/1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d/README.md).

**User and stake.** An alpha reference stack for operating supported agents, including OpenClaw, Hermes and Deep Agents, through OpenShell. It supplies onboarding, managed inference, integration configuration, policy operations and lifecycle work. The immediate alternatives are running the agent directly or operating OpenShell yourself. The wrapper's value must be judged by work it makes reliable and repeatable.

**Called source inspected.** The policy command enters [policy-channel](https://github.com/NVIDIA/NemoClaw/blob/1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d/src/lib/actions/sandbox/policy-channel.ts); this large action is only partly read. The [blueprint policy client](https://github.com/NVIDIA/NemoClaw/blob/1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d/nemoclaw/src/blueprint/openshell-policy.ts) builds real OpenShell calls through an injected execution boundary. The source for the shared compiled `.cjs` import is [openshell-policy-boundary.cts](https://github.com/NVIDIA/NemoClaw/blob/1981b81a3d39ca3e58d4f5aae0bce7d2b7051b0d/nemoclaw/src/shared/openshell-policy-boundary.cts).

Its inspected functions distinguish base/effective/revision reads, issue `policy set --wait`, and classify a write as applied, authoritatively rejected or ambiguous. A transport error is not casually treated as proof the write was rejected. This is useful control-plane design; parsing and command construction alone do not prove sandbox enforcement.

**History and people.** The merged [policy-authority change #10515](https://github.com/NVIDIA/NemoClaw/pull/10515) explicitly removes NemoClaw's durable second policy lifecycle in favor of OpenShell state. Its claimed lifecycle qualifications and test totals are maintainer-reported, not tests run here. Current typed-boundary history includes [custom endpoint conflict handling](https://github.com/NVIDIA/NemoClaw/commit/444ce08acf2aa036060448357a0e36cfc6eb7b23).

[Report #13904](https://github.com/NVIDIA/NemoClaw/issues/13904) describes a compatible-provider switch on Ubuntu 26.04/NemoClaw v0.0.139/OpenShell 0.0.116: overlapping pinned/unpinned network policy refused the switch and left a generated provider. It is closed, and the corrective commit is in the selected source. Do not present the old state as a reproduced current defect. The report is useful because it distinguishes OpenShell's refusal from NemoClaw's partial resource cleanup. The older Apple Silicon snapshot [report #4071](https://github.com/NVIDIA/NemoClaw/issues/4071) is also closed and version-specific; no current failure is inferred from it.

**Claim → evidence → consequence.** [NVIDIA's current architecture overview](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/about/how-it-works) assigns the enforcement boundary to OpenShell and describes NemoClaw as orchestration around it. [Prerequisites](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/get-started/prerequisites) document container/runtime requirements and potentially consequential installer changes. These are live, unversioned docs, read November 16. The selected source supports the policy-authority separation; credential custody, actual egress enforcement and replacement persistence have not been independently checked.

**Proposed trial, not run.** First resolve an installable artifact to source/runtime versions. In an owned supported environment, use a local allowed endpoint and denied endpoint; mutate policy, inspect the actual applied revision, introduce a controlled ambiguous write result, and replace the sandbox. Inspect policy and workspace preservation after replacement. Compare direct OpenShell where useful. No provider key is necessary for a policy-only trial. A fake command capture may qualify orchestration but cannot stand in for this enforcement result.

**Take so far / next action.** The project deserves attention for lifecycle integration and explicit authority boundaries. It is not yet qualified for a security or reliability recommendation. Finish artifact mapping and one real supported runtime sequence; narrow or drop the entry if that essential evidence remains unavailable.

## Plannotator

**State:** selected; release capability/targeting and reply-ownership paths partly understood; no local execution. MIT or Apache-2.0. **v0.28.66**, [`85e847e8369189ee4027598212623edfe0cd1602`](https://github.com/backnotprop/plannotator/tree/85e847e8369189ee4027598212623edfe0cd1602). [README](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/README.md).

**User and stake.** Review plans/code and keep replies connected to local or paired agents across sessions. The current project is broader than a plan-annotation screen. A reader needs to know whether feedback reaches the intended work, especially when an agent goes away and another reads the shared thread. Agent-native plan/review interfaces and a normal Git review remain relevant alternatives; no comparative workflow cost has been measured.

**Called source inspected.** [Inbox capability](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/packages/server/inbox-capability.ts), [plans capability](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/packages/server/plans-capability.ts), [plan approval](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/apps/hook/server/mod-plan-approval.ts) and [decision target](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/apps/hook/server/decision-target.ts). Disabled plans do not mount/import their store. Enabled plans use background import and capability routes. Approval targets come from resolved server state; the review-id hint is scrubbed before a child inherits it. This is inspected targeting, not an approval-isolation test.

Reply settlement was followed into `markAgentChecked`, `owedToAnother` and `settleReadPast` in the released [Inbox store](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/packages/shared/inbox/store.ts#L3839), and the gone/unreachable distinction in [T3 wake](https://github.com/backnotprop/plannotator/blob/85e847e8369189ee4027598212623edfe0cd1602/packages/server/inbox-t3-wake.ts#L667). Only those portions of the large files were read. A different reader does not automatically settle a reply owed to a recipient the Inbox may still wake. Known-gone and temporarily unreachable are different states.

**History and people.** The project [relicensed in February](https://github.com/backnotprop/plannotator/pull/144); current source contains both license files. November 15 store changes include routing to a new session after the one asked has ended. [Report #3339](https://github.com/backnotprop/plannotator/issues/3339), by `stjepanvrbic`, supplies a concrete multi-reader/late-grant case, not a general adoption claim. The [maintainer's response](https://github.com/backnotprop/plannotator/issues/3339#issuecomment-6881466766) explains the fix and a remaining tradeoff: without a grant or authoritative disappearance signal, the Inbox cannot distinguish a dead thread from a live one. [Fix #3348](https://github.com/backnotprop/plannotator/pull/3348) merged November 14; the selected release's inspected code contains the ownership rule. No independent reproduction has run here.

**Claim → evidence → consequence.** Keeping a reply safe from the wrong reader may leave it waiting when liveness is unknowable. That is a useful operational tradeoff, not a universal delivery guarantee. The release's new integrations and mobile/cloud capabilities need their own supported paths; the README is not evidence that every host has been exercised.

**Proposed trial, not run.** Use actual Inbox store/routes and an owned data directory. Compare intended recipient, another reader before grant, later grant, temporarily unreachable session and confirmed-gone session. Inspect both message delivery state and the recipient send; verify restart persistence and a no-grant control. Start without model calls or host configuration changes; a later supported host trial is still necessary for a full integration take.

**Take so far / next action.** There is a concrete review-delivery question worth testing, beyond screenshots of an annotation UI. Run the ownership/liveness cases at this release pin and reconstruct the material product expansion before writing the entry.

## CodeRelay

**State:** selected; actual bounded HTTP/store path exercised; local agent-launch sequence inspected but not executed. MIT; built on T3 Code. Snapshot [`ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8`](https://github.com/AymanAhsan/CodeRelay/tree/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8). [README](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/README.md), [team-hub guide](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/docs/user/team-hub.md).

**User and stake.** Teammates keep their agents/code locally while exchanging suggested work, pinned contract files and completion receipts. Ordinary Git branches/specs plus PRs are a useful baseline; direct T3 Code comparison remains unperformed. Retaining T3 copyright and an initial import means feature authorship/novelty must not be inferred from the product name.

**Action traced.** Actual [HTTP handler](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/apps/hub/src/server.ts) → [schema/helper definitions](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/packages/contracts/src/teamHub.ts) → [SQLite store](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/apps/hub/src/store.ts). Posting starts a suggested task and records who owes agreement; revisions update the pinned SHA and consent state; explicit agreement compares the supplied SHA. Completion records a branch, SHA and summary in the same transaction as its activity receipt.

The actual local [decision service](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/apps/server/src/teamHub/TeamHubTaskDecisionService.ts#L116) reads its snapshot, resolves the repository/project and provider, builds a task prompt from that snapshot, launches a thread, then accepts through the hub. Automatic starts reserve a token and contract SHA before launch. Manual acceptance supplies no observed SHA. The [local HTTP route](https://github.com/AymanAhsan/CodeRelay/blob/ba0f79b7d81c3508e5d6fd95fd915b0babf54ac8/apps/server/src/teamHub/http.ts#L149) forwards task ID and decision. The service's tests and upstream store tests were inspected, not run.

**Executed result.** [Protocol, fixture and receipt](coderelay/README.md) retain eleven conditions against the unchanged hub server/store and actual schemas on Node 24.14.1/macOS arm64. Fictional Bob reads authored contract A; Alice revises to B. Explicit agreement at A returns **409**. The manual decision endpoint accepts without an observed SHA and records B as accepted. Agreement at current B succeeds. Bob's own revision remains blocked until Alice agrees; revising an accepted task is refused. These passing refusal controls matter: the result is a particular version-binding distinction, not absence of all consent.

A syntactically valid authored completion SHA and test-success text persist after SQLite close/reopen despite no Git repository or tests behind them. Another member, malformed SHA and duplicate completion are refused. This matches the guide's explicit boundary: completion is the agent's receipt, not an independent test certification or merge. It is not a reported defect.

**History and people.** The initial CodeRelay import is October 30; subsequent changes add prompt handoffs, queued reassignment, repository access status, opening/cloning the team project and broader installers. [Maintainer PR #6](https://github.com/AymanAhsan/CodeRelay/pull/6) explains why uncached but valid clones were rejected on acceptance; selected source resolves missing identities before matching. The latest twenty updated issue/PR records returned on this pass are maintainer PRs, not independent use reports. The scout's launch discussion had no comments at its dated capture. Neither observation establishes absence of users, satisfaction or demand.

**Unresolved consequential question.** Source inspection suggests a possible interleaving: the manual service can capture A, yield during project resolution/launch, then the hub can accept a newly revised B while the launched prompt still names A. The API result makes this worth testing. No actual local-service or UI race has been reproduced; do not call it a confirmed running-product defect. A connected WebSocket snapshot may update later, but the inspected function retains its captured task object.

**Take so far / next action.** The coordination state and receipts are useful concrete machinery, with clear human integration responsibilities. Reproduce or disprove that interleaving through the actual decision service with a controlled launch boundary; compare the shipped artifact and upstream T3 Code before any novelty or installation recommendation. The [attempt record](coderelay/attempts.json) keeps runtime/sandbox setup failures and a corrected fixture expectation.

## GoDoxy — return from #1

**State:** selected return; historical/current description compared and changed called code inspected; runtime untested. MIT plus Go-derived-code notices. **v0.34.0**, [`77cbac6b532d7d3881010eade21fe1a7f9e4bf8e`](https://github.com/yusing/godoxy/tree/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e). [Release](https://github.com/yusing/godoxy/releases/tag/v0.34.0).

**User and stake.** A self-hosted reverse proxy with route discovery, container operation and Proxmox integration. Compare operating an ordinary reverse proxy plus separate container/health tooling. Its broader management surface matters only if it behaves reliably through normal changes and failures. No throughput, cost-saving or production reliability measurement exists in this work.

**What persisted.** [#1](../../../posts/002-oss-radar-01-vercel-winter-2026-cohort.md) already described Proxmox and idle sleep. The [reconstructed March 19 README](https://github.com/yusing/godoxy/blob/213e4a5cdb635bf1f5f5985fd04515ad592497d5/README.md) documents those capabilities, Docker/Podman discovery and lifecycle/log UI. The exact original audited revision is unknown. The current [README](https://github.com/yusing/godoxy/blob/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e/README.md) preserves those jobs. A larger management description is not evidence of a pivot, newly invented integration or measured economic advantage.

**Changed action inspected.** November 16 adds daily health-notification silence windows. [Parsing/membership](https://github.com/yusing/godoxy/blob/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e/internal/health/silence.go) validates clock ranges and uses start-inclusive/end-exclusive windows, including cross-midnight ranges. [Health configuration](https://github.com/yusing/godoxy/blob/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e/internal/health/health.go) supplies `IsSilenced`; the actual [monitor](https://github.com/yusing/godoxy/blob/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e/internal/health/monitor/monitor.go) checks it at the down-notification gate. Source intends to defer an outstanding down notice until an eligible check after silence ends, and to send recovery only after a down notice was sent. Notification delivery, timezone configuration and reload behavior remain untested.

**People and contrary evidence.** [PR #296](https://github.com/yusing/godoxy/pull/296), by `hfabre`, explains a daily backup window that causes unwanted downtime alerts. This is a contributor's firsthand use case; it is not evidence every deployment needs the feature. The November 16 [startup report #298](https://github.com/yusing/godoxy/issues/298) compares v0.31.4 with v0.32.0/v0.33.0 when autocert is absent. [The maintainer](https://github.com/yusing/godoxy/issues/298#issuecomment-6910386206) says the setup script was fixed and explicitly declines a general missing-certificate fallback.

The selected [setup script](https://github.com/yusing/godoxy/blob/77cbac6b532d7d3881010eade21fe1a7f9e4bf8e/scripts/setup.sh#L352) writes an empty `GODOXY_HTTPS_ADDR` when autocert was not configured. This is an explicit HTTP-only setup choice; it does not prove arbitrary certificate failures now fall back to HTTP. The distinction corrects an overly broad reading of the release note. No setup script or real listener was run.

**Proposed trial, not run.** Use the actual monitor with an owned notification sink and controlled time: ordinary failure, failure wholly inside silence then recovery, still down when silence ends, and recovery after a delivered down notice. Inspect notification contents/counts and current health state, not only `Contains`. Include a cross-midnight/local-time case and route-level opt-out if those remain part of the entry. Separately inspect generated setup state after declining autocert and retain a missing-certificate refusal control.

The current module declares Go **1.27.0** and several local/submodule replacements. Only Go 1.26.2 was found installed; an unconfigured shim failed before a project build. No build, module downgrade, global toolchain change or container installation was performed. Resolve the actual toolchain/submodules in an owned checkout before running the monitor; a copied parser test would not be a full product evaluation.

**Take so far / next action.** The return can replace #1's broad promise with evidence about operation over time. Finish the notification sequence and historical implementation comparison. Keep setup handling separate from runtime certificate failure. Source inspection is sufficient to choose this research, not to declare the return review done.
