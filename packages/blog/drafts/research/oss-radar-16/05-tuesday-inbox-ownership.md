## The project beyond plan annotation

Plannotator gives people a place to review agent work and return actionable feedback: plan and document annotations, code review, artifacts and an asynchronous Inbox. Its [February checkpoint README](https://github.com/backnotprop/plannotator/blob/1d2948b6a6add18eac70b3511e3c7aa92473411f/README.md) centered the project on visual plan review for Claude Code and OpenCode; it already described code review as a January addition. The [current README](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/README.md#plannotator-inbox) places an Inbox for multiple coding agents and personal assistants beside those review surfaces. This is an expansion of the documented product, not evidence that it abandoned plan review or the date every Inbox feature first shipped.

The current source still documents the synchronous plan-review hook: an agent's plan opens a local review surface, then approval or structured rejection returns to the session. The Inbox is a different workflow: agents leave durable work for the person, whose later answer has to find its recipient. That changes the engineering problem from drawing annotations to maintaining ownership while sessions, connections and grants come and go.

It does not replace a coding agent or its provider. It supplies the review and feedback path around them. A prospective user must still operate the local Inbox and the chosen host connection/grant, and understand that different hosts have different identity and wake behavior. Our trial exercises the T3 component path, not the README's full integration list.

The [February relicensing PR #144](https://github.com/backnotprop/plannotator/pull/144) replaced BSL-1.1 with a choice of MIT or Apache-2.0 on February 12. Both current license files byte-match the files checked in v0.28.66. Do not describe the earlier BSL checkpoint as already carrying today's permissive licenses.

The handoff proposed v0.28.66. Release notes include thread mentions, Linear cards/account setup, linked-machine artifacts and configuration-save fixes. Those are release-reported changes, not additional product trials here. The T3 wake file is byte-identical across the two releases. The store has changes elsewhere, so the whole new source archive was used rather than substituting one file.

The [store](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/shared/inbox/store.ts) is a single-writer in-memory view backed by the default [append-only per-project JSONL log](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/shared/inbox/store-log/jsonl-log.ts). It shares reply rules between callers. An agent read can advance the thread's checked mark; it does not need to put a delivery object on every reply. Consequently, both pending state and the persisted checked mark matter when inspecting whether another reader consumed a reply.

The called delivery path is actual store reply → [T3 wake](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/server/inbox-t3-wake.ts) → saved fixture grant through real [credentials](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/t3-code/auth.ts) → actual [delivery record](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/t3-code/delivery.ts) and [thread client](https://github.com/backnotprop/plannotator/blob/969084882013ac7634283ebca06f3118e766d30d/packages/t3-code/t3-client.ts) → scripted RPC. Its queued response returns through the real validation and persistence paths. No real T3 server, model, provider, user account, personal Inbox or external message was used.

The environment was Bun 1.4.0 on Darwin arm64. Actual workspace packages were linked using their package exports; 13 isolated external package versions match versions present in the upstream lock. Lifecycle scripts and runtime auto-install were disabled. The [121 runtime source hashes](plannotator/source-hashes.json) were verified before store creation, matched the observed closure afterward, and independently matched the pinned source archive. Logical clock advances test retry conditions; no latency benchmark is claimed.

## What happened

| Authored control | Observed result | Reader consequence |
| --- | --- | --- |
| Another reader, then a read without a session, before a grant | Neither consumed the unpromised T3 reply. It remained pending after reopening the JSONL store; the intended recipient's own read settled it | A T3 thread's stable identity survives unrelated readers even when the original message did not promise a wake |
| Restarted raw MCP client; T3-shaped identifier under an unrelated host | The newcomer exception settled both replies | This is host-aware ownership, not one universal strict-identity rule for every agent |
| No grant → another reader → store reopening → fixture grant appears | Initially recorded `sign_in`; the actual wake later submitted the person's words once to the intended T3 thread in queue mode. Another sweep did not submit a second copy. Delivery survived another store reopening | Late grant arrival worked through actual store/wake/receipt code under the scripted service control |
| Temporary lookup transport failure | The thread was not marked gone; another reader could not consume the reply. After recovery and advancing the controlled clock beyond the initial retry interval, one queued send was accepted | Failure to reach T3 is treated differently from an authoritative ended-thread response |
| A grant's initial lookup says it does not have the thread | No global gone state was established; the reply remained pending after another reader | One environment not having a thread does not prove no environment can reach it. This can leave work waiting |
| A previously reached thread's send returns `thread_not_found`, with no wake promised | The wake marked the session gone; a newcomer could then settle the reply. A later Inbox tool call cleared the known-gone state | The looser newcomer rule becomes available after this stronger disappearance signal |
| The same ended-thread control with `wakes: true` | The newcomer still could not settle it. After the session called again and the scripted send recovered, it was delivered | Explicitly promised wakes stay strict. The unpromised fallback must not be generalized to every reply |

The independently inspected late-grant artifacts contained five message-log records, one persisted delivery request and one queued receipt. The request id and exact submitted message matched the service submission. This establishes the Inbox's state transition after an accepted queued response. It does not establish that a real coding agent received a turn, read the reply or completed the requested change.

## Reports, contrary case and judgment

[Report #3339](https://github.com/backnotprop/plannotator/issues/3339), by `stjepanvrbic`, described a different reader swallowing a reply before its T3 grant arrived. [Correction #3348](https://github.com/backnotprop/plannotator/pull/3348), merged November 14, widened the ownership rule for sessions the Inbox could wake later. The [maintainer's response](https://github.com/backnotprop/plannotator/issues/3339#issuecomment-6881466766) also states the unresolved case: if no grant ever arrives, the Inbox cannot distinguish a dead thread from a live one merely by its silence. We exercised current released behavior consistent with that correction; we did not run the pre-fix version or reproduce the reporter's entire host setup.

The useful distinction is between preserving the person's answer and making progress on it. The tested T3 path favors keeping an answer for the right thread when it cannot establish that the thread ended. That is valuable when a person reviews several agents' work asynchronously, but a waiting row can still require operator judgment. The raw-MCP exception is another reason the eventual entry should explain the selected integration rather than present generic delivery guarantees.

The component evidence supports continuing the project review. A firm adoption take still needs the actual Inbox interaction and a supported live host path. What would change the judgment is a representative session showing whether a person can identify and recover a reply stranded by a missing grant, without forwarding it to the wrong agent. File persistence and a queued service receipt alone cannot answer that.
