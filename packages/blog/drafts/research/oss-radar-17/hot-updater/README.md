# Hot Updater's native fingerprint

November 19, 2026. Changing only the store build numbers left both fingerprints alone in the default bare adapter on Hot Updater 1.1.17. Adding a method to the shared React Native codegen spec changed both. Carrying forward a configuration that explicitly hashed the Xcode and Gradle build files brought the build-number churn back. [Fixture](fingerprint_trial.py) · [Results](results-2026-11-19.json).

## What changed since issue #1

[Issue #1](../../../../posts/002-oss-radar-01-vercel-winter-2026-cohort.md#hot-updater--kang-sungyu) covered the service as an over-the-air JavaScript update option for React Native teams moving off CodePush. The March 19 reconstruction at `b1f3fb155fe6b06acd27bcc1139de8450f7f35b1` shows the CLI calling `@expo/fingerprint` directly. The release history now gives a specific follow-up question. Can two store builds with the same native interface receive updates for the same fingerprint? [March source checkpoint](https://github.com/gronxb/hot-updater/blob/b1f3fb155fe6b06acd27bcc1139de8450f7f35b1/packages/hot-updater/src/utils/fingerprint/index.ts).

A bare React Native user on Hot Updater 1.0.2 and Expo Fingerprint 0.20.14 reported that changing a store build number changed the hash. Their configuration followed the older guide by adding the Xcode project and app Gradle files to `extraSources`. Those files also hold build numbers. The maintainer's RFC proposed hashing declarations that affect which native interface is available and then recomputing the hash during the native build. That work shipped in 1.1.0. ## What the CLI reads

`fingerprint create` loads the project config and records the two platform hashes with the adapter and fingerprint settings. The bare provider runs the project's React Native CLI `config` command to discover linked packages. The engine then hashes the React Native version, linked registry packages by name and version, app codegen config and selected spec files, relevant patches and declared settings. Android has explicit Hermes and architecture flags among its inputs. Codegen filenames and platform suffixes determine which spec bytes are hashed. This is a useful check on what the engine sees, with semantic compatibility still the app team's responsibility. [Bare provider](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/plugins/bare/src/bare.ts#L95-L105) · [Autolinking and settings](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/cli-tools/src/interfaceFingerprint.ts#L400-L460) · [Spec filter](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/cli-tools/src/interfaceFingerprint.ts#L479-L522) · [Digest construction](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/cli-tools/src/interfaceFingerprint.ts#L627-L841).

The native build command reads `fingerprint.json` and calls the adapter from its recorded inputs. It can fall back to the stored hash when an older file lacks those inputs. The iOS SDK's script uses the stored hash in Debug and can recompute it for the Release header. The deploy command compares the recorded and recomputed hashes and stops on a mismatch before it assigns a fingerprint to the release. [Read-only command](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/hot-updater/src/utils/fingerprint/recorded.ts#L58-L132) · [iOS script](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/react-native/ios/scripts/generate-fingerprint-hash.zsh#L48-L84) · [Deploy check](https://github.com/gronxb/hot-updater/blob/08a4cbca00214511ddb983a76a0a2b5781f7c8e1/packages/hot-updater/src/commands/deploy.ts#L753-L807).

## Released package trial

The fixture installed the published CLI, bare adapter and native SDK at all three version pins in separate directories. It used React Native 0.85.2 throughout and Expo Fingerprint 0.20.14 in the older setup. The user who reported the issue used React Native 0.86. Version 1.0.2's configuration explicitly tracks the two native build files. The newer baseline uses the bare adapter's default fingerprint settings. Each edit below starts from its stated baseline. [Exact source tags, npm integrity values, and observed hashes](results-2026-11-19.json).

| Edit | 1.0.2 with guide's build files | 1.1.0 and 1.1.17 |
| --- | --- | --- |
| Bump the iOS and Android store build numbers from 37 to 38 | Both hashes change | Both stay stable with default settings |
| Change ordinary UI source in the codegen directory | | Both stay stable |
| Add a method to the shared module spec | Both stay stable | Both change |
| Add an iOS-only module spec | | iOS changes, Android stays stable |
| Change an app Swift function's return value | | Both stay stable by default. Listing that file under iOS `extraSources` makes a further edit change only iOS |
| Keep the old `extraSources` build files and bump the build numbers | | Both change |
| Set a `nativeVersion` marker | | Both change |

Both newer CLIs returned the stored legacy hashes with a missing-inputs warning before `fingerprint create`. Creating the record again reported the engine change and wrote new hashes. In the later read-only trials, the deployment config deliberately threw on load. `fingerprint hash` still worked from the recorded inputs and left the file byte-for-byte intact. With a changed shared spec, the shipped iOS build script wrote the saved hash in the Debug header and the recomputed hash in the Release header. The Release run emitted a stale-record warning. The SDK script executed on Linux with synthetic Xcode environment variables. Compiling the app and reaching an installed binary with an update remain separate tests.

An initial two-version run established the build-number and spec result. The second attempt exhausted the 4 GiB guest disk when duplicate dependency trees filled it before the 1.1.17 command. The accepted third attempt cleared those replaceable dependency trees, used fresh fixture directories and covered all three versions, the SDK script, and the old-configuration control. The receipt retains the package lock hashes and 17 distinct package/version integrity values checked against npm. The fixture ran through npm with install scripts disabled on Alpine 3.23.4 ARM64. It requires Python 3.12, Node 24, npm 11, zsh, and room for the three dependency trees and package cache.

```sh
python3 fingerprint_trial.py /tmp/hot-updater-fingerprint-trial
```

## Judgment

The change makes build numbers a poor reason to create a new update target. For a team upgrading an existing bare app, the useful review is the old `extraSources` list and the set of native changes JavaScript actually depends on. Include stable compatibility inputs explicitly or move the `nativeVersion` marker when an untracked native change matters. Both tested newer baselines include the Hot Updater native SDK package as an input, so the same engine can yield a different fingerprint after a native dependency update. An existing binary keeps the value it already embedded. The maintainer calls for new store builds to move apps across the original engine change. Hot Updater's `appVersion` strategy offers manual version targeting when the team instead wants to maintain that mapping explicitly.
