## Yogurt — local meeting notes and assistant access

**State:** selected recording/transcription/notes wiring and assistant boundary inspected; scheduling and MCP/socket components exercised. Actual recording, recognition and summarization quality remain untested. [Repository at `ada44ea`](https://github.com/FrigadeHQ/yogurt/tree/ada44ea930d34b11742e2febc5b4f129261124cb), MIT; [launch discussion](https://news.ycombinator.com/item?id=50454625).

**Job and distinction.** A desktop meeting-notes application for people who want recordings, transcripts and notes on their own machine. The project uses Electron, local speech recognition and local model tooling. Its README describes whisper.cpp/Apple SpeechAnalyzer and llama.cpp paths, with substantial initial model downloads. This is a maintained application and model/runtime stack, rather than a small text-only CLI. Those descriptions were read; this investigation has not established end-to-end network independence or note quality.

**Main product path.** The inspected [`index.ts` wiring](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/index.ts) attaches capture and transcription to meeting events, and starts notes after the stopped state has been saved and recording/transcript finalization completes. [`asr/index.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/asr/index.ts) feeds PCM into a chunk pipeline and saves segments. At this pin, `APPLE_FINALS_LANGUAGES` is empty: Apple's speech supplies the live view where available; Whisper supplies saved final transcript lines. [`transcribe.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/asr/transcribe.ts) posts WAV chunks to the managed whisper-server, retains language decisions and filters selected silence/prompt-echo cases. That code does not establish measured recognition quality.

[`notes/index.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/notes/index.ts) queues enhancement, reads the person's notes and transcript, streams a draft and saves the enhanced result separately. [`notes/model.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/notes/model.ts) loads the selected local model and supports reading ahead. [`queue.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/notes/queue.ts) gives recording priority: on its small-Mac branch, notes wait during recording, running work is aborted/requeued, and unloading is requested. The actual app wires `smallMac` from total memory. Larger-Mac behavior also monitors transcription backlog; that branch was read, not exercised.

A second synthetic component trial used the unchanged queue, verified as Git blob `6cbf8a4788b13cdc74db0f5830ae29c430f3cb78`. An enhancement job waited during recording, began after stop, was aborted at the next recording, requested unload, and ran again after stop. The 24/32 GiB classification controls passed. [Receipt](results/yogurt-queue-01.json). The input deliberately selected `smallMac: true`; this is scheduling evidence, not actual capture, RAM use, model unloading or an assessment of a real 24 GiB Mac.

**Called path.** The optional MCP access path is concrete enough to inspect independently. [`server.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/mcp/server.ts) dispatches read-only meeting, transcript, note and audio-path requests against the application's store, checking an `enabled()` gate. [`socket.ts`](https://github.com/FrigadeHQ/yogurt/blob/ada44ea930d34b11742e2febc5b4f129261124cb/app/src/main/mcp/socket.ts) exposes it through a local Unix socket with mode 0600. The feature is off by default. The enabled gate is global; a client's displayed name is not a per-application credential. Same-user software can connect while it is enabled. A downstream assistant can still send retrieved text to its own model provider.

**Trial.** The unchanged server/socket modules were checked against their pinned Git blobs and run with a wholly synthetic in-memory meeting. Two same-user clients were refused with the gate off, both received the fake transcript with it on, and both were refused after it was switched off on their existing connections. Disabled requests made no store reads; actual socket mode was 0600. [Receipt](results/yogurt-mcp-02.json). The first attempt failed at sandbox socket-listen permission, before the protocol ran; a separately retained second attempt exercised it with permission to open the owned local socket. No microphone, real meeting, model or whole Electron application was used.

**People and recent work.** [A Linux user's report](https://news.ycombinator.com/item?id=50474482) says an initial bug was fixed in a subsequent release and the application then worked for them. That is a useful firsthand account, not our installation result or evidence that the current release has the old bug. The [maintainer's Electron explanation](https://news.ycombinator.com/item?id=50456480) emphasizes the React ecosystem. Recording-notice and speech-recognition questions occur in the launch discussion; they do not establish transcription accuracy or an all-platform privacy audit.

The recent [0.3.14 release](https://github.com/FrigadeHQ/yogurt/releases/tag/v0.3.14) includes a Linux Zoom Workplace call-name change; 0.3.15 was published after the inspected source pin. The captured latest-commit slice also includes agenda/date-search and UI work. Release and default-branch state must be rechecked before final copy; the component receipts remain tied to `ada44ea`.

**Take / gap.** Local ownership carries scheduling and model-management responsibilities that a hosted notes service normally absorbs. The inspected pipeline and tested queue make that trade concrete, while optional assistant retrieval adds a separate access decision. Try a short synthetic recording if the required environment is practical before making a note-quality recommendation. Keep complete-app network and real-machine resource claims open until tested.

## AssemblyForNeovim — compiler context in the editor

**State:** all 412 implementation lines inspected; actual plugin exercised in a clean headless editor. [Repository at `58a471e`](https://github.com/0xdeadf1sh/AssemblyForNeovim/tree/58a471ec97fb5987eca2b955fd2cba8693a414f6), Unlicense; [launch discussion](https://news.ycombinator.com/item?id=50453229).

**Job and called path.** The plugin brings optimized assembly into Neovim without moving the user to a separate compiler explorer. In [`lua/asm/init.lua`](https://github.com/0xdeadf1sh/AssemblyForNeovim/blob/58a471ec97fb5987eca2b955fd2cba8693a414f6/lua/asm/init.lua), `db_entry` finds compilation context, `cc_base` builds the base arguments, `build` adds assembly/debug flags, and `vim.system` invokes the compiler. `extract` uses debug line mappings to select the relevant assembly. Normal mode tries the enclosing Tree-sitter function, falling back to the current line; Rust has Cargo and standalone paths. This shows freshly generated assembly from the source file, rather than disassembling an already linked executable.

**Claim audit and trial.** A C function depended on a header under a directory containing a space. An `arguments` compilation-database entry preserved the include path and rendered `add w0, w0, #7`. An equivalent shell-quoted `command` entry failed: whitespace splitting broke the path into separate arguments. In a third case, the on-disk function still added 7 while the unsaved editor buffer added 99. The plugin warned that it was reading disk, but displayed the new source comment beside assembly adding 7. [Receipt](results/neovim-context-01.json). The warning is material; the result is not a claim that the plugin silently compiles the unsaved buffer.

The runtime was official Neovim 0.12.6 on macOS arm64 with Apple Clang 21.0.0, `--clean -u NONE -i NONE`; no editor configuration was installed or changed. The fixture compiled only to assembly. It did not run an executable, assess runtime speed or test the complete interactive UI. Initial Neovim log-path permission noise is retained in the raw record; future reproductions should set `NVIM_LOG_FILE` to their temporary directory.

**Recent change.** The pin includes the [November 12 C23/C2x fallback](https://github.com/0xdeadf1sh/AssemblyForNeovim/commit/820949a80763e82378dceaa4da640944380e9412), a concrete compiler-compatibility change. No GitHub release was returned in the checked release collection; the trial uses the source pin, not an invented package version.

**People and alternatives.** [A launch reply](https://news.ycombinator.com/item?id=50454067) points to nvim-dap-disasm for inspecting the actual compiled result in a debugger. [A cargo-show-asm contributor](https://news.ycombinator.com/item?id=50454596) discusses Rust edge cases. These are useful distinctions between workflows, not evidence that one tool has greater adoption.

**Take / gap.** A small plugin can make compiler feedback much easier to reach, provided it retains the build context and the source revision the user means to inspect. This paired test found two concrete cases to check in a real project. Next, inspect or exercise the Rust/Cargo path before making Rust-specific claims; do not turn the C fixture into a general compatibility verdict.

## bo2-mac — translating a game and rebuilding its environment

**State:** selected build/runtime/graphics paths inspected; no game build or gameplay trial. [Repository at `ea6f78e`](https://github.com/adrbn/bo2-mac/tree/ea6f78e0a41a374e5748635da99bafcc2d062d0b), GPL-3.0; [launch discussion](https://news.ycombinator.com/item?id=50449891).

**Job and distinction.** Run a Windows-era game on Apple Silicon through ahead-of-time binary translation. The project requires the user's own game files; this research neither acquired nor redistributed them. It is a combination of translation, replacement platform behavior and graphics adaptation, not a source port of the original game.

**Called path.** The [build script](https://github.com/adrbn/bo2-mac/blob/ea6f78e0a41a374e5748635da99bafcc2d062d0b/scripts/build_steam.sh) runs the lifting/compilation pipeline: Remill-derived LLVM IR, project-specific passes, ARM64 compilation and linking against the runtime. [`runtime/gfx/dxbc_to_msl.cpp`](https://github.com/adrbn/bo2-mac/blob/ea6f78e0a41a374e5748635da99bafcc2d062d0b/runtime/gfx/dxbc_to_msl.cpp) uses vendored HLSLcc to translate shader bytecode. The bridge remaps D3D resource registers using reflection and handles the mismatch between packed D3D constant-buffer offsets and Metal layout. Recompiling CPU instructions does not supply those graphics conventions by itself.

The [README](https://github.com/adrbn/bo2-mac/blob/ea6f78e0a41a374e5748635da99bafcc2d062d0b/README.md) and [`runtime/win32/interp.cpp`](https://github.com/adrbn/bo2-mac/blob/ea6f78e0a41a374e5748635da99bafcc2d062d0b/runtime/win32/interp.cpp) also describe/provide interpreter fallbacks for missed or protected code. The launch's absolute no-emulation wording is too broad for this inspected implementation. That qualification does not negate the ahead-of-time path; it describes the actual hybrid boundary.

**Reports and limits.** The [prerelease note](https://github.com/adrbn/bo2-mac/blob/ea6f78e0a41a374e5748635da99bafcc2d062d0b/docs/PRERELEASE.md) limits the demonstrated machine/session coverage and lists unsupported online/LAN/co-op use. Performance and campaign results are upstream reports. The [author describes](https://news.ycombinator.com/item?id=50451368) months of parallel development with repeated measurement and play, and [reports](https://news.ycombinator.com/item?id=50453299) substantial translated-binary growth. Neither is a locally reproduced benchmark.

**Recent direction.** [November 6's test build 4](https://github.com/adrbn/bo2-mac/releases/tag/v0.2.0-test.4) packages a no-Terminal app and describes signed same-developer updates, retained previous versions and selective reconversion when translation patches change. That is release-reported distribution/upgrade work, not a tested installer here. It suggests effort to make the translation usable by owned-copy players, beyond the initial technical demonstration; it does not establish adoption or general playability.

**Take / gap.** The instructive achievement is reconstructing enough of the old program's environment for translated code to be useful. A performance or playability recommendation needs a lawful owned-copy trial on declared hardware and a meaningful session. Until then, keep this entry a source-grounded architecture review and qualify the launch wording. Next source check: follow a concrete shader call through resource binding and the actual fallback caller, rather than treating the translator file alone as the entire rendering path.

## AgentRun — durable orchestration around existing harnesses

**State:** selected recovery/kernel/bridge and learning-admission source inspected; actual provider-free kernel/bridge interruption controls executed. No disk-store, real agent/provider, cost or learning-outcome trial. [Repository at `b98a6c0`](https://github.com/Parcha-ai/agentrun/tree/b98a6c025b9795ec452431114a18a66c6160ef7d), Apache-2.0; [launch discussion](https://news.ycombinator.com/item?id=50471650).

**Job and distinction.** AgentRun wraps existing agent harnesses with durable execution, control and reusable learned artifacts. It does not remove the harness/model provider or make their operational costs disappear. Its documented Node minimum is newer than the blog repository's pinned Node runtime; any execution needs an isolated compatible environment.

**Recovery path.** [`packages/run-adapters/src/process/recovery.ts`](https://github.com/Parcha-ai/agentrun/blob/b98a6c025b9795ec452431114a18a66c6160ef7d/packages/run-adapters/src/process/recovery.ts) constructs a resumed turn from durable records. It distinguishes completed, failed, interrupted, retryable and still-running calls. A lost result for a `never` replay call can mean the outside action already happened; the note tells the model to check actual state before repeating it. Durable progress is not proof of exactly-once effects in an external service. The file explicitly records its durable-harness ancestry and subsequent changes; do not describe every mechanism as invented here.

**Learning path.** [`learning.ts`](https://github.com/Parcha-ai/agentrun/blob/b98a6c025b9795ec452431114a18a66c6160ef7d/packages/serve/src/learning.ts) and [`runner/learning-loop.ts`](https://github.com/Parcha-ai/agentrun/blob/b98a6c025b9795ec452431114a18a66c6160ef7d/packages/serve/src/runner/learning-loop.ts) manage Git-pinned notes, skills and workflows. A run begins from a committed snapshot; proposals are graded, checked against a bounded byte budget and admitted or dropped. The inspected admission loop persists/flushed the grade before committing learning, checks whether the run was already merged, and records conflicts/failures. This is artifact selection and versioning, not model-weight training. Source inspection does not establish that grades improve later task outcomes.

**Trial.** Built the unchanged DSL and kernel/adapter packages with isolated Node 24.22.3, TypeScript 5.9.3 and pinned dependencies; installation scripts were disabled. The actual [`openDrive`/`effect`](https://github.com/Parcha-ai/agentrun/blob/b98a6c025b9795ec452431114a18a66c6160ef7d/packages/run-adapters/src/kernel/drive.ts) and [`toolBridge`](https://github.com/Parcha-ai/agentrun/blob/b98a6c025b9795ec452431114a18a66c6160ef7d/packages/run-adapters/src/process/tools.ts) ran an owned journal append, then were interrupted before the result was recorded. With `never`, reopening the retained memory store recorded an interrupted failure and the same call key did not append again. With `safe`, reopening released the intent to retry and the callback appended a second time. A completed `never` control reused its recorded result with one append total. [Three-case receipt](results/agentrun-recovery-01.json). The `safe` append deliberately lacks deduplication: the doubled file is the negative control showing that the framework relies on the tool's declared replay policy. It does not automatically make an operation safe to repeat.

Separately, the three upstream faux-adapter recovery tests passed: unanswered requests do not invent tool calls, a parked answered call runs after recovery, and a two-call response retains its ordering/text boundaries. Those synthetic adapter tests are separate from the three authored kernel cases. The retained store was upstream `memorySessionStore`; no process was killed and no disk-store or actual CLI/model recovery was tested. Reading the journal independently verifies this side effect, not production persistence.

**People and contrary questions.** [A user asks](https://news.ycombinator.com/item?id=50492989) when learned material applies, how deterministic it is and whether its costs accumulate. [Another asks](https://news.ycombinator.com/item?id=50477365) how detached process growth is bounded. These are unresolved operating questions, not measured defects. Upstream savings and self-improvement stories remain attributed, with no matched local cost comparison.

**Recent release and adoption cost.** [Beta.37](https://github.com/Parcha-ai/agentrun/releases/tag/v0.1.0-beta.37), published November 14 before this source pin, calls the learning loop unfinished and says the compile/guard/promote stack is absent from that release. It also requires a fresh SQLite store when upgrading from beta.36; Postgres migrations are a different path. These are consequential release-reported limits, not an upgrade this research executed. Computer takeover/provider integrations are active work, but the durable-kernel trial does not verify them. Do not turn the top-level self-improvement claim into a shipped universal outcome.

**Take / gap.** Recovery and learning are valuable to examine as explicit state transitions rather than broad agent promises. The interrupted-effect distinction survived a real component trial, and the policy label carries a concrete responsibility. Next bounded action: inspect the production journal/session-store flush/fence path and choose a provider-free disk-backed interruption trial if making a production durability claim. A matched task comparison would be separately required for learning or cost benefits.

## ZigZag — artwork to embroidery, with hardware still downstream

**State:** core CLI built and exercised; selected import/document/check/format code inspected. [Repository at `ad19cb0`](https://github.com/simpsoka/zigzag/tree/ad19cb09dcf5649fac55b43a083714bcd2b761d4), Apache-2.0, CLI 0.1.3; [launch discussion](https://news.ycombinator.com/item?id=50470488).

**Job and called path.** ZigZag offers an editable route from vector artwork to stitches and common machine files, with optional GUI and device-specific Bluetooth work. The CLI's [`convert` path](https://github.com/simpsoka/zigzag/blob/ad19cb09dcf5649fac55b43a083714bcd2b761d4/src/main.rs) opens a [`Document`](https://github.com/simpsoka/zigzag/blob/ad19cb09dcf5649fac55b43a083714bcd2b761d4/src/document/mod.rs), applies settings, produces a stitch design and calls the selected format writers. [`checks.rs`](https://github.com/simpsoka/zigzag/blob/ad19cb09dcf5649fac55b43a083714bcd2b761d4/src/checks.rs) evaluates machine/design constraints. **Trial and consequence.** The core CLI was built with Rust 1.96.1, locked dependencies, GUI/Bluetooth disabled and a temporary build directory. ## DeepSeek V3 in JAX — architecture that can be inspected

**State:** the complete 265-line model implementation inspected and tiny CPU mechanism controls executed. [Repository at `6901be6`](https://github.com/Vaibhaav-Tiwari/deepseek-v3-jax/tree/6901be60941b98dc654ed542465290db9e8bafa6), MIT; [launch discussion](https://news.ycombinator.com/item?id=50497589).

**Job and distinction.** An educational implementation makes multi-head latent attention, routing and balancing small enough to read. The README's miniature training result is a maintainer report, not a reproduction of the full DeepSeek-V3 model, its training corpus or quality. The value here can be understanding a mechanism even when the code is not an efficient production implementation.

**Called path.** In [`deepseek_v3.py`](https://github.com/Vaibhaav-Tiwari/deepseek-v3-jax/blob/6901be60941b98dc654ed542465290db9e8bafa6/deepseek_v3.py), the router adds its balancing bias for top-k selection but weights the selected experts with the original sigmoid affinities. Latent attention retains compressed content and shared rotary keys in its cache. The mixture-of-experts implementation computes every routed expert's intermediate tensors, then gates the output: selecting a sparse result is not the same as computing only selected experts. The source explicitly favors simplicity there.

**Trial.** With four authored affinities, a bias changed the selected pair from experts 0/1 to 2/3 while preserving raw-affinity weighting. A six-token attention calculation matched a three-token prefill followed by three incremental steps within a declared float32 tolerance of 1e-5; maximum absolute difference was 2.91e-10. In this tiny configuration, the cache used 12 scalars per token versus 40 for uncompressed head keys/values. Traced contractions included all four experts, although two were selected. [Shapes, versions and results](results/jax-mechanisms-01.json).

The isolated Python 3.12 CPU environment used JAX/jaxlib 0.4.34, Optax 0.2.5 and NumPy 2.5.4. No model checkpoint, training data, training run, provider or throughput comparison was used. The project's stated 39-test result was not rerun and is not a local acceptance count.

The [November 14 v1.0 release](https://github.com/Vaibhaav-Tiwari/deepseek-v3-jax/releases/tag/v1.0) supplies the author's checkpoint, data, tokenizer and logs for a more exact reproduction. Those artifacts were not downloaded or loaded. The repository's initial model commit is November 13 and the license was added at the inspected pin; HN attention still says nothing about independent training reproduction.

**Primary architecture comparison.** [DeepSeek's technical report, §§2.1.1–2.1.2](https://arxiv.org/html/2412.19437v2#S2.SS1), separately describes the compressed content/shared rotary-key cache, bias used for selection while gate values retain original affinities, and a small complementary sequence-wise auxiliary loss. The inspected educational code includes those distinctions. The report also describes distributed node-limited routing and training infrastructure beyond this small implementation. Checking these mechanisms is not establishing full model equivalence or reproducing the report's training results.

**People / take / gap.** [The maintainer](https://news.ycombinator.com/item?id=50497618) frames it as architecture learning and a small training exercise. [A reader](https://news.ycombinator.com/item?id=50499974) appreciates that purpose while raising the problem of comparing miniature runs on different datasets. The code and controls make two easy-to-confuse distinctions visible: routing bias versus output weight, and sparse selection versus sparse computation. The next useful work is a reader-facing worked explanation of those distinctions, with the educational simplifications kept explicit. No training-quality advice follows from these controls.

**Claim audit and contrary result.** The release says a font buffer can now be registered again with a different name/weight/style/range, where the earlier descriptors could be reused. The [regression test](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-napi/tests/register-font-again.test.ts) uses an ArrayBuffer and a view sharing it. We tested published native `@takumi-rs/core` 2.19.0 and 2.20.0 with the pinned Geist variable WOFF2, registering Alpha and Beta and rendering `Again` with both.

The first condition supplied separately copied byte arrays; the second supplied an ArrayBuffer plus its view. **Both versions passed both conditions**, returned the requested family names and produced identical 809-byte PNGs. [Copied-byte receipt](results/takumi-font-alias-01.json); [shared-buffer receipt](results/takumi-font-alias-shared-01.json). Those results did not establish the advertised change and remain retained.

Further reading of the [November 1 fix](https://github.com/kane50613/takumi/commit/4fd9276e43b0130abab25da788625a2b3bd19aa2) and the actual published facade explains a narrower condition. The old JavaScript registry used buffer/view object identity as its cache key; an ArrayBuffer and a view of it are two objects. [`FontRegistry`](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-bindings-js/src/renderer.ts) now includes face descriptors in that generated key. A third control was declared from that source hypothesis and passed the **exact same Uint8Array object** for Alpha and Beta. On 2.19.0 the Beta request returned `Alpha`; on 2.20.0 it returned `Beta`. [Same-object receipt](results/takumi-font-alias-same-object-01.json). This reproduces that registration-identity contrast through the published native facade.

PNG bytes were identical even in the old failing registration case. Image equality alone would have missed the absent requested family in this fixture; the returned registration is the decisive observation. The font Git blob, SHA-256, package integrity and output hashes are recorded. No general font-conformance, other-descriptor or WASM result follows from this case.

**Resource preparation trial.** The afternoon continuation followed [`takumi-napi/src/export.ts`](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-napi/src/export.ts) through the complete released [`prepared.ts`](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-bindings-js/src/prepared.ts), image helper and selected upstream tests. Actual native 2.20.0 preparation made one loopback request for a CSS background image and none for a CSS-hidden image. PNG/SVG/measurement from the prepared object did not refetch. Its PNG equaled direct rendering with explicitly supplied bytes and differed from the raw no-bytes control; its SVG embedded image data. Supplied-byte preparation avoided transport, and a denied URL rejected before transport. [Receipt](results/takumi-prepared-resources-01.json), [fixture](repro/takumi-prepared-resources.mjs). The owned server was closed.

This API distinction matters: raw native `render` calls `readSource` without fetching; native `prepare` calls the collecting/fetching path. The high-level `takumi-js` path calls preparation itself. `Prepared` holds source/layout options/resources here; these controls do not establish a precomputed-layout cache or a speed benefit. They cover one HTML/CSS resource case across native PNG/SVG/measurement, not PDF/paint/WASM or complete fetch-policy security.

[Receipt](results/takumi-font-shadow-01.json), [fixture](repro/takumi-font-shadow.mjs). The same-name and alias Cyrillic PNGs and removed-fallback ASCII PNG were visually inspected. The checked [`default_fonts`/embedded registration](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-bindings-common/src/lib.rs), [`font_data_for_family`](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-core/src/fonts/css_font_selector.rs), [bucket ranking](https://github.com/kane50613/takumi/blob/ae2a35011e5cddedb0a4c8b33ab0c9242ca76b2d/takumi-core/src/fonts/font_face_cache.rs) and fallback bucket path support the report's explanation: the built-in and supplied faces share a family lookup, with capability-bucket selection preceding character fallback.
