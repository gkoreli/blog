## Authoritative compiler instructions used

All links use the tested compiler source rather than current mutable docs:

- [AOT](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/aot.mdx): native compilation and type checking differ from usual runtime execution.
- [Compatibility](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/compatibility.mdx): runtime-discovered files need entry points or disk loading; disk-loaded JS is interpreted; the build must see mutable built-in assignments.
- [Executables](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/executables.mdx): `--asset` embeds required files; AOT preserves module-relative paths. This informs the separate Keryx packaging variant.
- [Libraries/frameworks](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/libraries.mdx): the official Next standalone recipe passes server chunks and assets explicitly. That is a different build path from this adapter's extraction-based launcher; do not claim our adapter experiment certifies the official recipe.
- [Troubleshooting](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/troubleshooting.mdx): disk-loaded code and generated code are separate reasons for slower execution; compatibility failures need the actual runtime path.

## Claims being tested

| Claim / rival | Evidence state | Required result / limit |
| --- | --- | --- |
| Keryx works unchanged as a standalone AOT executable | Contradicted by reproduced missing-resource failures; ordinary packaged JIT failed too | Preserve that shared packaging problem, then measure a named corrected variant against the real source-run app. |
| Every Zod-backed app inherits our synchronous-validator slowdown | Contradicted as a code-path inference | Keryx uses async parsing. The real route and full output checks passed; the measured cells are in the summary, without a universal async speed claim. |
| Adding `--aot` to this Next adapter is sufficient | Contradicted: static page 200, real sharp route 500 | Check all selected outputs, retain the documented disk-loading and explicit console-compatibility variants. |
| The working Next compatibility variant is a fully native-compiled Next application | Contradicted by inspected extraction/loading path and compiler docs | Label it AOT launcher with interpreted disk-loaded Next JS; native sharp still executes native addon code. |
| Smaller binary means the whole deployment is equally small | Not established | Report extracted regular-file bytes alongside executable bytes, without summing them into unique physical RAM. |
| These experiments establish an independent maintainer's adoption | Not established | Our own controlled experiments can inform the article; author use/endorsement requires separate evidence. |

All retained numerical batches passed the offline audit: 118 fresh startup/load/control processes, 172 timed windows, 56,076,491 checked responses, plus 24 separate first-dynamic launches. [Summary](results/summary.json) and [audit script](verify.py). Varsafe currently exposes a public binary-release distribution route, not a verified public CLI source checkout or matched JIT/AOT builds. No guessed binary-mode comparison is acceptable.

## Session storage and runtime build tools

The first client sent no Cookie header. Keryx's [web server](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/servers/web.ts) creates a UUID without one; [Connection.loadSession](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/classes/Connection.ts) creates a session when none exists; [session.ts](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/initializers/session.ts) persists it for the configured default day. The [memory Redis mode](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/initializers/redis.ts) puts that storage in the app process. The internal source-run diagnostic counted 20 new keys after 20 no-cookie requests, then one additional key for the cookie and no further keys after twenty returning requests. This is retained state with a declared TTL, not proof of a memory leak. Returning-cookie and real-Redis comparisons remain separate batches.

The native MCP start failure follows [spawnBunBuild](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/util/bunBuild.ts): it invokes `process.execPath` with build arguments. The [pinned Bun docs](https://github.com/oven-sh/bun/blob/3f3a9ff87cdccf3d32d7ec6b648c664eddaae840/docs/compiler/executables.mdx#act-as-the-bun-cli) explicitly say native `bun compile` executables do not include the Bun CLI. The working HTTP variant therefore does not establish MCP compatibility. [mcpAppBundler](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/util/mcpAppBundler.ts) already supports prebuilt HTML without a browser client entry; the separately labeled build-time UI variant passed the public protocol/health checks without implying the original app already did it.

## The uncancelled action deadline

The final source trace found a separate retained resource in [`Connection.executeWithTimeout`](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/classes/Connection.ts): `setTimeout` captures the timeout error/controller, `Promise.race` can finish first, and finally restores the prior signal without cancelling the timer. The [default action deadline](https://github.com/actionhero/keryx/blob/d119595bec716ae99b4eca740964343e47f57eee/packages/keryx/config/actions.ts) is 300,000 ms. This is a more specific explanation than assigning the entire rising footprint to Redis sessions or claiming a garbage-collector fault.

The source-run diagnostic instruments actual timer scheduling while calling the real registered action over HTTP. Twenty successful calls leave twenty default-deadline timers originally and zero with [the cleanup patch](timer-cleanup.patch). Fast success, a genuinely slow action with abort observed, and a thrown error retain their expected HTTP 200/408/500 behavior. The patch stores the timer handle and clears it in finally; the deadline stays enabled. The balanced four-cell comparison reproduced the memory reduction: source JIT 842.9 → 143.5 MB and native 525.0 → 47.6 MB; four fresh processes per cell, same services, cookie and selected handler. The original minute series continued growing with stable Redis key counts; the separate two fixed minute checks stayed at 129.2–130.4 MB / 46.9–49.2 MB at ten-second checkpoints. This supports a causal contribution from the uncancelled action timers in this workload, not a universal leak or production capacity verdict. See the complete [summary](results/summary.json); no earlier or slower observation was discarded.

The native MCP build-time remedy separately passed with the whole study source tree temporarily hidden, an empty working directory and no Bun on PATH. Initialize, tool listing and the public status tool's DB/Redis health fields passed; no child build process existed. Anonymous resource listing was empty under the existing auth policy. This does not establish authenticated UI access or browser rendering. The original failure remains retained.
