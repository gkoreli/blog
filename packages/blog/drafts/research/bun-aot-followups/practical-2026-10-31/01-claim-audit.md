# Claim audit: use the saved RAM, measure the CPU

The preceding article's original results remain historical. These questions extend the same Bun project deep dive; they do not compare languages or certify production density. [Plan](00-plan.md) · [methods](README.md).

| Claim / rival explanation | Evidence | Current state | Reader decision | Limit |
| --- | --- | --- | --- | --- |
| Lower per-process app memory can leave room for another useful copy | Complete matrices plus the matched four-client/twelve-DB-connection control | Two native copies served 52% more requests with 11% less end app memory than one JIT copy in the matched short batch | Compare actual pools, rather than multiplying a one-process screenshot | No enforced memory cap; sum of process physical footprints is not uniquely occupied machine RAM |
| The gain is solely from allowing more DB connections | Separate JIT/native overlay with twelve configured connections across every cell; actual counts all twelve in the short control | Contradicted as the sole explanation in this fixture | Hold the external service budget steady when testing more processes | Does not isolate every scheduler, client, CPU or driver mechanism |
| More native copies provide the gain without a CPU cost | App and PostgreSQL CPU next to each request/memory observation | Contradicted in the completed main and short control | Spare RAM and spare CPU are different constraints | CPU seconds on heterogeneous laptop cores do not translate directly to cloud prices |
| Splitting the local client could create a misleading pool result | Final matrix holds four request clients, 32 HTTP connections and twelve DB connections steady | Copy-count benefit persists; the unrun one-app diagnostic was superseded before measurement | Test the load generator as part of the apparatus | Same-host closed-loop clients do not establish unlimited external capacity |
| Short-window memory remains low after minutes of allocation | Four five-minute pools, retaining every minute, JIT/native/native/JIT order | Two native copies ended at 48–49 MB; one JIT copy at 56–61 MB, with sampled and lifetime peaks retained separately | Inspect longer allocation/GC behavior before a memory-packing claim | Client reconnects between minutes; not a production or uninterrupted-connection soak |
| First observed executable launch and routine restarts are interchangeable | Earlier tiny-server observation, reproduced in final four-mode tool data with the two phases separated | Contradicted in this Mac example | Retain first checked launch separately from repeated fresh-process startup | One first observation per new file; cause not isolated, prebuilt files may already have run |
| A local comparison tool can expose compiler/runtime/output failures before recommending a mode | Seven integration gates, twelve four-mode example starts, eighteen real-API starts and 36 timed API windows | Final source reproduced on macOS; source ZIP verified against all eight release files | Compare complete expected responses, speed, RAM, CPU and file size on the reader's own case | Experimental Linux branch; single-process fixed-body HTTP only; selected cases are not full app certification |

Do not turn “more requests on this cached route with spare CPU” into “half the server bill,” “double the capacity,” a Linux result, an independently operated rerun or TypeScript/Rust equivalence. Informal delivery can lead with the useful result while keeping the conditions that change its meaning. No new outreach is a prerequisite for publishing the useful artifact.
