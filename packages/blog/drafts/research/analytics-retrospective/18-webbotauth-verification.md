## Public demonstration-key policy — October 27 UTC

[WG draft §6.8](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol-00#section-6.8) says test keys must not be deployed and recommends rejecting known examples. [RFC 9421 B.1.4](https://www.rfc-editor.org/rfc/rfc9421.html#appendix-B.1.4) and [RFC 8037 A.1](https://www.rfc-editor.org/rfc/rfc8037.html#appendix-A.1) publish two Ed25519 signing values alongside their public keys. Anyone can sign with those values. Correct signature mathematics therefore cannot establish exclusive control of those example keys.

The [pinned Cloudflare reference](https://github.com/cloudflare/web-bot-auth/blob/e4d3167886d0e7508d55fc5c501f1e498a3d4f5c/packages/web-bot-auth/src/index.ts) separates its resolver, signature checks and application `validate` hook. We re-read that exact source from the private capture and matched its SHA-256 against the [saved manifest](webbotauth-reference-sources.json). That separation is the useful borrowed idea: preserve mathematical validity independently from local acceptance. This inspection does not establish the provider's deployed demonstration-key policy or full repository behavior. A fresh raw-source web fetch failed; the hash-matched saved primary source supplied this comparison.

The [independent probe](probe-known-test-keys.mjs) assembles short-lived signatures covering authority, method, path and signer without our message-base builder. Native WebCrypto confirms their mathematical validity before the application verifier runs. Both published examples are exercised in normal and padded public-key encodings, alongside an ephemeral positive control. Directory responses are intercepted in process: **zero network/production calls**, no real vendor directory or impersonation.

The [before result](known-test-keys-before.json) accepts all five. The [after result](known-test-keys-after.json) still finds all five cryptographically valid, but rejects the four example-key cases as `known-test-key` / `policy-rejected`; the ephemeral positive remains verified. Canonical example thumbprints stop before lookup. Padded encodings require one intercepted lookup to identify the same decoded key bytes and never populate the imported-key cache.

**Why thumbprints alone were insufficient:** our compatibility path accepted padded `x` encodings. A JWK thumbprint hashes the encoded value, so a different spelling gives a different thumbprint while native crypto imports the same physical key. [`known-test-keys.ts`](../../../../analytics/src/known-test-keys.ts) therefore checks both the two reviewed thumbprints and normalized decoded public-key material. This rejects the observed alias without claiming that padded encodings are recommended JWK output or that all other malformed encodings are supported. Imported entries carry the key-policy revision; entries not reviewed under it are re-resolved rather than trusted.

This is a deliberately bounded two-key registry, not a complete detector of all demonstration, weak or compromised keys. No production bypass option is added. Existing published-vector tests now check the valid signature math and the separate policy rejection; cache-isolation fixtures use ephemeral keys. Verifier profile advances to `2026-10-27.6`; collection/classifier profiles, schema and historical rows remain unchanged. Routine evidence stores only the closed rejection reason/profile, with no coverage or authenticated signer; it does not retain keys or signing values.

[Native local workerd/D1 acceptance](known-test-keys-local.json), through the [maintained helper](../../../scripts/check-known-test-keys.mjs), runs five actual collector fixtures in a response wrapper: canonical rejection, padded-alias rejection, rejected Exa declaration, genuine ephemeral signature and referral-excluded rejection. Rejected controls use dummy bytes because policy acts before verification; independently signed examples are in the separate probe. The genuine method/path-bound signature verifies in workerd. A claimed Exa origin/UA remains `not-verified` with no authenticated signer. Aggregates count three included policy rejections and one verified result, preserve one historical null and exclude the extra control. The single directory lookup is intercepted. The [indexed bounded acceptance SELECT](known-test-key-control-acceptance.sql) is accepted locally with both owner flags. This is not production blog routing, native Cloudflare authentication or organic vendor acceptance.

The [same retained Exa corpus](known-test-keys-exa-regression.json) also re-verifies all nineteen records under profile `.6`, with eighteen distinct provider IDs and unchanged coverage/native-availability limits. Input and later-directory hashes match the original capture. This is a zero-network regression at recorded times, not fresh vendor traffic or proof of receipt-time keys.

[Scoped source checks](known-test-keys-source-checks.json) pass 141 analytics tests, 106 site tests, workspace types, post validation and a 32-post isolated production build. The retrospective is 1,248 words and retains its original shaping messages. Delivery, activation, served prose and an excluded actual-Worker rejection must be accepted separately. Broader standards vectors/algorithms/discovery, DNS/egress/rebinding controls, expiry-only replay, organic signed/native comparison and independently labelled human/device trials remain open. The dedicated article outline can now teach the difference between valid signature math and a key suitable for attribution, alongside covered-field and discovery boundaries.

## Directory URL admission follow-up — October 27 UTC

The existing verifier and published RFC/draft vector tests already covered the requested capability. The remaining discovery gap was narrower: valid-looking signatures could cause a directory lookup at an HTTPS IP literal or local hostname. [WG draft §6.7](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol-00#section-6.7) explicitly warns about client-controlled discovery targeting internal services. [OWASP's SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html#case-2-application-can-send-requests-to-any-external-ip-address-or-domain-name) distinguishes URL validation from address/egress enforcement. Earlier fetch/body/cache bounds did not close that gap.

The [independent signed probe](probe-signature-discovery.mjs) makes **zero network or production calls**: ephemeral keys sign manually assembled bases, and an in-process fake directory intercepts every lookup. The [before result](signature-discovery-before.json) accepts all sixteen controls, including fifteen targets now outside local policy. This proves URL admission and lookup behavior under injected key discovery; it is not an actual connection to private infrastructure, vendor impersonation or evidence of exploitation.

The new dedicated [`directory-discovery.ts`](../../../../analytics/src/directory-discovery.ts) accepts DNS origins on default-port HTTPS and rejects all IPv4/IPv6 literals, nondefault ports, single-label hosts, malformed DNS labels and `localhost`, `.local`, `.internal`, `.home.arpa` names/subdomains. URL parsing precedes checks, so integer, hex, octal and shortened IPv4 aliases cannot evade literal rejection; terminal-dot local names also reject. Rejecting public IP literals and alternate HTTPS ports is a deliberately stricter **local profile**, not an RFC prohibition. Documented Exa, Ahrefs and DuckDuckGo origins remain admitted; admission alone does not authenticate them. Existing origin-only, credential/path/query/fragment rejection remains distinct.

The [after result](signature-discovery-after.json) accepts the DNS positive control and rejects fifteen disallowed targets with **zero lookups for those targets**. Both quoted-string and dictionary forms check policy before directory/imported-key caches. The closed reason `discovery-policy-rejected` maps to `policy-rejected`, not `invalid` or a malicious-bot verdict. Failed discovery supplies no authenticated origin or coverage. Verifier profile becomes `2026-10-27.5`; schema, collection/classifier profiles and historical records stay unchanged.

[Native local acceptance](signature-discovery-local.json) bundles the actual collector into workerd with native D1/crypto and a fixture HTTP response wrapper. Five unsigned/rejected/excluded controls preserve closed reasons, policy-rejected aggregates, null historical evidence and optional raw-capture absence. Directory fetches are intercepted and remain zero. The [bounded production acceptance SELECT](signature-discovery-control-acceptance.sql) is accepted in local D1 and uses the existing owner/path/time index with both owner flags. The fixture does not execute production blog routing or a native Cloudflare bot verdict. Source delivery, deployment and an excluded actual-Worker rejection must be recorded separately.

[Scoped source checks](signature-discovery-source-checks.json) pass 137 analytics tests, 106 site tests, workspace types, post validation and a 32-post isolated production build. Local runtime/builder permission failures and their successful bounded reruns remain recorded. Production acceptance is separate.

**Remaining boundary:** permitted DNS names can still resolve to private addresses or change resolution; a hostname check is not DNS rebinding protection. No connection pinning, resolved-address policy, global fetch budget or network egress enforcement is claimed. These require a separate design against actual Workers capabilities. Replay remains expiry-only; broad conformance, known demonstration-key rejection, directory proof/redistribution modes and organic signed/native comparison remain open. The existing dedicated-article outline below is still a proposal, now supported by another reproducible failure/repair.

## Answer and actual evidence

A dedicated local verifier already existed at [`webbotauth.ts`](../../../../analytics/src/webbotauth.ts), called by the collector before classification. It reconstructs the signed message and verifies Ed25519 with discovered public keys. It does not depend on Cloudflare supplying a verdict. The gap was preserving what verification covered, its operating policy and native availability.

The [retained Exa sample](exa-native-verification.json) contains 19 native log records for October 26 UTC. All 19 verify with the revised verifier at their recorded timestamps against a separately captured, later Exa directory. All declare ExaSearchBot and use the quoted-string header form. Their signatures cover authority and Signature-Agent, but none covers User-Agent, method, path, query or target URI. Each has a 300-second validity window and arrived 0–3 seconds after creation.

These are **19 records, not 19 proven unique events**: two nonidentical records share one provider ID, leaving 18 distinct IDs. We preserve the collision. The export lacks both native verification booleans, although a native category is present. Missing booleans do not establish a negative verdict. No exact D1 join or complete sampling/retention coverage is claimed.

The later key capture proves this key set validates these retained messages at their original times; it does not prove the directory's contents at receipt, current-time freshness, all Exa traffic being signed, a human trigger or a citation. The [maintained reproducer](reverify-exa-capture.mjs) makes zero network/page requests and emits only an aggregate receipt. Raw messages, addresses, URLs, signatures and nonces remain in a restricted private archive with an October 31 retention review.

Directly fetched HTTPS directories and redistributed key sets have different trust conditions in the WG draft. We fetch the former; we do not ingest third-party key registries or claim directory-response proof validation. Merely hosting a key authenticates an origin/key relationship, not a company's reputation, task, authorization or human principal. The existing reviewed signer catalogue controls public naming; it is not an authorization list.

## Changes prepared in this iteration

- Keep successful signature coverage, wire form, validity/age and explicit `expiry-only` replay policy. Production caps signature lifetime/age at 24 hours with the existing 60-second skew allowance; this is a versioned local policy, not proof of replay prevention.
- Respect directory max-age and Age, cap cache lifetime, avoid reuse under no-store/no-cache, expire imported keys with the directory/key, enforce key activation/expiry, refresh an unknown key once per origin/30 seconds, and invalidate removed imported keys on refresh. No complete HTTP-cache implementation is claimed.
- Require the protocol media type, HTTP 200 and no redirect; bound bodies to 64 KiB, keys to 128, cache maps to 256 and pending distinct-directory fetches to 64. The collector's existing two-second deadline aborts fetch work. These limits are per isolate, not a global abuse budget or full SSRF defense.
- Add nullable `signature_evidence` through migration 0012. Keep raw signature/key/nonce/header values out of this new field. Record local failure reasons, profile and independent native booleans; test-injected verdicts are labelled and cannot claim cryptographic coverage.
- Add a public coverage/availability summary using the same selected population, exclusions and single SQL report statement. Counts overlap. Historical absence remains unknown; no backfill or reclassification. Cache/report version changes with these semantics.
- Disclose routine derived facts on /privacy. The optional raw diagnostic profile remains off. Linked observations remain potentially personal; this change does not settle the existing collection-basis, retention or rights questions.

The [decision](../../../../../docs/adr/0016.11-signature-verification-evidence.md) and source files define the implementation. Collection/verifier profiles advance to `2026-10-27.1`; classifier remains `2026-10-26.3`.
