# Analytics improvement plan — October 25, 2026 Pacific

This is a proposed engineering sequence derived from [today's audit](../edge-vs-rum/05-analytics-audit-2026-10-25.md), [Wrangler follow-up](03-wrangler-followup.md), [native capabilities](01-native-capabilities.md), and [standards/library review](02-standards-and-libraries.md). No row rewrite, new reporting policy, authentication service or instrumentation below has been implemented by this writing request. Existing accepted releases stay accepted; existing tasks retain their scope.

## Decisions the plan must improve

Can we distinguish our own tests from external recorded access? Can we explain which service/declared role fetched a page, with what verification? Does a new source warrant a reporting exclusion or distribution decision? Which stage explains an edge/beacon disagreement? The aim is useful publishing decisions under [ADR-0016.1](../../../../../docs/adr/0016.1-analytics-purpose-and-decision-loop.md), not identifying private people or building a general analytics product.

“Deterministic” must name its object. A SQL selection can deterministically count stored rows. Signature validation can check particular bytes against a key under stated trust and freshness conditions. Neither yields a universal actor, human identity, purpose or readership oracle for anonymous public HTTP.

## Candidate evidence model

| Axis | Example value | Evidence to retain prospectively |
|---|---|---|
| Recorded event | Eligible HTML destination response | Representation, collection version, UTC time and selected path |
| Declared client | ExaUser | Versioned UA rule result; no implicit vendor verification |
| Local key verification | Covered bytes accepted under the selected directory key | Verifier/profile version, bounded result/reason, key/directory reference and coverage/freshness assessment |
| Vendor recognition | Exa | Association with an archived primary documented identifier, separate from arbitrary directory ownership |
| Native assessment | Verified/category or unavailable | Source, actual availability, version/date and bounded returned value |
| Documented role | On-demand retrieval | Role source/version and whether the relevant assertion was signature-covered or only declared |
| Trigger / authorization | Unknown; labelled trial; validated scoped action | Exact basis and scope; no inferred human intent |
| Reporting decision | Included, R1 unresolved | Policy/report version, reason, exclusions, calculation time and retained capture |

These are semantic design candidates, not final column names or permission to collect everything. Select only fields that support a named decision. Keep request IDs for a bounded diagnostic join only if needed; define scope, retention/deletion and public projection before collection. Never call IP/UA HMAC IDs anonymous people or publish a precise private journey.

## First implementation boundary

The first implementation should close owner/test exclusion acceptance and deliver the model/catalogue correction in TASK-0119. It should not simultaneously replace the verifier, add an auth system, activate a new R1 exclusion and introduce new collection infrastructure. Those changes have different acceptance evidence and rollback behavior. This plan schedules no background work or automatic capture.
