# A stored “listed” flag needs supporting checks

October 27 Pacific / October 28 UTC. Continues [report-cost visibility](55-report-calculation-cost.md). Human trials remain deferred.

**The network report trusted its summary flags without checking their basis.** Native synthetic records reproduce “listed” claims with an empty checks array, an unknown method profile, contradictory counts or JSON number `1` where a boolean belongs. This is a report-consistency defect, not measured production inflation or a change to vendor attribution policy.

## Follow the claim back to the stored method

[SQLite documents](https://www.sqlite.org/json1.html#jex) that single-path `json_extract()` turns JSON true into SQL integer one. Comparing its output with `1` therefore cannot distinguish the boolean from a number. The repair uses JSON types and a closed [stored assessment](../../../../analytics/src/vendor-network-summary.ts) before projecting any outcome.

Recognized profiles retain their original source scope: `.27.1` has the original eight feeds; `.28.1` additionally permits DuckDuckBot and Google-Agent. Checks must have distinct recognized sources, coherent declaration counts, typed summary booleans matching their outcomes, and compatible address/reason/snapshot fields. Successful checks need a structured snapshot with a digest, bounded prefix count and coherent recorded times. Missing, malformed and future profiles cannot inherit today's method catalogue. Ahrefs' two declarations sharing one feed remain valid; so do overlapping results from different feeds.

The assessment checks the fields supporting public claims. It is not a complete JSON canonicalization validator or a repeat of the historical IP comparison: the raw address and ranges are not in this record. A plausible, internally consistent stored object cannot independently prove that its comparison occurred. Freshness dates describe the recorded snapshot, not a currently fresh feed.

[Google's verification guide](https://developers.google.com/crawling/docs/crawlers-fetchers/verify-google-requests) documents matching an accessing address against the appropriate published ranges. A declared client name alone does not perform that comparison. [Cloudflare's address-header reference](https://developers.cloudflare.com/fundamentals/reference/http-headers/#cf-connecting-ip) explains Worker subrequest and pseudo-IPv4 distinctions; the collector's existing relay/address abstentions remain unchanged. Neither a source-range match nor a coherent stored record establishes a person, trigger or readership.

## Preserve the unknown denominator

Record presence, recognized assessments and unrecognized/inconsistent records now have separate counts. Only recognized assessments contribute to configured/unmapped declarations or outcome counts. No observation is deleted or reclassified. Server and browser reject incomplete or impossible summary totals; overlapping outcomes are bounded without summing them as an exclusive partition.

The dashboard explains the historical scope and displays inconsistent records separately. Report/cache version becomes `2026-10-28.6` because public summary semantics change. Collector, classifier, verifier, IP-method profile, schema and optional capture settings do not change.
