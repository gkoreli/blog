## A separate, guarded instrument

[`native-bot-capture.ts`](../../../../analytics/src/native-bot-capture.ts) handles a dedicated JSON namespace before assets or the page collector. It is off without a valid optional configuration. Activation requires an allowlisted HTTPS origin, registered control, at most fifteen minutes and the existing current-day owner-profile mark. The shared owner lookup is extracted without changing calibration's predicate. Unknown paths, queries, methods and cross-origin requests are rejected; guard failure/timeout produces a closed unavailable response. Expiry, clock reversal and UTC-day changes are checked again after the asynchronous lookup.

Accepted responses retain only candidate shape (`missing`, `literal-true`, `literal-false`, `other`) and independent typed native-field states (`true`, `false`, `unavailable`, `unrecognized`). Each response has an exact private response/control reference and an identical structured log event. Raw header values, IPs and User-Agent do not enter this payload. All candidate values remain **untrusted header observations**: none enters classifications, native verification facts, authorization or public counts. The planned condition is labelled as planned, not authenticated by the request.

The route performs an owner SELECT, never an observation or diagnostic write. Its 32-control configuration limit is **not** a globally enforced request budget; repeat requests can occur. The controller must enforce the proposed executed-request bound. Guard reads and provider logs are additional service work. No new schema, persistent admission counter, credential or capture activation is introduced.

## Local acceptance and the fixture trap

[The maintained harness](../../../scripts/check-native-bot-capture.mjs) executes the actual composed blog Worker in local workerd with native D1. [Twenty HTTP controls](native-capture-local.json) produce seven captures and thirteen rejections/unavailable results. The historical sentinel count stays one; raw diagnostic and calibration tables stay empty. No asset binding is needed. Config-off/expired/future/malformed, mark removal, database failure, wrong-origin/method/query/path and supplied candidate values are covered. Combined strings in this harness are single header values; they do not establish wire-duplicate handling by Cloudflare.

Two early harness assumptions failed. The synthetic sentinel first violated the existing 32-hex daily-ID constraint; that fixture was corrected. Then the first capture returned native `verifiedBot=false` where the harness expected unavailable. **Miniflare can populate provider-shaped metadata without the provider making a verdict on this request.**

The installed Miniflare **4.20260301.1** source and its [official release implementation](https://github.com/cloudflare/workers-sdk/blob/ea57dfd56f2e82079927ce0b6fe690713e794a78/packages/miniflare/src/cf.ts) explain the mechanism: `cf: false` returns a fallback containing `verifiedBot: false`; omitted configuration may read cached metadata or fetch the documented development endpoint. An explicit object is returned directly. We resolved the annotated release tag to its commit rather than treating the tag-object hash as a source commit. The initial default-metadata capture does not establish whether cache, fetch or fallback supplied it; its metadata network activity was not instrumented.

The accepted harness now uses **`cf: {}`**. Three separate native-runtime controls reproduce empty → unavailable, disabled-fetch fallback → false, and explicitly injected positive → true. Those are labelled fixture controls, not provider verification or extra HTTP-routing cases. [Source checks](native-capture-source-checks.json) preserve the installed and pinned-source hashes. This finding does not rewrite previous native fixtures or promote their metadata into managed-service acceptance.

The [Worker Request contract](https://developers.cloudflare.com/workers/runtime-apis/request/#incomingrequestcfproperties) distinguishes runtime metadata from ordinary headers. [RFC 9110 §5.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.3) explains why field combination can hide original line multiplicity. Neither standard establishes the transformation/ingress behavior of this deployment. Current Node controls also verify that candidate headers cannot manufacture existing `verificationEvidence` native booleans.
