# Standards, libraries, and the evidence an agent identity can carry

Checked October 25, 2026 Pacific / October 26 UTC. Scope: primary standards and maintainer sources, the repository implementation at `a04ee04`, retained September experiments, and today's [dated audit](../edge-vs-rum/05-analytics-audit-2026-10-25.md). No production request, signature replay, SQL, credential access, or runtime modification was performed for this review. One network-free classifier probe is recorded below.

## The implementation's actual dependencies

The analytics package has no production-library dependencies in its [package manifest](../../../../analytics/package.json). UA classification, request evidence, HMAC identities, HTTP-message-signature parsing, Ed25519 verification, referral policy, and SQL composition are local code using native APIs. Matomo supplies an archived data list and comparison evidence; Matomo is not this site's runtime. The native crypto API is not a bespoke cryptographic primitive.

The [lockfile](../../../../../pnpm-lock.yaml) resolves Zod **4.3.6**, uPlot **1.6.32**, and Wrangler **4.71.0**. [.mise.toml](../../../../../.mise.toml) pins Node **24.14.1**. Zod validates research extraction/frontmatter; uPlot draws precomputed browser-side series; `node:sqlite` runs local fixtures. These layers cannot authenticate the audience represented by valid-looking numbers. The site renderer's other libraries are outside this measurement-specific review.

## What the verifier currently establishes

The relevant local path is inspectable without making a new network request:

1. `Signature-Agent` supplies an HTTPS URI. `agentLocation()` rejects URL credentials, derives `url.origin`, and uses that origin's fixed well-known directory (lines 636–640). It does not maintain a recognized-vendor catalogue or grant ledger.
2. Dictionary members accept the `directory` discovery type; unsupported types are rejected (lines 422–431). Direct `jwks_uri`/`cimd` discovery in the active draft is not implemented.
3. Directory fetches require HTTP 200 and disable automatic redirects. The code requests the directory media type but does not validate the response Content-Type (lines 578–589). It filters for Ed25519 verification keys and matches key IDs to derived JWK thumbprints (lines 529–547, 621–627).
4. Directory and key caches live in memory, expire after a fixed one-hour TTL, and coalesce concurrent directory loads. Keys are cached on `(directory URL, keyid)`, not keyid alone (lines 553–627). That avoids one cross-directory attribution error; it does not provide immediate key revocation or a global cache guarantee.
5. Verification requires a bot-auth tag, validity timestamps, accepted algorithm/key, a covered signer component, and either `@authority` or `@target-uri`. It allows 60 seconds of skew (lines 646–695). There is no local nonce-uniqueness/replay store or maximum-age policy beyond these supplied bounds.

A verified result therefore means the covered bytes verified under a key discovered from the selected HTTPS directory at that time, subject to that cache/profile. Someone controlling a new directory can sign as that directory; that alone does not make them Exa, Ahrefs, a benign client, or an authorized representative of a reader. A recognized vendor needs an independently maintained association with its documented identifier. That recognition must remain separate from cryptographic verification.

The active bot-auth draft has a consequential detail: a signature covering only `@authority` is reusable against that origin with another method, path or body until expiry. It allows that minimal profile while recommending narrower coverage. The local implementation accepts the minimal profile. It would be inaccurate to call every stored `verified` row proof of a fresh, uniquely bound page request or proof that a request body was authenticated.

Two compatibility points need an actual test review before another full-conformance claim. For `directory`, the active draft requires an ASCII origin (an empty `/` path may be accepted); local `agentLocation()` instead reduces a general HTTPS URL to its origin, discarding non-origin paths, query and fragment. Also audit dictionary signature-label/member association, media-type enforcement, key-source trust, caching/rotation and unsupported discovery forms. This is source inspection, not an executed exploit or a complete conformance audit. Preserve raw outcomes while deciding which profile is appropriate.

The [Cloudflare reference repository](https://github.com/cloudflare/web-bot-auth) is prior implementation art, not an installed dependency. Its README explicitly says the software has not been audited. The blog's parser is independently written. Compare a pinned reference version and official draft vectors before adopting code or claiming superiority; reuse the prior [bounded Matomo comparison](../agent-readership/01-matomo-and-agent-subscriptions.md) without rebranding it as a security benchmark.

## What can be determined about the 397 R1 events

The saved evidence supports a deterministic **cohort selection**: Browser rows reporting the retained R1 hostname under the dated window and exclusions. The [SQL and measurements](../edge-vs-rum/2026-10-25-audit.json) establish 397 events and their recorded distributions. This does not supply a deterministic mapping from that cohort to an authenticated agent, a person, the referral website's operator, or abuse.

In the current classifier, successful signature verification would take precedence over Browser classification. Navigation-shaped headers and ASN membership therefore do not replace missing signer evidence. Matching another provider's published network, a familiar referrer name, or a repetitive behavioral pattern would not establish that R1 caused a genuine external navigation or that a particular person directed it.

The [persisted schema](../../../../analytics/schema.sql) contains `signature_status`, verified `signature_agent`, UA rule outcome, reader kind/reason, bounded request evidence and pseudonymous daily ID. It does **not** retain the raw source IP, raw User-Agent, full Signature/Signature-Input, covered-component list, signing key snapshot, or a cross-source request ID. Verification failures are recorded in the reason; unverified claimed signer strings are not promoted into verified identities. The daily HMAC is not a substitute for those missing inputs. Most historical signature messages and UA/IP checks cannot now be replayed from D1.

Before proposing new storage, inspect whatever relevant existing native logs/traces are actually retained and whether they contain a reliable join key. A matching time/path is a candidate correlation, not an authenticated join. A future experiment can measure known causes; it cannot supply the missing historical trigger. A hostname exclusion can be an explicit reviewed reporting policy without pretending to identify the remote actor. Removing all 397 events is a sensitivity calculation until that decision is made.

## Bounded next iterations

1. **Separate evidence axes.** Keep observed request/representation, declared client name/role, signer origin/key result, vendor-recognition status, signature coverage/freshness and trigger knowledge separate. Unknown is a useful result. Preserve raw historical outcomes and version any new derivation.
2. **Repair known catalogue gaps prospectively.** Add documented ExaSearchBot/ExaUser and Ahrefs role names only after tests for collisions and unsigned/signed combinations. Preserve the unsigned role even when a signature verifies. Accept historical unknown role instead of assigning it from the signer.
3. **Review the supported verifier profile.** Compare implementation with a pinned active draft/reference, run positive/negative vectors, and test origin normalization, dictionary labels, coverage changes, expiry/skew, key rotation and stale-cache behavior. Describe supported subsets precisely. Assess narrower request signatures and stateful replay checks against bot compatibility, storage/read budgets and privacy; do not falsely call every minimally conforming authority-only signature invalid.
4. **Recognize vendors explicitly where useful.** Treat a verified directory as a directory/key result; recognize a vendor only against its primary documented identifier. For unsigned named crawlers, evaluate published IP/DNS checks at ingestion and retain a bounded validation result/version. An ASN is insufficient. Failure to verify can remain unknown without implying maliciousness.
5. **Add authenticated task receipts only for a concrete cooperative client.** A publication-issued credential or scoped grant could establish that a request presented an authorized credential for a named resource/action/time, if validation, revocation and audit records exist. [RFC 6750](https://www.rfc-editor.org/rfc/rfc6750.html) explains why a bearer token proves possession, not who physically used it. Request-bound signatures can add key possession and covered request integrity. Record the grant's issuer, subject/client, scope, expiry/revocation and validated action; do not expose credentials or require enrollment to read public articles. Such a receipt would still not prove attention, comprehension, benign purpose, or that a human initiated each request. No such system is implemented here, and it cannot authenticate old R1 requests retroactively.
6. **Calibrate with known cases after owner exclusion.** Use TASK-0120's explicit labels and collection-stage observations. Source verification and browser execution are different tests. Counter agreement is not an accuracy threshold; a disagreement is not a measured bot fraction.

## Historical wording that must not be copied as current evidence

- [ADR-0016.2](../../../../../docs/adr/0016.2-browser-evidence-and-reader-tier.md) contains an early assertion that the beacon/edge gap *is* automation, a clients/visits comparison, and a three-times heuristic. [TASK-0104's later contract](../../../../../docs/tasks/TASK-0104.md) and retained captures explicitly supersede that interpretation. Reuse the dated numbers with their original windows, not the unsupported causal conclusion.
- The same ADR's assertion that whole history can be recomputed from retained raw evidence is too broad for current fields: raw UA/Accept/IP and complete signature messages were not retained. Named-client and parser revisions cannot reconstruct all missing inputs. Its derived-partition description also predates stored reader-kind revisions.
- [ADR-0016.3](../../../../../docs/adr/0016.3-audience-composition-and-citable-articles.md) calls Web Bot Auth a shipping standard. The article should distinguish RFC 9421's published standard, the bot-specific active working-group draft, implemented vendor traffic, and the blog's tested subset. Deployed code is not proof of complete draft conformance.
- Older class names, Fetch Metadata browser-version thresholds and native plan assertions must be checked against newer implementation and platform sources. Do not silently edit the historical receipt or present its original expectation as today's acceptance criterion.

This review changes no code, policy or historical rows. Its constructive result is a more precise identity model and test plan, while today's R1 attribution and actual user triggers remain unresolved.
