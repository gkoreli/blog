This is a documentation/code review: no production request, SQL, credential read, entitlement change, or new instrumentation was performed in this lane. [Today's measured audit](../edge-vs-rum/05-analytics-audit-2026-10-25.md) owns the live observations; documentation does not establish which products this zone currently has enabled.

## Identity, role, and trigger are separate questions

Cloudflare now has a richer native vocabulary than the September ADRs describe. Its [Verified bots documentation](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/) (updated October 8) says that signed agents were folded into Verified bots and agents on July 1. BotBase distinguishes behaviors such as Search, Agent, Training, SEO, and Monitoring, and Direct versus Intermediary operation. The same page warns that the new behaviors are not individual WAF custom-rule fields: the older category taxonomy remains supported there.

That is useful identity and service-role evidence. It is not a publisher-visible receipt proving the trigger of each individual request, the end user's authorization, successful reading, or citation. Even an Intermediary service is a separate party from its end users. The native taxonomy should inform a separately sourced role field, rather than replacing our current signature-first conflation with a different single label.

## What is deterministic about R1?

The existing evidence deterministically identifies **the stored cohort selected by its reported hostname**, within the audit's dates, owner predicate, and Browser classification. It contains 397 recorded page events. The query and aggregate commitments are in [the audit SQL](../edge-vs-rum/2026-10-25-audit.sql) and [JSON](../edge-vs-rum/2026-10-25-audit.json). The raw hostname remains private; R1 is an alias, not a new public approval.

That selection does not deterministically identify the requester, authenticate the external referring website, prove the requests came from one operator, or prove automation. The stored evidence retains category, path, ASN, country, limited request shape, daily pseudonym, and signature outcome; it does not retain a raw message suitable for later signature replay or a shared request ID joining every historical event to Cloudflare logs. Absence of a verified signature is not a bot identity.

A current native bot-verification/category receipt could strengthen attribution for matched requests if available. A retained full log could expose repeatable declared-client characteristics. A narrow time/path/country correlation remains a candidate match, especially against sampled zone groups. To label all 397 as one known actor or bot requires evidence that covers all 397, not an explanation that fits a few.

## Native alternatives worth evaluating only against a demonstrated gap

- **Queues:** [delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) are at-least-once, so ingestion needs an idempotent event key and duplicate-handling acceptance. This is an option if measured `waitUntil`/persistence loss warrants it, not a current deployed fix or an exactly-once counter.
- **Workers Analytics Engine:** the [native binding](https://developers.cloudflare.com/analytics/analytics-engine/get-started/) writes data points without awaiting or manually using `waitUntil`. Its query model includes sampling. It may serve operational stage/error counts; it does not automatically replace retained D1 evidence or solve classification.
- **Scoped analytics access:** [API tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/) can be restricted by permission, resource, and lifetime. A supported authorized export path is preferable to scraping a broad stored credential. This research creates no credential or access grant.

## Historical language that must not become the current claim

1. [ADR-0016.2](../../../../../docs/adr/0016.2-browser-evidence-and-reader-tier.md) treats the earlier counter gap as automation and proposes rough ratio thresholds. The later calibration contract and measured audit supersede those inferences; counter disagreement does not allocate its causes.
2. The same ADR describes no available native per-request bot fields on the then-Free zone. Current documentation now explicitly exposes signed-agent and category mappings. Actual availability remains a product/entitlement question; Workers Paid does not answer it.
3. Its original simplified `Accept` rule and request-time recomputation model are historical; the September parser release and stored `reader_kind` implementation govern the current code.
4. The `wrangler.jsonc` comment accurately names **Free** three-day retention, but must not be read as today's Paid retention. The current logs/traces docs say seven days for the relevant Paid/logs and trace retention windows, subject to collection and actual access.
5. [September zone-state notes](../readers-vs-bots/07-cloudflare-agent-readiness-and-zone-state.md) are a dated dashboard observation. Their bot categories, access settings, roadmap panels, and recommendations are not a current native capability inventory.

No historical ADR or capture was rewritten during this review. Next bounded evidence collection should first establish current product state and retained field coverage, then use those fields only for the question they can answer.
