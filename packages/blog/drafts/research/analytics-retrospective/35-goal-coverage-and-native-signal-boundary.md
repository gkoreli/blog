## A documented field is not yet a trusted runtime signal

The original [native inventory](01-native-capabilities.md) identified a product-specific question. A fresh native inspection reaches this zone's request-header Transform Rule editor. The zone badge says Free; the editor shows zero of ten available rules. That establishes editor access, not acceptance of a particular field or expression. The visible field picker lists seventeen options and no bot field; picker omission likewise does not establish expression rejection. The rule name stayed blank, no fields were entered, and neither Save as Draft nor Deploy was invoked. Cancel returned to Rules Overview. The template count there is not a deployed-rule count.

Official documentation, re-read today, supplies the candidate and its boundaries:

| Primary source | Supported finding | Consequence for this implementation |
|---|---|---|
| [`cf.client.bot`](https://developers.cloudflare.com/ruleset-engine/rules-language/fields/reference/cf.client.bot/) | Boolean assessment of a known good bot/crawler; documented as the same information as `cf.bot_management.verified_bot`. | It is not an `IncomingRequestCfProperties` field name, a cryptographic-only verdict or a human classifier. |
| [Request-header expression fields](https://developers.cloudflare.com/rules/transform/request-header-modification/reference/fields-functions/) | Lists `cf.client.bot` and `cf.verified_bot_category`. | A plausible rule-product route exists; this list alone does not prove actual-zone entitlement or delivery. |
| [Functions](https://developers.cloudflare.com/ruleset-engine/rules-language/functions/#to_string) | `to_string` accepts Boolean values. | `to_string(cf.client.bot)` is a documented candidate expression, not an executed rule in this audit. |
| [Transform availability](https://developers.cloudflare.com/rules/transform/) | Free zones have ten active rules. | Consistent with the observed editor quota; not Bot Management entitlement. |
| [Header modification contract](https://developers.cloudflare.com/rules/transform/request-header-modification/) | Set overwrites or creates; empty/undefined removes; `cf-` and `x-cf-` names are reserved. Later rules can overwrite earlier results. | Use neither reserved names nor a header-name convention as proof of origin. Overwrite, duplicate handling, ordering and missing states need acceptance. |
| [Worker Request API](https://developers.cloudflare.com/workers/runtime-apis/request/#incomingrequestcfproperties) | `request.cf` provides native metadata; `botManagement` is only set with that product. | Preserve its actual nullable booleans independently. Workers Paid and a Free zone do not establish Bot Management availability. |
| [Worker-subrequest example](https://developers.cloudflare.com/rules/transform/examples/add-request-header-subrequest-other-zone/) and [`cf.worker.upstream_zone`](https://developers.cloudflare.com/ruleset-engine/rules-language/fields/reference/cf.worker.upstream_zone/) | Rules can distinguish a Worker subrequest's upstream zone from an empty non-Worker value. | Relay coverage belongs in the experiment. This is not proof that every application ingress or internal call traverses the intended rule. |

The existing `verificationEvidence` reads native bot values from `request.cf.botManagement`, with exact Boolean checks, and the category from `request.cf.verifiedBotCategory`. It does not interpret ordinary headers as those facts. A future header bridge needs separate source/version/configuration provenance. A disabled or bypassed transform could leave a caller's identically named header intact; a stale application flag or expected hostname alone would not attest the transformation. This is a design counterexample, not an observed attack against production.

One new [regression test](../../../../analytics/test/native-category.test.mjs) protects this boundary. Synthetic requests with provider-looking headers, a proposed analytics header, guessed Ruleset aliases and malformed Boolean values cannot manufacture Worker-native evidence. Actual fixture booleans retain false/true separately, and a native-positive fixture does not replace a local invalid-signature outcome. These are in-process source tests, not Cloudflare-generated metadata or measured production header sanitization. The complete analytics suite passes **189 tests**; runtime code and all collection/classifier/verifier/report versions are unchanged.
