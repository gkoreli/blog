## The remaining gap is measurement coverage

The code now preserves considerably more evidence than the early analytics did. That does not make every recognized bot authenticated or every Browser event human. The [source-derived catalogue inventory](goal-audit-catalogue.json) counts **48 recognized client declarations**. Nine have a configured published-IP method; two have a documented signing-origin method. Their union is **11 declarations**, leaving **37 without either configured per-declaration method**. Eight IP feeds serve those nine declarations; method counts are not vendor counts or traffic shares.

Four declarations separately map to two reviewed directory publishers. Three public signer display approvals are another distinct catalogue. Neither is silently counted as a per-client signing promise. Generic signature verification can work beyond these maps, but an arbitrary key or display label does not establish a reviewed operator. Missing configuration also does not prove that a vendor publishes no verification method.

[The maintained inventory helper](../../../scripts/audit-analytics-capabilities.mjs) checks catalogue references, duplicate source IDs and complete declaration coverage. It emits closed catalogue names, declared roles, configured methods, source links and code hashes—not reader records. The same run can be repeated after each deliberate registry extension. It is not a freshness probe for every external source.

## Re-score the actual labels without creating more traffic

[The replay](goal-audit-calibration.json) checks the original seven private-input hashes against the accepted ledger and reproduces its evaluation and condition totals. Six classification components are byte-identical to the accepted stage-release source; the evaluator is byte-identical to its accepted publication source. This establishes source continuity and a repeatable stored-kind evaluation, not a new end-to-end run of the now-changed collector/verifier.

The denominator stays twelve selected automation executions: **3 decisions / 9 abstentions**, with **0 wrong among the 3 decisions**. A separately undeployed Browser-as-human interpretation makes **9 wrong decisions** on the same controls. Repeated conditions from two profiles are not independent readers. The later one-request parser-failure check has a different protocol/exclusion basis and is not appended to this calibration cohort. The original ledger's 166 diagnostic reads are reused historical cost; this replay performs no SELECT.

The directory's five published `kid` labels differ from computed thumbprints. Using those labels in our controlled requests yields key-not-found; using computed thumbprints reaches signature-invalid. The [current WG draft §5.2](https://datatracker.ietf.org/doc/html/draft-ietf-webbotauth-httpsig-protocol-00#section-5.2) requires the thumbprint form for protocol `keyid`. We have no real signed Google request here, so neither infer Google's on-wire choice nor relax our key-selection policy from directory labels alone. The browser research tool could not render the directory's media type; curl captured it successfully without sending reader data.

Google-GeminiNotebook's appearance on a broad fetcher page does not assign it every Google IP feed or Google-Agent's experimental signing promise. Its precise mapping needs its own evidence. The inventory also confirms that the current Exa signing table intentionally exposes overlapping known-method and unmapped-declaration counts; this audit does not mistake that documented overlap for a new exclusive partition.

No runtime/profile/schema/report change, production visit/query, raw-capture activation, human trial or native-rule change occurs. Next: implement the dedicated Google-Agent and DuckDuckBot published-IP sources, then the documented experimental Google signing-origin association, with native controls, preserved historical profiles, exclusion/cost acceptance and no promise that every Google request signs. Keep actual positive vendor traffic, native agreement and deferred human/device trials as separate gates. This has a stronger evidence basis than adding another isolated protocol mutation test.

Adding a second documented signing origin also requires mixed-declaration controls: one selected proof may match one expected origin while another declaration names a different one. Preserve the current overlapping unmapped counts, keep selected-proof scope explicit, and expose that conflict instead of turning a partial match into a global vendor verdict. The current catalogue has only one such origin, so this is a required extension test, not a claimed production failure.
