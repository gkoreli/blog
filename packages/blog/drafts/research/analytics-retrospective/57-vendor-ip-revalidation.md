# A 304 must identify the feed being reused

October 27 Pacific / October 28 UTC. Continues [network-summary consistency](56-vendor-network-summary-consistency.md). Human trials remain deferred.

**Our feed cache renewed old IP ranges on any 304 response.** A response carrying a different ETag could therefore make the old body available for attribution again. Thirteen controlled cases reproduce the weakness in Node and workerd. This establishes a local cache-admission defect, not that a production vendor sent those responses or that historical attribution changed.

## Select the representation before refreshing it

[RFC 9110 §15.4.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4.5) defines 304 for conditional requests. [RFC 9111 §4.3.4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4) requires identifying an appropriate stored response before updating it. A returned strong tag that does not match a stored strong validator cannot refresh that representation.

The dedicated [conditional-validation policy](../../../../analytics/src/vendor-ip-cache.ts) requires a conditional request and a corresponding returned validator. Strong tags must match exactly; returned weak tags compare opaque values. A matching Last-Modified date can identify our single stored representation when no ETag is returned. Missing, malformed, mismatched and unsolicited validation results become `unavailable / revalidation-mismatch`. The old entry is evicted; the bounded cooldown remains, then a full GET can recover. No extra immediate retry is added.

The policy intentionally accepts bounded ASCII entity tags and canonical IMF-fixdate modification dates. Other validator forms are omitted from conditional requests, allowing a full fetch. This is narrower than a general HTTP cache and is not a full HTTP-conformance claim. The existing body/media/feed validation, fixed endpoints, deadline, redirect rejection and no-stale-on-error policy remain.

A late aborted response cannot evict a newer entry. Matching validation retains the original body digest and fetch time while updating the recorded validation time. These timestamps use the helper's supplied request-start clock; they are not separately measured response-receipt timestamps.

## Borrow the distinction, inspect the differences

The pinned [`http-cache-semantics` implementation](https://github.com/kornelski/http-cache-semantics/blob/b1d4bd682fbab0252985de45219f4e7497c0067c/index.js#L856) returns a separate `matches` result when handling revalidation. That separation is useful: a 304 status alone is insufficient. We reviewed its source; it is not a new dependency or an executed independent oracle. Its strong-tag branch removes an old weak marker before comparison. Our narrower policy rejects that upgrade, following the strict stored-strong-validator reading above. Do not infer agreement on every case or library conformance from this review.

## Preserve the age calculation that already works

The initial review also suspected a missing response-delay adjustment. [RFC 9111 §4.2.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3) supplies the reference equations. Algebraically, a request-start-anchored expiry using the larger of header age and request-start apparent age reaches the same deadline for a fresh response. Moving the anchor without adjusting age would introduce an error.

Forty-eight Node controls vary date, age and simulated receipt delay: fresh deadlines agree with the independent response-age calculation; expired cases remain non-reusable. These are arithmetic controls, not measured network latency or a general cache audit. The age algorithm is unchanged.
