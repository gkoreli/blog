# Twelve User-Agent failure families: evidence, scale and disposition

November 10, 2026. Evidence map for [worklist 136](136-user-agent-trust-and-hardening.md). These twelve families organize this audit; they overlap and are not an exhaustive count of possible bugs. A documented browser default can affect an entire browser/mode population without every affected site being broken. A reported incident, controlled counterexample and measured prevalence are different evidence.

## What scale can be established

The platform families are broader than the original phone-brand defect: browsers deliberately reduce versions or change presentation identity. The relevant population is defined by browser/version/mode/customization, not by a total count of people or broken sites. Reported library incidents establish specific experiences; our reproductions establish supplied-input mechanisms. We do not sum these populations or turn package downloads into affected deployments.

The code audit initially isolates two repair domains: single-browser selection and OS/version selection in optional diagnostics. Existing final collection/role classification does not consume the optional OS values. The new reusable supplied-input assessment exposes these distinctions without granting trust to pasted headers. Unsolvable missing identity or hidden OS details remain explicit limits rather than engineering TODOs.

A later native `Headers` comparison finds a third normalization domain: NBSP-padded `Sec-CH-UA-Mobile: ?1` survives native header normalization but JavaScript `trim()` turns it into an accepted preference. The Structured Fields Boolean accepts no such padding. The repair uses only HTTP SP/HTAB, advances collection/form/current-request profiles prospectively and explicitly retains both older form profiles. A mixed-history report test must preserve the older recorded preference rather than recompute it under the new rule. This belongs to family 9, not a new prevalence category.

## Native and source checks

The final native run compares 35 supplied cases in Node and actual local workerd, then stores/reads each closed result in a fixture D1 table: all 35 match exactly. This checks runtime/serialization agreement, not a human device, browser fidelity, the production collector or an external bot verifier. The existing full collector integration separately passes its 22-request baseline and 26-request detection phase. [Acceptance 138](138-user-agent-hardening-acceptance.md) records profiles, costs, checks and limits.

The ReDoS source lookup initially used a wrongly expanded commit prefix and failed. The known short prefix from the advisory is then resolved to the actual full commit above; only that inspected fix supports the claim. No vulnerable package is installed or exploit run. Web/native-source captures, the initial counterexamples and failed checks stay privately preserved under the worklist's archive.
