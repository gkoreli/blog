# Deterministic guarantees for public analytics and referral defenses

Reviewed September 9, 2026 UTC / September 8 PDT. [TASK-0140](../../../../../docs/tasks/TASK-0140-audit-deterministic-guarantees-and-prior-art-for-referral.md), [complete owner prompt](source.prompts.md), [referral-abuse worklist](../../../../../docs/folders/FLDR-0009.md).

We can enforce rules about which names appear, which observations count, and which operations are admitted. We cannot guarantee that every anonymous request represents a person or a genuine external referral. This distinction gives us concrete engineering work without describing a deterministic classifier as an infallible account of the world.

## Why the evidence has a limit

`Referer` is a claim supplied by the requesting client. [RFC 9110 §10.1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.3) defines its meaning and circumstances in which it can be absent or shortened. [curl's `--referer` option](https://curl.se/docs/manpage.html#-e) makes the client's control explicit. A real browser can also suppress the field under [Referrer Policy](https://www.w3.org/TR/referrer-policy/#referrer-policy-no-referrer).

The engineering inference is simple: if a genuine navigation and a fabricated request present identical evidence to our decision function, the function cannot distinguish their origins. Collecting another field helps only to the extent that it adds relevant evidence an adversary cannot reproduce. A browser-enforced restriction on page JavaScript does not make a header trustworthy when a different HTTP client can set it.

Likewise, proving that an external page contains a link would establish the link's presence at inspection time, not that a particular request followed it. A missing referrer cannot tell us whether someone used a bookmark, followed a privacy-preserving link, or ran a script. These are reasons to label the evidence accurately, not reasons to stop defending the system.

## Guarantees we can define and test

These are conditional software guarantees: all relevant output and execution paths must use the specified policy, with correct implementation and configuration. They are not guarantees against every software defect or compromised authority.

| Issue | Enforceable property | Remaining uncertainty | Our status |
|---|---|---|---|
| Arbitrary names gaining public exposure | Only exact reviewed hostnames can enter public referrer-name fields; every other included name uses a generic bucket, regardless of volume. | An attacker can still claim a reviewed name. Reviewing a name approves its display, not the requests claiming it. | Deployed under policy `2026-09-06.2`; see the activation evidence below. |
| Observations matching a spam rule | The same versioned exclusion removes matching observations from all defined public metrics and discloses the excluded count. | A real referral from that hostname is excluded too; different or missing names can evade the rule. | Deployed, including the Matomo snapshot and local override. |
| False headers or an impersonated approved referrer | Parse and bound input; classify it as reported evidence. A stronger protocol can require a valid signature over specified fields from an explicitly trusted issuer. | Correct syntax or a valid signature does not establish a real click. Existing uncooperative referring sites supply no such receipt. | Reporting distinctions exist. No general external-referral attestation protocol is deployed. |
| Absent or unusable referrer | Record observed absence, unusable input, internal context, and external context separately; retain unknown historical states. | The reason for absence and the original external source remain unknown. | Implementation `c338059` is deployed; migration and collection acceptance are in the [separate release receipt](../article-024-hacker-news/07-transition-release-acceptance.md). Real-browser calibration remains open. |
| Automation passing other filters | Enforce a stated admission condition or request quota, and retain the exact evidence supporting each classification. | Passing a challenge, authenticating a key, or staying below a limit does not establish a human reader, benign intent, or authentic referral. | Existing reader kinds describe evidence. No universal human-authentication claim is supported. |
| Repeated requests causing query expense | A design can ensure public report fetches never trigger database calculation, or require atomic budget reservation before every costly operation. | Collection, serving, coordination, and other account operations still have costs. A query-admission count is not an exact D1 row-read or billing cap without a defensible cost bound. | Shared assessment and local caching are deployed; a global admission budget is not. |

The deployed reporting decision is [ADR-0016.5](../../../../../docs/adr/0016.5-referral-abuse-defense.md), extended by [ADR-0016.6](../../../../../docs/adr/0016.6-versioned-referral-policy-and-matomo-source.md). [Saved activation evidence](../readers-vs-bots/19-referral-policy-activation.md) establishes its release; this study did not repeat production queries. The separate [referrer-context decision record](../article-024-hacker-news/06-transitions-and-funnels.md) and [acceptance receipt](../article-024-hacker-news/07-transition-release-acceptance.md) now establish migration and live scripted collection. A code commit alone would not establish either. This September 9 status correction reuses that evidence; scripted header probes do not establish ordinary browser behavior or complete funnels.

None of these sources independently establishes that the destination discussed in article 025 distributes malware or that every recorded referral was false.

## What stronger attestation can establish

A stronger mechanism is useful when its verified property matches the decision we need to make. It must not acquire a broader meaning in the dashboard than it has in the protocol.

| Mechanism | Verified property and required enforcement | Limit |
|---|---|---|
| [Turnstile server verification](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/) | A token passes Cloudflare's server-side verification; tokens expire after 300 seconds and are single-use. Check expected hostname and action as well as `success`. | The hostname identifies where the challenge was served, not the external referrer. This does not establish readership or referral provenance. |
| [Cloudflare bot scores](https://developers.cloudflare.com/bots/concepts/bot-score/) | A classification based on available signals; most scoring uses machine learning, with other detection methods also present. | The documentation discusses false positives. A deterministic heuristic is still a heuristic about humanity or automation. |
| [Privacy Pass, RFC 9576 §3.5.1](https://www.rfc-editor.org/rfc/rfc9576.html#section-3.5.1) | Attestation establishes the configured property, which can concern a device, account, or challenge capability. | Those properties are not interchangeable. [Cloudflare's PAT integration](https://developers.cloudflare.com/cloudflare-challenges/reference/private-access-tokens/) can reduce challenge steps; token absence is not proof of abuse. |
| [HTTP Message Signatures, RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2) | Given a trusted verification key, validate the signature and the covered request components, with an explicit freshness/replay policy. | Unsigned fields remain unprotected. Signing a referral claim authenticates the signer's statement, not its real-world truth. |

There is a concrete replay caveat in [Cloudflare Web Bot Auth](https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/#43-construct-the-required-headers): its documented verifier does not currently validate nonces or retain a seen-nonce database. Short validity windows reduce exposure; they do not make a request single-use. Recommended coverage includes target authority and signer identification, not automatically `Referer`. Cloudflare's [implementation examples](https://github.com/cloudflare/web-bot-auth) are inspectable prior art and explicitly unaudited.

Our [existing verifier](../../../../../packages/analytics/src/webbotauth.ts), inspected at `c338059`, checks Ed25519 signatures, target coverage, signer location, and validity times. It discovers keys from the client-selected HTTPS directory origin; this function has no trusted-operator allowlist. It checks supplied `created` and `expires` values with 60 seconds of clock tolerance but imposes no maximum signature lifetime. This bounded inspection found no replay ledger; it was not a full security audit. The returned verified signer establishes signature validity and directory-origin attribution. It must not be interpreted as a human identity, proof of a referral, short-lived single-use admission, or independent approval of that operator's reputation.

A cooperating publisher could issue a signed, destination-bound, expiring referral receipt, and our server could redeem it atomically once. That proposed design would establish a statement from the trusted issuer and a redemption. Tokens can still be obtained or shared by automated clients; the protocol would not establish attentive human reading. Requiring cooperation from arbitrary referring websites is disproportionate to the current public-blog problem.

## Resource guarantees are a separate design problem

The deployed [report cache](../../../../../packages/blog/src/worker/stats-cache.ts) has a one-hour maximum TTL, validated versioned keys, and at most eight pending fills per isolate. It can still calculate on a cache miss. The [Cloudflare Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) is local to a data center, so the TTL does not establish one global calculation per hour.

The [Workers Rate Limiting API](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/#accuracy) is permissive and eventually consistent, with per-location limits; it is unsuitable for exact accounting. [WAF rate-limiting counters](https://developers.cloudflare.com/waf/rate-limiting-rules/#important-remarks) can also lag. Either can mitigate volume without being a strict spending ceiling.

If measurements justify stronger cost isolation, one option is a finite set of scheduled report snapshots: public requests only retrieve prepared reports, and no cache miss or novel filter launches SQL. Unavailable or stale snapshots need an explicit response. This can guarantee zero request-triggered report queries if every public report path follows it, while trading off freshness and arbitrary exploration. It does not cap ingestion or all account costs.

Another option is atomic admission before a costly operation. [Durable Objects](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) provide transactional coordination, but an exact quota needs every relevant path to reserve before execution and deny admission on uncertainty. Query counts require defensible per-query cost bounds before they can imply row-read bounds. [Cloudflare cautions against a global singleton](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#do-not-use-a-single-durable-object-as-a-global-singleton); distributed allocation and failure handling need design. Neither option is implemented by this study or needed to substantiate article 025's reporting result.

## Next engineering work and meaningful acceptance

Keep the current exposure and exclusion guarantees, use the accepted context collection, and measure residual abuse before choosing another heuristic. A blanket challenge for every reader or exclusion of every missing referrer would introduce costs and lost observations without proving authentic referrals.

| Priority | Bounded work | Acceptance evidence |
|---|---|---|
| 1 | Preserve the established public projection and shared exclusion policy through report changes. | Existing adversarial-host and reconciliation cases continue to pass for every public filter and cache version. Raw retained evidence remains unchanged. See [initial verification](../readers-vs-bots/17-referral-abuse-defense-verification.md) and [Matomo-policy verification](../readers-vs-bots/18-matomo-referral-policy-verification.md). |
| 2 | Observe organic referrer context and complete the controlled browser calibration in TASK-0120. Reuse the accepted migration and scripted checks rather than repeating them. | Record known browser navigation and policy-driven omission with owner/test exclusions. Keep it separate from the nine excluded scripted acceptance requests. Internal, absent, unusable, external, and historical unknown remain distinct; no historical unknown is invented as a direct visit or HN referral. |
| 3 | Capture a small controlled comparison locally before expanding detection. | Label human-operated navigation and scripted requests independently. Include a forged reviewed host, rotated unreviewed hosts, missing header, ordinary browser navigation, and a legitimate privacy-preserving navigation. Record what each rule sees, counts, and publishes. No production traffic simulation or guessed false-positive percentage. |
| 4 | Select any further admission or cost control from a measured failure. | For a challenge: wrong action/hostname, expiry, replay, and provider failure. Before using signatures for admission, specify issuer trust, maximum lifetime, and replay semantics; test unsigned-field tampering, changed covered fields, an untrusted signer, excessive lifetime, and replay. For a quota: concurrent reservations, retries, failure states, and all bypass paths. For snapshots: public requests never call the query function. These are proposed tests, not completed results. |

The controlled comparison can demonstrate known limitations and catch regressions. It cannot estimate a population-wide bot-detection rate from a few chosen cases. External request classifications should continue to describe evidence; friendly names such as Browsers or reviewed referrers must not become claims of verified people.
