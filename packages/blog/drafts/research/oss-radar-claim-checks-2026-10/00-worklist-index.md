# Five OSS Radar claim checks

Started October 30, 2026 (Pacific; initial source capture continues into October 31 UTC). Owner requested applying the question-led claim-checking approach to five ideas. This is active research, not five completed articles or a claim of reader adoption.

## Scope and acceptance

For each selected idea: identify the original claim, dated public reader question and intended user before substantial research; pin the implementation; inspect and reproduce the consequential behavior where feasible; test the strongest obvious alternative; then publish the supported missing answer, or explicitly reject/defer the idea if the evidence or distinct reader value fails. Keep each resulting article to roughly four–five minutes. Use a separate project deep dive for each; this intake is not a five-project roundup.

Publication on our site follows repository delivery rules. The specific Theo follow-up was separately authorized and delivered. This goal does not imply permission to send five unsolicited pitches, post generated HN comments, make paid API calls or provision paid GPU hardware. Prepare distribution around the observed questions; seek a narrower route if a destination requires human operation.

## First bounded experiments

1. **tsrs:** pin release, upstream TS revision and one public application; compare diagnostic sets before timing. Run current default and `--fast` separately, same worker settings where supported, five runs with source/config unchanged. Treat source-build cost and checking speed separately. Include at least one invalid-code control. Broaden only if this changes the decision.
2. **Status summaries:** establish the named harness version and original measurement method. Use synthetic transcripts only; identify trigger, cadence, selected model, cache accounting and whether the proposed setting stops calls or just hides UI. Recompute any available public trace totals; do not report that as a new week of usage. No proxying private sessions or transmitting user transcripts.
3. **Hob:** inspect the hardware picker and local inference path; select one available machine and two synthetic document tasks with objective expected output. Separate install/model downloads from an offline run. Record RAM, timing and whether tools actually changed the intended file. Do not generalize one Mac to every M1/Windows/Linux machine.
4. **PaperPilot:** pin source and trace CLI/WASM/MCP operations. Use a synthetic PDF containing a unique canary; split/extract/redact, then inspect text/objects from output. Inspect network-capable code and test the selected local execution path. A local tool returning document text to a cloud model is a composition boundary, not proof that PaperPilot itself uploads PDFs.
5. **Qwenputer:** pin source and trace one instruction through circuit compilation, memory state and the driver. Run available CPU/circuit tests without downloading a giant checkpoint first. Compare exact results to a reference interpreter, including a negative control. Keep full-model behavior author-reported unless actually run.
