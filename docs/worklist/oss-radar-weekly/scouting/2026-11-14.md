## Bright Lines: a process can fail closed while its host policy still matters

Pinned revision: `84cfe3912b1c15dd1caf8a46bcbaab5d98b5a2a3`. The setup combines Claude Code permissions, a Python hook, human review and recovery. It adds policy around the host's tools; it does not replace the host, sandbox arbitrary programs or make approval harmless. Its README already discloses pattern-matching limits and a timeout gap.

The [guard](https://github.com/LeriderTechnologies/bright-lines/blob/84cfe3912b1c15dd1caf8a46bcbaab5d98b5a2a3/template/.claude/safe/guard.py) checks the stop file and permission mode, then locks and updates session counters **before** matching commands. The [settings wrapper](https://github.com/LeriderTechnologies/bright-lines/blob/84cfe3912b1c15dd1caf8a46bcbaab5d98b5a2a3/template/.claude/settings.json) converts an abnormal guard exit into exit 2. A wrapper cannot perform that conversion while its child is still waiting.

The unchanged upstream suite passed **28 test methods**, covering its 177 blocked-command and 50 allowed-command fixtures plus other controls. Those command strings are fed to the guard; the suite does not execute the proposed actions. This is upstream regression-suite acceptance, not 227 independent real-world tasks.

The [qualification protocol](bright-lines/protocol.md) and [probe](bright-lines/probe.py) add six direct-process controls. The [receipt](bright-lines/results-2026-11-14.json) records the exact source hashes and Python 3.14.6/macOS conditions:

- Ordinary command data exited 0; network-command data and malformed JSON exited 2.
- A scratch guard that exited 1 was converted to exit 2 by the actual configured wrapper.
- Holding the probe's own same-session counter lock left that same wrapper without a decision at its configured 10-second deadline. The harness stopped its own child process group after 10.006 seconds. Once the lock was released, the network-command payload was rejected again in about 72 ms.

No proposed command was executed. This is fault injection into an owned scratch state directory, not evidence that normal concurrency stalls this long or that another agent can acquire the lock. The mechanism matters because bounding command length does not bound a blocking filesystem wait.

[Current host documentation](https://code.claude.com/docs/en/hooks#block-the-action-when-a-hook-fails) provides `onFailure: "block"` from Claude Code v2.1.295, including timeouts. The pinned template omits it. With the field unset, the documented timeout path continues through ordinary permissions; that does **not** establish automatic execution or removal of human review. This host behavior and the field's effect are primary documented, not reproduced by the direct-process test. The locally installed CLI reported 2.1.319 via `--version` only; no model session ran.

Candidate value: a reader can inspect three different failure decisions and test the boundary in their own hook setup. A possible configuration change is supported by documentation, but no patch was installed, submitted or called accepted. A full issue still needs host-level missing/crashing/stalled hook controls with and without the field, plus useful allowed-workflow and approval-cost checks. Reproducing a disclosed limitation alone is insufficient for a broad adoption verdict.

## Agweb: workspace separation and profile sharing are different choices

At `a52c8b66e16499ec2781c7fea3c4a37983a7002c`, [workspace construction](https://github.com/paul-nameless/agweb/blob/a52c8b66e16499ec2781c7fea3c4a37983a7002c/Sources/AgwebApp/Browser.swift#L43) passes the profile into `Workspace`. [Model.swift](https://github.com/paul-nameless/agweb/blob/a52c8b66e16499ec2781c7fea3c4a37983a7002c/Sources/AgwebApp/Model.swift#L197) uses a fresh nonpersistent website store when the profile is absent, while named profiles reuse a cached store. The configuration installs that store into WebKit. [Cookie commands](https://github.com/paul-nameless/agweb/blob/a52c8b66e16499ec2781c7fea3c4a37983a7002c/Sources/AgwebApp/BrowserState.swift#L89) act on the workspace's store. Separate workspaces using one named profile therefore share website data by design; the runtime consequences have not been measured here.

A [public discussion question](https://news.ycombinator.com/item?id=50497457) asks about logout/account changes affecting other workspaces. It supplies an operator question, not a reproduced incident. A feasible next trial uses a local fictional-login fixture to compare two workspaces with one named profile, distinct profiles and no profile. It should inspect cookie/logout effects and default ad blocking without real accounts. The app requires macOS 26/WebKit; isolated named-store placement also uses private WebKit interfaces. Memory, focus, compatibility and token-saving claims remain maintainer-reported.
