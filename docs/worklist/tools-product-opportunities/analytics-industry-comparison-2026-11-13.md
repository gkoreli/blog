## Method and selection

Inspect our current source, the standalone-install result and the latest D1 performance handoff. Compare them with current first-party product documentation and public GitHub repository pages. GitHub connector metadata confirmed the selected repositories; its normalized response omitted stars, so public repository pages supplied the displayed counts.

Stars measure repository interest, not installed sites or successful use. This is a representative web/product analytics set, not an exhaustive GitHub ranking. BI dashboards, databases and generic telemetry projects are outside this comparison. Features refer to the documented product family unless an edition is specified; a hosted feature is not automatically present in a free self-hosted release. No competitor stack was installed, no detection-accuracy benchmark was run, and no new own-site traffic or production SQL was generated.

## What the current competitors actually offer

- **Umami:** its [v3 documentation](https://docs.umami.is/docs) covers acquisition, UTM campaigns, custom events, goals, funnels, journeys, retention, revenue, boards and teams. Its [official MCP](https://docs.umami.is/docs/mcp) is read-only, uses API permissions and can serve analytics to another agent. Cookieless collection and an AI-query interface are established features in this market.
- **Plausible:** the [documented collection policy](https://plausible.io/docs/bot-traffic-filtering) excludes bots and directs operators to server/CDN logs for AI crawls; AI click-through referrals are distinct. Its [data interfaces](https://plausible.io/docs/data-access) include event ingestion, reporting and exports. [Community Edition](https://plausible.io/self-hosted-web-analytics) omits cloud features including funnels, journeys, revenue goals, SSO and the sites API. Its two official pages give differing approximate datacenter-range counts; no numeric detection-coverage comparison is inferred.
- **PostHog:** [product analytics](https://posthog.com/docs/product-analytics) supplies trends, funnels, paths and retention. Its [current bot documentation](https://posthog.com/docs/web-analytics/bot-detection) describes retained HTTP logs, UA and published-IP rules, query-time categories and custom rules. Our inclusion of agents and retention of underlying observations is therefore not unique. Those documented rules do not establish cryptographic identity. [Self-hosting](https://posthog.com/docs/self-host) is officially unsupported, so source availability is not a managed-operation guarantee.
- **Matomo:** [AI chatbot reports](https://matomo.org/faq/reports/ai-chatbots-overview-report/) use Cloudflare, CloudFront, WordPress or HTTP integrations; [the setup guide](https://matomo.org/faq/how-to/install-ai-chatbot-tracking/) describes UA substring rules. The [tracking API](https://developer.matomo.org/api-reference/tracking-api) separately exposes bot and visit/action modes. Treating Matomo as a browser-script-only product would now be wrong.
- **Rybbit:** [bot detection](https://rybbit.com/docs/bot-detection) combines UA, headers, browser signals, ASN and rate evidence and can retain compact filtered bot events with matching layers. This is broader behavioral detection than our current request classifier. It is not a demonstrated accuracy advantage. Its [suite](https://rybbit.com/docs) also supplies goals, funnels, annotations, imports and integrations; some dashboard/SQL delivery depends on the edition/image.
- **OpenPanel:** its [documentation](https://openpanel.dev/docs) supplies script/SDK installation, event and identity APIs, exports, MCP, product reports and deployment guides. Those practical integration paths are substantially broader than our current package.
- **Cloudflare AI Crawl Control:** [analytics](https://developers.cloudflare.com/ai-crawl-control/features/analyze-ai-traffic/) includes errors/blocked attempts, transfer volume, operators and requested/served formats. [GraphQL](https://developers.cloudflare.com/ai-crawl-control/reference/graphql-api/) distinguishes spoofable UA filters from verified detection IDs, with plan restrictions. Our successful-page collector cannot see requests rejected before the Worker. Our offline access ledger helps reconcile supplied evidence; it is not an automatic replacement for that upstream view.
- **GA4:** the [acquisition report](https://support.google.com/analytics/answer/12923437) connects sources/campaigns, sessions, key events and revenue. That outcome workflow, rather than the number of available traffic labels, is a meaningful mainstream benchmark.

More client signals and longer identity histories also carry tradeoffs; matching every competitor field is not automatically desirable.

These are dated, scoped receipts, not current health, a competitor benchmark or cost per reader. The completed availability/performance work is not reopened here.

## Standards: alignment with explicit limits

[RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) is the published HTTP Message Signatures specification. Our verifier explicitly supports an Ed25519/directory-discovery subset, including dictionary and legacy forms; it does not claim full RFC conformance. It records covered components rather than authenticating unsigned UA/resource/purpose claims. Expiry-only replay mitigation and lack of request-body digest validation remain documented boundaries.

[Web Bot Auth protocol draft-01](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/01/), updated October 29, is an active IETF Internet-Draft, not a completed standard. Compatibility needs version-specific vectors; passing our own fixtures does not establish complete interoperability. The [W3C Fetch Metadata document](https://www.w3.org/TR/fetch-metadata/) is a Working Draft about request context, not proof of a human. Our explicit Browser-signals/Unresolved distinction is consistent with that evidence boundary.

There is no single universal web-analytics event model against which missing features can be called standards violations. Campaigns, goals, segments, exports and easy installation are market expectations; protocol conformance, detection quality and product utility require different checks.

## Proposed sequence

| Order | Bounded milestone | Why it comes next | Acceptance evidence |
| --- | --- | --- | --- |
| 1 | Portable Worker reporting starter | Makes the existing advantage usable outside this publication | A separate online install with versioned source/artifact; fresh and upgrade schema paths; reusable cache and explicit cold-fill admission/cost policy; a basic reusable read-only report; documented retention/recovery. Exercise a second site's own task and record setup time, failure recovery, measured reads, and operator understanding |
| 2 | Publisher campaign and outcome contract | Answers which distribution/action produced useful results | Allowlisted bounded campaign labels and a small closed event model for a real action; provenance for browser/server/supplied observations; explicit unknown attribution; automation filtering and event deduplication; no arbitrary query retention or invented cross-day/person joins |
| 3 | Stable evidence query/export interface, then read-only MCP | Lets other agents and tools use the evidence we already have | Versioned bounded outputs, public/private selection, explicit metric meanings and auth where needed; successful independent query/export task before adding an MCP adapter. Do not add an LLM dependency to the collector |
| 4 | Comparative accuracy/interoperability evidence | Supports stronger engineering claims and targeted repairs | A frozen, consent-appropriate labelled fixture set; spoofed/unsigned/ambiguous cases; identical eligible populations and declared abstentions; current protocol vectors; per-tool setup/version recorded. Compare precision/recall/coverage, not raw counts alone |

Milestone 1 should begin by packaging the existing cache contract and a small report. Keep its HTTP policy outside classification/storage semantics; reuse the current implementation rather than invent a new cache. Establish how externally reachable reports admit expensive cold fills: the current local cache and eight-pending limit do not form an account-wide budget. One database per site is enough for the first operator; shared multitenancy can wait for demonstrated need.

The first external trial should ask the operator to explain a traffic change or choose a concrete publishing/distribution action, using both people and agent outcomes. A real install and a supported decision count; a fresh agent-operated fixture, crawler total, or README approval alone does not establish adoption. No outreach, public deployment, npm publication or operator trial was performed by this review.

Continue [observed missing-name leads](../../../packages/blog/drafts/research/analytics-retrospective/139-own-data-user-agent-audit.md) as bounded maintenance when they matter to a report. New detector names, session replay, heatmaps, broad SaaS tenancy and another general detection rewrite have lower current priority than making the existing system independently useful. A demonstrated misclassification or reliability defect can change that order.
