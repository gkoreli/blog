# Product opportunities grounded in the source

Research completed November 6, 2026, Pacific time. Source snapshot: `7559a8551967443f27f5b85393846a0cb8cd3b5e`. This follows the owner's request to explore the code and develop a mix of analytics, publishing and agent-engineering tools connected through the blog.

This is a capability review and a set of proposed offers. It does not accept new implementation work, change the existing product decisions, reopen completed investigations, or establish customer demand. [ADR-0019](../../adr/0019-agentic-engineering-publication-and-analytics-ambition.md) owns the publication/product ambition. The existing [site-check research and delivery](../../../packages/blog/drafts/research/ai-site-audit/02-tools-product-exploration.md) and [ADR-0021](../../adr/0021-tools-and-technical-access-assessment.md) own the four-tool catalog and technical score.

**The practical recommendation is to offer explainable website and agent evidence through small tools, then test recurring reports and checks.** The closest reusable engines already analyze supplied records without another collector, account connection or model call. A general cross-vendor analytics reconciliation service, hosted multi-site analytics, and a generic answer-fidelity evaluator require substantially more new work.

The [normalized local evidence](source-checks.json) records 433 passing analytics tests, 41 passing site-audit tests, one passing research-footprint integration test, ten executed capability probes, and static catalogue coverage. The probes used a transport-denying guard; its counter remained zero. These results establish local behavior under the recorded inputs, not production health, detection accuracy, user value or adoption.

The [November 13 analytics landscape comparison](analytics-industry-comparison-2026-11-13.md) extends this review against six popular open-source projects, GA4 and Cloudflare AI Crawl Control. It recommends portable reporting/installation, followed by publisher campaigns/outcomes and a stable evidence interface. It preserves the distinction between current capability, documented competitor features and proposed implementation; no adoption or comparative accuracy trial was performed.

**Six coherent offers to test**

1. **Private Traffic Audit.** The first operator is a developer with a concrete unexplained traffic pattern and an existing Cloudflare Worker export. Start with that supported shape. Show declarations, unresolved/conflicting cases, source-network context, response status, duplicate/truncated/malformed inputs and the rules/profile applied. The cohort analyzer already exercises the actual metadata/classification functions and emits aggregates. Before accepting public uploads, add a strict size/row envelope, robust schema errors, a user-controlled inclusion policy and a stable output contract; the current research script has no general public-ingestion contract. Other host/log formats need explicit adapters. The recurring trigger is a new reporting period or a changed rule set. Human identification and a claimed detector accuracy advantage are unnecessary promises.

2. **Publisher Regression Checks.** Reuse Page Check and Report Compare to check an explicit URL list against a saved baseline or user-specified expectations. A useful first result identifies an observed generic noindex addition, changed final URL, lost title, missing response, or changed robots rule and supplies the relevant evidence. Schedules, state storage, credentials, notifications, a preview/production pairing policy and a CI wrapper are new work. The existing diff does not compare full HTML/Markdown meaning or prove why a change occurred. A 100-point score only summarizes its six declared tests; CI should use the checks and content assertions relevant to an operator's goal. This is a strong recurring-use hypothesis because publishing changes recur, not a measured retention result.

3. **Discovery Experiment Tracker.** Give a publisher a way to maintain a small frozen question set, import saved observations, distinguish failed/missing/completed runs, and compare only declared-compatible methods. Existing code also keeps reviewed external links/evidence reuse separate from returned search pools. The executed historical pack correctly withheld transitions when response settings differed between runs. A user interface, provider response adapters and convenient capture/export are needed. Automated provider execution and scheduling are additional capabilities with provider costs and separate comparability limits. Call the first product a discovery experiment tracker; the code does not already measure all-model visibility or automatically extract answer citations.

4. **Verification Workbench and Client Reference.** A developer integrating an agent or diagnosing a signed request can inspect declarations, configured verification methods, proof coverage, validity clocks, key/directory availability and bounded replay outcomes. Static catalogue lookup is simpler than arbitrary remote proof resolution. The inspected catalogue contains 63 canonical declaration entries, 17 configured IP feed sources, 22 entries with an IP method, five entries with a documented signing method, and 25 entries with either per-declaration method. The remaining 38 do not have such a configured method; that is not proof no method exists. Some entries are HTTP libraries or policy tokens. Several source pointers are explicitly inherited rather than freshly reviewed. Publish those distinctions and review dates. A public verifier additionally needs a safe resolver/input adapter and a clear supplied-capture trust model. There is no identity advantage from treating a pasted address or header as trusted edge metadata.

5. **Search Evidence Brief.** A publisher supplies one supported Search Console API response, its request metadata and article catalogue. Return page/query mappings, selected-row totals and CTR, URL variants, returned rows without a catalogue owner, and specific rows worth examining. The existing synthetic example reconciles 15 clicks over 455 impressions; those numbers are a fixture, not our search performance. The engine already preserves requested defaults, aggregation, row limit and incomplete-data metadata. Start with a documented JSON import; CSV conventions, pagination joins, period comparisons, OAuth and automatic editorial recommendations require adapters and additional decisions. A report can identify investigation candidates without claiming an unanswered row is zero demand.

6. **Agent Work Receipt.** A developer or writer runs a local command over selected supported agent transcripts. Show included roots/descendants, usage epochs, deduplication, token/cache buckets, the measured cutoff and a reproducible input commitment. The existing integration fixture covers six included session records, recursive descendants, multiple roots, repeated Claude message records and missing usage; it does not read the owner's real session logs. Extract repo-specific prompt/artifact counting and source discovery into optional adapters. Add friendly inputs and a versioned public contract before calling this a general tool. Provider billing rates, subscription charges and task quality are separate from recorded token usage. Local execution is a useful starting form because the relevant inputs are private files.

Each offer can have an article that explains the mechanism, a small tool that applies it, a reproducible example, and an operator decision that tells us what to improve. People and their agents can use the same contracts.

**What the code changes about the business recommendation**

- Free tools can run the pure engines locally or over bounded supplied JSON. This minimizes integration friction and avoids requiring another analytics collector before demonstrating value.
- Hosted work should expose distinct units: inspected records, URL assessments, scheduled runs, or bounded directory/network checks. One HTTP batch is not a useful universal cost unit.
- The present API quota is ten admitted checks per edge source address per UTC day, shared between site audit and current-request inspection. It includes admitted partial/failed checks. It is not a user account, API key, subscription entitlement or paid overage system.
- Changing a constant from ten to a larger number would not implement paid tiers. Key/account ownership, plan policy, revocation, work accounting, fair retry behavior, opt-in storage and operator visibility need deliberate design.
- The inspected route/package source has JSON APIs and local tools, but no product MCP server, API-key billing integration or general customer project model. Those distribution adapters are feasible new work, not existing features.
- Analytics is a private TypeScript workspace package. The fresh schema has no tenant column and the example directs operators to use a separate D1 database per site. A shared hosted analytics service needs an explicit tenancy and data-ownership design.
- The standalone package does not inherit the blog's stats cache. The [October 31 trial](../../../packages/blog/drafts/research/discovery-experiment-02/15-standalone-install-and-operator-decisions.md) demonstrated a local integration and retained an uncached-public-report cost boundary. Its results are historical local evidence, not current customer operating cost.
- Native Cloudflare request metadata is an adapter input, not something a remote caller can recreate by submitting headers. A local Node request with browser-shaped headers and no trusted network context remained unresolved in the executed control.
- The concrete maintenance value is reviewed source/method updates, supported adapters, saved history and useful recurring execution. Hosting a readily copied pure classifier alone does not establish an enduring paid advantage.

**How the blog can organize the mix**

Keep the existing engineering-workbench identity. Start with task paths rather than exposing the internal module graph: check a page; explain a request; analyze an export; compare evidence; measure agent work.

A practical article can link to the exact relevant tool and its fixture. A reference page can expose a versioned client/method record and change history. A downloadable kit can accompany an OSS Radar investigation when it transfers a genuinely useful check. Topic subscriptions could later let readers/agents follow a research question or method update; a feed alone does not establish that workflow.

For acquisition, give a visitor a useful bounded answer with a public URL, sample report or local file. For repeat use, test saved comparisons, publishing runs and periodic exports. For differentiated reference value, maintain actual observations and review provenance. These are proposed distribution and retention mechanisms, not measured effects.

**Validation and remaining limits**

The source was exported before testing so generated outputs could not collide with concurrent development. Existing installed dependency trees were reused read-only; compilation and output stayed in the export. This was not a fresh dependency installation or independent customer setup.

Executed checks:

- `pnpm -C packages/analytics test`: 433 passed, zero failed/skipped.
- `pnpm -C packages/site-audit test`: 41 passed, zero failed/skipped.
- `pnpm -C packages/blog exec node --import tsx --test test/research-footprint.test.ts`: one integration test passed.
- `node packages/blog/scripts/audit-analytics-capabilities.mjs OUTPUT`: static catalogue relationships/counts reconciled.
- The saved discovery CLI produced a JSON report and readable brief from the public October 31 pack without rerunning searches.
- Ten local probes executed actual compiled functions: conflicting declarations; absent trusted edge context; robots path selection; a synthetic noindex regression against a saved report; synthetic search totals and invalid aggregation rejection; synthetic resource accounting; page-event eligibility; historical discovery method mismatch; synthetic Worker-log replay; and local Ed25519 coverage/mutation controls. The [receipt](source-checks.json) preserves their outputs and provenance.

Setup failures were preserved before correction: the exported site-audit package initially had no local dependency link, then passed using the matching existing analytics dependency tree; the tsx CLI's IPC listener was refused by the sandbox, then the footprint test passed through Node's tsx import hook. Neither was treated as a domain-test failure or silently counted as a pass.

No production database query, new provider trial, external outreach, paid API call or independent customer experiment was performed in this source review. Only research documentation and indexes changed; release activation and current production behavior were not assessed. Newsletter/client-observability/benchmark behavior was inspected rather than rerun here. Historical release acceptance remains under its original records.

**Next bounded decision**

Research is complete. A proposed next experiment is to choose one existing engine and one independent operator's real task. Private Traffic Audit tests the most direct analytics need; Publisher Regression Checks test a recurring publishing workflow; Agent Work Receipt tests the broader developer audience. Static Client Reference can provide a small public companion to the existing request tool.

Record the operator's input format, the decision they need, the minimum adapter, actual work cost, and whether they return with fresh input. A working local result, a published wrapper, use by an independent operator/agent, repeat use and a paid commitment are separate outcomes. No experiment or implementation is automatically started by this recommendation.
