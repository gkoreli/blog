# ADR-0016.22: User-Agent claims and platform ambiguity

## Status

Accepted for the November 10, 2026 source iteration. [Worklist 136](../../packages/blog/drafts/research/analytics-retrospective/136-user-agent-trust-and-hardening.md) owns actual checks, delivery and remaining acceptance. Acceptance of this contract does not establish deployment, affected traffic, browser execution or independent adoption.

## Problem

The owner's renewed direction treats the article and analytics library as products and expands the CUBOT example into the full User-Agent trust problem. [The twelve-family evidence map](../../packages/blog/drafts/research/analytics-retrospective/137-user-agent-pain-point-map.md) distinguishes declared text, browser compatibility/privacy policy, independent identity evidence, native capabilities and observed action. A browser-wide default has a defined version/mode population; historical incidents and synthetic counterexamples do not measure current affected-site prevalence.

The code audit reproduces optional diagnostics selecting Edge when Edge and Opera are both present, selecting Android from Android+Windows, and selecting an OS/version from contradictory/reordered claims. Existing capability logic already abstains for conflicting iOS versions. These producers should not offer a more specific OS/browser conclusion than their supplied evidence supports. Reduced/frozen platform versions also need a machine-readable interpretation boundary, not an invented actual OS.

## Decision

### Keep domain values separate

- `user-agent-products` remains the reviewed lexical/URI exclusion dialect. It is not full HTTP product/comment validation or authentication.
- `user-agent-browser` selects a reported browser under explicit compatibility rules. Chrome+Safari and Chrome+Edge/Opera are retained. Simultaneous Edge+Opera cannot choose one vendor by priority. This optional browser selection is distinct from the existing coarse Chromium compatibility-family claim.
- `user-agent-platform` considers every supported OS/version claim, normalizes equivalent numeric forms and retains absent minor versions. Android/Linux and ChromeOS/Linux are compatible generic/specific markers. Incompatible supported families or versions produce unknown selection with explicit conflict, rather than a first-regex winner. Invalid version text remains unresolved; valid-plus-invalid claims conflict.
- `assessUserAgent` is a pure supplied-input domain service joining existing declared-client policy with these values and existing form/preference policy. No Worker context, network, database, attestation or collection is implied.

### Expose the trust boundary in the reusable contract

Export `@gkoreli/analytics/user-agent`, with current profile `user-agent-claims/2026-11-10.2`. The earlier `.1` source/local acceptance remains dated in worklist 138. Distinguish missing/empty/present input, complete catalogue candidates, generic automation declarations, selected/ambiguous browser and platform values, form markers/mobile preference and claimed Fetch Metadata compatibility. HTTP whitespace uses SP/HTAB rather than every Unicode whitespace character. Authentication is always `not-performed`.

Complete Mac OS 10.15.7, Windows NT 10.0, reduced Android 10/K and Safari 26 with iOS 18.6 patterns receive a compatibility-pattern caution. Partial/nearby versions do not qualify solely by major/minor selection. [The own-data audit](../../packages/blog/drafts/research/analytics-retrospective/139-own-data-user-agent-audit.md) reproduces two partial Mac OS 10.15 records receiving an overly broad `.1` caution; `.2` narrows only this pure assessment explanation. Collection, optional diagnostics, form and incoming-request API profiles remain `2026-11-10.1`. This is a match against documented patterns, not proof the sender is a genuine browser or that its hidden OS differs. Do not infer iPad from a Mac-shaped string, infer Windows 11 from NT 10, recover a hidden device model, or treat a missing hint as automation. Flag supplied robots-only policy tokens separately from request identity. No raw header, arbitrary unmatched product, URL, address or contact value is returned.

Keep signature, directory-publisher, trusted-edge network and provider metadata in their existing independent domains. A supplied name is not authenticated by being recognized. Cryptographic validity only covers signed components; policy, purpose, human operation and downstream use need their own evidence. Agents remain legitimate audience at observed stages under ADR-0016.19.

### Update optional diagnostics prospectively

The existing `extractRequestEvidence` uses the same browser/platform values. Advance `REQUEST_EVIDENCE_VERSION` to `2026-11-10.1`; the record shape remains compatible and historical rows retain their stored values/profiles. Optional diagnostics remain under their existing off-by-default scope; no new raw collection is enabled.

The native header check additionally reproduces JavaScript `trim()` promoting NBSP-padded `?1` to a valid mobile preference. Parse only HTTP SP/HTAB padding around the closed boolean. Advance collection, client-form and incoming-request assessment profiles to `2026-11-10.1`; preserve every older recognized form profile and admit the new collection profile in the unchanged Fetch Metadata evidence decoder. Classifier, catalogue, alias codec, form-envelope shape and verifier profiles are unchanged. The current-request API's new version is required for this prospective interpretation change, not for a new raw field or a changed response shape.

### Provide a local product path

Extend the existing User-Agent tool with an inspection command accepting one bounded regular UTF-8 JSON file. Reject unknown fields, invalid encodings and oversized inputs with a fixed error. The file limit is an explicit CLI contract, not silent classifier truncation. A client-provided address, native-bot flag or signature cannot enter through additional JSON fields as trusted evidence. The reusable package remains private TypeScript workspace source; no registry release, hosted multi-site service or customer adoption is implied.

## Sources and alternatives

[RFC 9110 §10.1.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.5) defines products/comments and warns about compatibility masquerading. [Chrome's reduction/Client Hints guidance](https://developer.chrome.com/docs/privacy-security/user-agent-client-hints), [Safari 26's OS freeze](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/) and [tablet desktop mode](https://developer.chrome.com/blog/desktop-mode) establish information limits a parser cannot undo. [WICG UA-CH](https://wicg.github.io/ua-client-hints/) defines mobile preference, privacy/policy-dependent hints and GREASE. These are vendor/specification contracts, not a universal observed device oracle.

Reject first-match selection on conflicting evidence. Reject turning another parser's output or a larger corpus into ground-truth identity. Retain supported coarse compatibility facts separately from unresolved detailed selection. Do not add a device database, high-entropy probes, brand/hint collector, new detector dependency, global runtime input cutoff, migration or raw-log expansion without its own demonstrated need and contract. Existing lexical limitations, legacy compatibility fields and privacy decisions remain explicit.

## Acceptance boundary

Require semantic counterexamples and retained positives, prospective version checks, exact Node/native workerd comparisons, fixture D1 preservation, scoped CLI refusal controls, portable pure-module execution, full analytics tests/types, the existing collector integration, and isolated article/build checks. These establish the specified inputs and implementation. Record bundle cost separately; do not manufacture an accuracy/performance win. Source delivery, production activation, production incidence, independent operator use and repeat adoption remain separate results.
