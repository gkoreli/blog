# ADR-0015.1: Initial substrates, authoring model, and event/pipeline runtime architecture

* **Status:** Proposed
* **Date:** 2026-04-19
* **Owner:** Goga Koreli
* **Decision Type:** Runtime and authoring architecture
* **Supersedes:** None
* **Related:** ADR-0015: Adopt a Pixi-backed custom animation runtime for gkoreli.com

---

## 1. Context

ADR-001 established that the animation system for gkoreli.com will use **PixiJS as a rendering substrate** while preserving a **custom TypeScript runtime and authoring model**.

The publication is intended to function as an authored editorial space where selected essays become **museum pieces**. The runtime therefore needs to support motion and interactivity that are:

* intentional rather than decorative
* semantically meaningful
* performant enough for article-grade interactive scenes
* modular and evolvable
* expressive enough to become a house visual language

The next architectural question is no longer whether to use PixiJS. The next question is:

> What are the initial visual substrates, what authoring model should represent them, and what runtime architecture will allow effects to compose and stack efficiently without collapsing into an unmaintainable scene graph or a globally reactive bottleneck?

This ADR defines the first-generation runtime architecture.

---

## 2. Problem Statement

The runtime needs to satisfy several constraints at once.

### 2.1 Artistic constraints

The system must support recurring visual motifs that can carry semantic meaning across essays, such as:

* ambient drift
* thought fields
* memory zones
* fracture arcs
* text-bound emergence
* pulse and decay

### 2.2 Architectural constraints

The system should be:

* readable and declarative at the authoring layer
* modular and composition-oriented
* practical to implement and evolve
* renderer-isolated
* explicit about performance-sensitive paths

### 2.3 Performance constraints

The system should preserve the highest realistic performance ceiling available under the chosen stack by:

* minimizing unnecessary per-frame allocations
* avoiding broad invalidation graphs
* preferring data-oriented hot paths
* keeping renderer-facing state compact and incrementally updatable
* allowing effects to stack without duplicating simulation work unnecessarily

### 2.4 API constraints

The publication should author scenes in a language that reflects meaning and motion, not raw renderer objects. At the same time, the abstractions cannot become so abstract that they hide expensive work or make optimization impossible.

This ADR must therefore define:

* the initial substrates
* the first authoring model
* the runtime data model
* the folder structure
* starter interfaces
* the composition strategy for stacking effects
* the event/pipeline model used to coordinate transitions efficiently

---

## 3. Decision

We will implement the first-generation runtime around **five initial substrates** and a **hybrid pipeline + event architecture**.

### 3.1 Initial substrates

The runtime will initially support these core substrates:

1. **Field**
2. **Zone**
3. **Emitter**
4. **Material**
5. **Timeline / Modulation**

These substrates are chosen because they are both:

* sufficiently primitive to serve as reusable building blocks
* sufficiently expressive to create article-scale motion language immediately

### 3.2 Runtime architecture

The runtime will use a **hybrid architecture** with two distinct layers:

1. **Data-oriented simulation pipelines** for hot-path work
2. **Event-driven transitions** for coarse semantic state changes

This means:

* per-frame particle simulation and renderer preparation will be handled by systems/pipelines operating over compact runtime data
* enter/exit, threshold, section, and timeline transitions will produce events
* effects will compose through **pipelines over entity sets**, not inheritance chains
* event emission will be selective and coarse-grained, not a universal reactive model

### 3.3 Authoring model

The authoring model will be **declarative** and publication-oriented. Article authors will describe:

* what exists
* where it is emitted from
* which zones matter
* which effects are attached
* how modulation is applied
* how sections or timelines transform the scene

The authoring layer will not expose Pixi objects.

### 3.4 Composition model

Effects will stack through **ordered effect pipelines** operating on runtime channels or traits. The composition style is:

* composition over inheritance
* narrow effect modules
* explicit ordering
* additive or overriding semantics by channel
* event hooks for transitions that change pipeline membership or parameters

---

## 4. Why this architecture

### 4.1 Pure event-driven architecture is not enough

A purely event-driven architecture sounds attractive, but it is not sufficient for hot-path simulation. Particle movement, integration, decay, and renderer state preparation happen continuously every frame. Representing all of that as events would introduce unnecessary overhead and obscure the actual computation model.

### 4.2 Pure reactive/signal architecture is not enough

A universal signal graph would also be the wrong default for the core runtime. It risks broad invalidation and makes per-particle state updates too abstract. Signals remain useful at the orchestration layer, but not as the dominant internal representation for all motion.

### 4.3 Pure inheritance is the wrong composition model

Inheritance-based effect hierarchies would make composition rigid and brittle. The runtime needs small units that can be assembled, reordered, and parameterized without class tree explosion.

### 4.4 A pipeline + event hybrid matches the problem

A pipeline architecture fits continuous simulation. An event architecture fits meaningful state boundaries. Together they enable:

* efficient frame updates
* clear transition semantics
* composable effects
* readable authorship
* room for optimization

## 5. Initial substrates

### 5.1 Field substrate

A field is a spatially queryable influence function that can affect runtime channels such as:

* velocity
* drift direction
* force
* glow intensity
* arc probability
* spawn density
* noise amount
* opacity or disturbance

Initial field types:

* noise field
* attractor field
* repulsor field
* gradient field
* flow field

#### Why included first

Fields create movement and atmosphere with high reuse value. They are central to the publication’s desired visual language, especially for concepts like thought topology, pressure, drift, and clustering.

---

### 5.2 Zone substrate

A zone is a spatial realm or geofence that changes runtime behavior when particles or entities enter, exit, overlap, or remain within it.

Initial zone types:

* rectangle
* circle

Initial zone semantics:

* on enter
* on exit
* while inside
* overlap priority / blending policy

Example uses:

* memory zone → warm persistent glow
* fracture zone → electric instability
* silence zone → dim / stillness
* pressure zone → compression and acceleration

#### Why included first

Zones are one of the most semantically powerful primitives in the system. They convert motion into meaning.

---

### 5.3 Emitter substrate

An emitter is a source that instantiates particles or entities into the runtime.

Initial emitter shapes:

* point
* line
* rectangle
* text outline or text box bounds

Initial emitter controls:

* spawn rate
* burst count
* directionality
* initial velocity distribution
* lifetime range
* material assignment
* tags and channel defaults

#### Why included first

Emitters tie visual systems to article composition and content layout.

---

### 5.4 Material substrate

A material describes how an entity appears and which render-oriented channels it exposes.

Initial material styles:

* solid
* glow
* ember
* electric
* haze / ghost

Initial channels:

* color
* radius / size
* alpha
* emissive amount
* blur amount
* blend mode hint
* trail intensity
* noise amount

#### Why included first

Materials create recognizable house style. They also provide a stable target for effect composition.

---

### 5.5 Timeline / modulation substrate

A modulation source alters parameters over time, scroll, section progress, or interaction state.

Initial sources:

* time
* scroll progress
* section entry/exit
* viewport visibility
* event-driven pulse trigger

Initial targets:

* emitter rate
* field strength
* zone activation
* material channel values
* effect parameters

#### Why included first

Modulation turns static systems into choreography.

---

## 6. First visual motifs enabled by these substrates

The initial runtime should support these first-class scene outcomes:

* ambient drift
* zone-triggered glow
* pulse / breathing modulation
* text-bound particle emergence
* sparse electric accents

These are considered enough to ship the first meaningful article pieces.

## 7. Architectural model

### 7.1 Core runtime layers

The runtime is divided into these layers:

1. **Authoring layer**
2. **Compilation / scene assembly layer**
3. **Simulation layer**
4. **Event layer**
5. **Renderer adapter layer**

### 7.2 Layer responsibilities

#### Authoring layer

Defines scenes declaratively using publication-oriented primitives.

#### Compilation / scene assembly layer

Transforms authoring declarations into runtime plans:

* allocates stores
* binds emitters to materials
* constructs pipeline graphs
* resolves zones and modulation links
* prepares renderer-facing registries

#### Simulation layer

Per-frame execution over runtime stores:

* spawn
* integrate
* query zones
* update effect channels
* decay
* compact or recycle dead particles

#### Event layer

Produces and dispatches coarse runtime events such as:

* zone enter
* zone exit
* section enter
* section exit
* burst trigger
* material threshold reached

#### Renderer adapter layer

Maps runtime state to Pixi-backed render instructions and cached objects.

---

## 8. Composition strategy for effects

### 8.1 Effects are pipelines, not subclasses

Effects are defined as small modules that read from and write to entity channels.

Example conceptual effect modules:

* `applyFieldVelocity`
* `enterZoneGlow`
* `decayAlpha`
* `pulseRadius`
* `electricArcChance`
* `trailPersistence`

Effects may be attached to:

* a particle stream
* a material instance
* a zone binding
* a scene section

### 8.2 Effects operate on channels

Each runtime entity exposes channels such as:

* `position`
* `velocity`
* `life`
* `age`
* `alpha`
* `radius`
* `color`
* `emissive`
* `noise`
* `trail`
* `flags`

Effects are allowed to:

* add to a channel
* multiply a channel
* override a channel
* set or unset flags
* emit coarse events

### 8.3 Effect order is explicit

Effect order affects the final result and therefore must be explicit, stable, and inspectable.

For example:

1. apply field influence
2. integrate velocity
3. compute zone occupancy changes
4. apply enter/exit transitions
5. apply per-frame in-zone modifiers
6. apply pulse modulation
7. apply decay
8. prepare renderer channels

This is a pipeline, not an inheritance hierarchy.

### 8.4 Event-triggered effect membership

Some effects should only become active after an event. Example:

* particle enters `memory` zone
* event emitted
* warm glow transition starts
* electric instability disabled
* persistence increased

This should not require allocating new entity objects. It should update runtime flags, effect bindings, or parameter references.

## 9. Performance model

### 9.1 Data-oriented hot path

The performance-critical runtime should favor compact stores and predictable iteration.

Suggested defaults:

* struct-of-arrays style for large particle sets where justified
* pooled IDs or slots
* sparse activation flags
* no per-frame object allocation in hot loops
* event queues backed by reusable arrays

### 9.2 Coarse event model

Events should be used only when they represent semantically meaningful transitions. They are not a substitute for every numerical update.

Good event examples:

* zone enter
* zone exit
* timeline threshold crossed
* burst requested
* viewport suspended/resumed

Bad event examples:

* particle moved by 0.1px
* alpha changed by 0.02 this frame
* glow intensity updated every tick

### 9.3 Pipeline compilation

The runtime should compile authoring declarations into executable plans ahead of frame execution where possible.

Compiled plans may include:

* ordered effect chains
* filtered entity sets
* zone-to-effect bindings
* modulation routing tables
* renderer channel mapping tables

### 9.4 Readability versus hidden cost

Declarative authoring is required, but runtime behavior must remain inspectable. The system should make it possible to understand:

* which effects run on which entities
* in what order
* on which channels
* under which event conditions

## 11. Starter data model

The starter data model is intentionally narrow.

### 11.1 Core IDs

```ts
export type SceneId = string;
export type ParticleSystemId = string;
export type ZoneId = string;
export type EmitterId = string;
export type MaterialId = string;
export type EffectId = string;
export type TimelineId = string;
```

### 11.2 Runtime particle store

For hot paths, large particle sets should prefer struct-of-arrays.

```ts
export interface ParticleStore {
  capacity: number;
  count: number;

  x: Float32Array;
  y: Float32Array;
  vx: Float32Array;
  vy: Float32Array;

  age: Float32Array;
  life: Float32Array;

  radius: Float32Array;
  alpha: Float32Array;
  emissive: Float32Array;
  noise: Float32Array;
  trail: Float32Array;

  colorR: Float32Array;
  colorG: Float32Array;
  colorB: Float32Array;

  materialIndex: Uint16Array;
  flags: Uint32Array;
  alive: Uint8Array;
}
```

### 11.3 Zone definitions

```ts
export type ZoneShape =
  | { kind: 'rect'; x: number; y: number; width: number; height: number }
  | { kind: 'circle'; x: number; y: number; radius: number };

export interface ZoneDefinition {
  id: ZoneId;
  shape: ZoneShape;
  tags?: string[];
  priority?: number;
```

```ts
export interface OccupancyStore {
  currentMask: Uint32Array;
```

A bitmask is sufficient for the first generation if the active zone count remains intentionally small.

### 11.5 Emitter definitions

## 13. Recommended authoring model

The authoring model should be declarative and scene-oriented.

Example target shape:

```ts
createScene('topologies-of-thought')
  .material('thought', glowMaterial({
    color: '#7bb8ff',
    radius: 2.5,
    emissive: 0.4,
  }))
  .zone('memory', rectZone({
    x: 240,
    y: 120,
    width: 260,
    height: 180,
  }))
  .emitter('hero-title', textBoxEmitter({
    x: 80,
    y: 100,
    width: 520,
    height: 90,
    rate: 24,
    material: 'thought',
  }))
  .system('nodes', particles({
    emitter: 'hero-title',
    material: 'thought',
    pipes: [
      pipe('ambient-drift', [
        applyFieldVelocity('hero-noise'),
        decayAlpha({ rate: 0.08 }),
      ]),
      pipe('memory-glow', [
        onEnterZone('memory', add('emissive', 0.35)),
        insideZone('memory', multiply('radius', 1.2)),
      ]),
      pipe('pulse', [
        timelinePulse('hero-scroll', 'alpha', { min: 0.8, max: 1.0 }),
      ]),
    ],
  }));
```

### Why this model

This model is:

* readable
* semantically expressive
* composable
* close to the publication’s language
* still compilable into efficient execution plans

## 14. Pipeline execution model

### 14.1 High-level frame order

A first-generation frame may execute like this:

1. update modulation sources
2. process scheduled bursts / triggers
3. run spawn system
4. run field influence system
5. run integration system
6. run zone occupancy system
7. enqueue zone enter/exit events
8. run transition effects bound to events
9. run continuous effect pipelines
10. run decay / cleanup
11. prepare render channels
12. render

### 14.2 Why two phases for effects

There should be a distinction between:

* **transition effects**: triggered by events
* **continuous effects**: executed every frame under a condition

This keeps the runtime explicit and avoids simulating transition logic as if it were just another always-on modifier.

### 14.3 Effect stacking semantics

Each pipeline stage must define whether it:

* adds
* multiplies
* overrides
* latches a flag
* emits an event

This avoids ambiguity and makes order inspectable.

## 16. What not to do

The first generation should explicitly avoid:

* general-purpose ECS maximalism
* inheritance-heavy effect hierarchies
* global immutable store updates for hot paths
* per-particle signal graphs
* exposing Pixi classes in authoring APIs
* abstracting so aggressively that execution order becomes opaque

The runtime should remain narrow, inspectable, and optimized for publication scenes.

---

## 17. Consequences

### Positive consequences

* effect composition remains modular and ordered
* transition semantics remain expressive without infecting hot loops
* the authoring model stays readable and publication-oriented
* runtime hot paths can be optimized independently of authoring ergonomics
* Pixi remains replaceable in principle

### Negative consequences

* the compile/runtime split adds conceptual weight
* effect pipelines need discipline to avoid order confusion
* some duplicated concepts exist between authoring declarations and compiled runtime plans
* the event model needs careful scope control to avoid expansion into a general reactive system

## 19. Decision Summary

For the first generation of the gkoreli.com animation runtime, we will:

* start from five initial substrates: **Field, Zone, Emitter, Material, Timeline/Modulation**
* use a **hybrid pipeline + event architecture**
* keep hot-path simulation **data-oriented and incremental**
* use **ordered, composable effect pipelines** rather than inheritance hierarchies
* use events only for **coarse semantic transitions**
* expose a **declarative authoring model** that compiles into runtime execution plans
* isolate PixiJS behind a renderer adapter layer
* prefer narrow, publication-specific primitives over general-purpose engine breadth

This design maximizes the combination of:

* performance potential
* practicality
* readability
* declarative expressiveness
* modularity
* composition over inheritance

while preserving the publication’s long-term ability to evolve into a more custom visual system if the work demands it.

---

## 20. Guiding Statement

> The runtime should read like authored editorial composition at the surface, execute like a disciplined simulation pipeline underneath, and remain narrow enough that every primitive earns its existence through real published work.
