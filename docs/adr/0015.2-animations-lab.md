# ADR-003: Animations Lab design for gkoreli.com

* **Status:** Proposed
* **Date:** 2026-04-19
* **Owner:** Goga Koreli
* **Decision Type:** Product / experience / runtime validation
* **Related:**

  * **ADR-0015**: Adopt a Pixi-backed custom animation runtime for gkoreli.com
  * **ADR-0015.1**: Initial substrates, authoring model, and event/pipeline runtime architecture

---

## 1. Context

The animation system should not be born inside production essays first.

That would be premature and messy.

Before the runtime earns a permanent place in the publication, it needs a **dedicated environment** where visual substrates, effect composition, interaction behavior, and performance characteristics can be explored in a disciplined way.

That environment is the **Animations Lab**.

The Animations Lab is not a random playground and not a generic demo gallery.

It is:

* a **design lab**
* a **runtime validation surface**
* a **performance testbed**
* a **visual language incubator**
* a **museum backroom** where future exhibition pieces are developed and judged

The lab must help answer:

* which substrates are actually foundational?
* which combinations feel coherent with the gkoreli brand?
* which interactions are expressive without being gimmicky?
* which effects deserve promotion into the core library?
* how far can the runtime be pushed while staying smooth and elegant?

---

## 2. Problem Statement

The publication needs a first-class experimentation surface that can:

1. **show live animation experiments**
2. **let the user inspect and manipulate them**
3. **explain what each experiment is trying to prove**
4. **make performance and system behavior visible**
5. **preserve the editorial / authored tone of the site**
6. **feel like part of the publication brand**, not a bolted-on dev tool

The lab must balance two competing needs:

* **artistic presentation**
* **engineering instrumentation**

If it leans too far toward presentation, it becomes decorative and vague.

If it leans too far toward instrumentation, it becomes a sterile internal tool.

The right design should feel like:

> an editorially designed, visually rich, technically honest experimentation chamber.

---

## 3. Decision

We will build an **Animations Lab page** with the following characteristics:

### 3.1 Core design direction

The lab will be:

* **alive**
* **interactive**
* **visually rich**
* **editorial**
* **technical**
* **highly legible**
* **brand-aligned**
* **performance-aware**

### 3.2 Structure

The page will consist of:

* a **lab shell**
* an **experiment registry**
* a **main live canvas stage**
* a **context panel** explaining each experiment
* a **control panel** for interaction
* a **metrics/debug layer**
* an optional **config/code preview section**

### 3.3 First release scope

The first release of the Animations Lab will contain **4 experiments**:

1. **Experiment 01 — Ambient Drift**
2. **Experiment 02 — Memory Zone**
3. **Experiment 03 — Text Emergence**
4. **Experiment 04 — Fracture Pulse**

These are the right first four because together they validate the first-generation substrates from ADR-002:

* field
* zone
* emitter
* material
* modulation
* transition/event pipeline

### 3.4 Standard experiment anatomy

Every experiment will be documented and presented with the same information blocks:

* **Label / title**
* **Quick explanation**
* **Distilled**
* **Rationale**
* **Insights**
* **What this proves**
* **Interactive controls**
* **Debug toggles**
* **Performance metrics**

This gives the lab a disciplined shape.

---

## 4. Goals

### 4.1 Primary goals

The lab should:

* validate the animation runtime with real moving scenes
* identify which primitives deserve promotion into the core library
* cultivate the publication’s house motion language
* let experiments be observed, tuned, and stress-tested
* show that the animation work belongs to the brand and editorial voice

### 4.2 Secondary goals

The lab should also:

* be aesthetically compelling enough to invite exploration
* be clean enough to share publicly
* be modular enough to add more experiments later
* be technical enough to guide implementation decisions

---

## 5. Non-goals

The first version of the lab is **not** trying to be:

* a generic shader toy
* a Storybook clone
* a general-purpose editor
* a visual node graph tool
* a public animation framework site
* a giant parameter jungle
* a replacement for article-specific scenes

This is a **focused laboratory**, not a productized animation IDE.

---

## 6. Brand and visual identity alignment

The lab should reflect the existing identity of gkoreli.com.

### 6.1 Brand traits to preserve

The publication already reads as:

* editorial
* restrained
* thoughtful
* engineered
* authored
* minimal but not empty
* technical but not cold

The lab must preserve those traits.

### 6.2 Motion identity

The motion language should feel:

* **alive**, not noisy
* **intentional**, not overproduced
* **conceptual**, not VFX-for-VFX’s-sake
* **rich**, but controlled
* **layered**, not cluttered
* **cool to observe**, but still serious

### 6.3 Interface tone

The interface should feel like:

* an instrument panel
* a studio console
* an editorial research notebook
* a quiet but potent systems space

### 6.4 Visual styling guidelines

Recommended styling directions:

* dark or deep-neutral background canvas surfaces
* restrained bright accents
* subtle grid / frame / rule lines
* editorial spacing
* crisp typography
* quiet UI chrome
* minimal color palette with one or two accent families

### 6.5 Accent palette direction

A first-pass motion palette could be built around:

* **cool thought-blue**
* **warm memory-amber**
* **fracture-violet / electric-cyan accents**
* **soft neutral haze**

This creates semantic contrast:

* blue = thought / drift / analysis
* amber = memory / warmth / persistence
* violet-cyan = rupture / instability / voltage

## 8. Standard anatomy for each experiment

Each experiment page/panel should use the same narrative structure.

### 8.1 Label

Example:

* `Experiment 01`
* `Ambient Drift`

### 8.2 Quick Explanation

A fast, plain-English explanation.

Example:

> A baseline particle field driven by a soft noise field. This establishes the default motion grammar of the system.

### 8.3 Distilled

A tighter one- or two-line statement of what matters.

Example:

> Drift is the base life-sign of the runtime. If this doesn’t feel elegant, nothing above it will.

### 8.4 Rationale

Why the experiment exists.

Example:

* validates field substrate
* sets the visual baseline
* benchmarks the simplest always-on scene

### 8.5 Insights

What the experiment is likely to reveal.

Example:

* too much motion makes it feel generic
* density interacts heavily with elegance
* subtle pulse may help the scene feel alive

### 8.6 What this proves

Direct validation criteria.

Example:

* the field substrate works
* the renderer is smooth
* the baseline motion matches the publication tone

### 8.7 Controls

Grouped and labeled.

### 8.8 Debug toggles

Optional, but visible.

### 8.9 Metrics

Always present.

# Experiment 01 — Ambient Drift

### Label

**Experiment 01**
**Ambient Drift**
*Tagline: “The default breath of the system.”*

### Quick Explanation

A restrained particle field animated by a soft flow/noise field. This is the baseline motion substrate from which richer scenes will grow.

### Distilled

This experiment answers one question:

> Can the runtime produce quiet life without spectacle?

If the answer is no, the rest of the system will feel forced.

### Rationale

Ambient drift should become one of the publication’s foundational motion motifs.

This experiment exists to validate:

* particle store
* field substrate
* material substrate
* baseline renderer path
* performance baseline
* overall motion taste

### Insights we want

* What particle density feels alive vs cluttered?
* How subtle can field motion be while still reading?
* Does pulse help or harm?
* What color/material treatment feels most “gkoreli”?

### What this proves

* the field substrate works
* the base motion language feels coherent
* the runtime can render a continuous ambient scene cleanly
* the page can feel alive without becoming noisy

### Primary substrates used

* **Emitter**
* **Field**
* **Material**
* light **Timeline/Modulation**

### Suggested visuals

* sparse particle cloud
* cool thought-blue palette
* subtle pulse in opacity or radius
* no zone yet
* no violent accents

### Interactive controls

**Motion**

* particle count
* drift strength
* field scale
* field speed
* damping

**Material**

* radius
* alpha
* emissive amount
* pulse amount

**Performance**

* max particles stress mode
* pause / resume
* reset scene

### Debug toggles

* show field vectors
* show bounds
* show particle centers
* show debug text

### Success criteria

* looks elegant at low density
* remains smooth as particle count scales
* feels branded and publication-appropriate
* makes you want to keep staring at it

# Experiment 02 — Memory Zone

### Label

**Experiment 02**
**Memory Zone**
*Tagline: “Motion gains meaning when space changes behavior.”*

### Quick Explanation

Particles drift through a field, but a defined zone transforms them. Inside the zone, particles warm up, glow, and slightly persist longer. Outside, the effect decays.

### Distilled

This is the first semantic animation.

> Space is no longer neutral. It has meaning.

### Rationale

This experiment validates the core geofence / zone idea that likely becomes a signature capability of the library.

It tests:

* zone substrate
* enter / exit events
* transition effect stacking
* in-zone continuous effects
* parameter decay

### Insights we want

* Does a semantic zone feel intuitive and emotionally legible?
* What is the right decay timing on exit?
* Should overlapping zones blend, override, or prioritize?
* Is the glow effect strong enough to read without becoming cheesy?

### What this proves

* the zone model is worth keeping
* event-triggered transitions can stack cleanly
* motion can carry narrative meaning
* the runtime can separate transition logic from continuous simulation

### Primary substrates used

* **Field**
* **Zone**
* **Emitter**
* **Material**
* light **Timeline/Modulation**

### Suggested visuals

* cool ambient particles outside the zone
* warm amber region inside the zone
* gentle halo growth on entry
* slight persistence increase inside the zone
* soft decay on exit

### Interactive controls

**Zones**

* zone x / y
* zone width / height
* zone enable / disable
* zone warmth intensity
* zone persistence multiplier

**Effects**

* glow intensity
* radius multiplier
* decay speed
* blending mode

**Motion**

* drift speed
* particle count
* emitter rate

### Debug toggles

* show zone boundary
* show in-zone occupancy count
* show enter/exit event count
* show particle trails

### Success criteria

* effect reads immediately
* transition feels meaningful
* no visible jank when particles cross zone boundaries
* architecture feels natural, not hacked

# Experiment 03 — Text Emergence

### Label

**Experiment 03**
**Text Emergence**
*Tagline: “The writing itself becomes a source of motion.”*

### Quick Explanation

Particles are emitted from a title region or text-defined bounds, then loosen into drift or structure. This ties the runtime directly to editorial composition.

### Distilled

This experiment tests whether the animation system actually belongs to the publication.

> If motion can emerge from language, the engine has found its home.

### Rationale

This is the first experiment that directly binds the animation library to the content system and brand identity.

It validates:

* text-bound emitter behavior
* publication-aware composition
* title/hero relationship
* motion as editorial extension, not decoration

### Insights we want

* Should particles emit from exact glyph outlines later, or are text bounds enough for now?
* How dense should emission be to preserve legibility?
* How much motion should originate from the title vs ambient background?
* Does this feel authored or gimmicky?

### What this proves

* the engine belongs on gkoreli.com
* animation can be anchored to content primitives
* the publication can produce “museum piece” hero moments
* the current authoring model can express content-bound scenes cleanly

### Primary substrates used

* **Emitter**
* **Field**
* **Material**
* optional **Zone**
* optional **Timeline/Modulation**

### Suggested visuals

* title-bound spawn area
* particles peel away from the title
* cool thought-blue or mixed blue/amber palette
* maybe a mild pulse or gentle directional drift
* optional subtle zone near the center of the hero

### Interactive controls

**Emitter**

* source region x / y / width / height
* emission rate
* burst mode
* initial speed
* spread

**Text motion**

* emergence intensity
* initial upward drift
* loosen time
* retention near source

**Visual**

* title-bound opacity
* particle size
* emissive
* color mode

### Debug toggles

* show text emitter bounds
* show spawn points
* show source anchors
* show section bounds

### Success criteria

* it feels integrated with editorial layout
* it enhances, not competes with, the title
* it is beautiful even when restrained
* it clearly belongs to the publication’s identity

# Experiment 04 — Fracture Pulse

### Label

**Experiment 04**
**Fracture Pulse**
*Tagline: “A restrained rupture: intensity used as punctuation.”*

### Quick Explanation

A controlled high-energy experiment where a pulse or threshold event causes sparse fracture-like electric accents, brief instability, or energized motion bursts.

### Distilled

This experiment is about controlled violence.

> The system needs a way to break composure without losing taste.

### Rationale

The first three experiments are all quiet and atmospheric. This one introduces contrast and lets the runtime prove it can handle moments of energy and tension without turning into generic VFX.

It validates:

* event-triggered punctuations
* burst logic
* modulation thresholds
* sparse high-energy effect layering
* temporary material changes

### Insights we want

* How much high-energy motion is too much?
* Should fracture effects be arcs, pulses, or shader distortion first?
* How sparse must the accents be to remain elegant?
* Does the runtime transition cleanly between calm and active states?

### What this proves

* the library can support dynamic contrast
* the event architecture can drive momentary effect bursts
* your future article climaxes have a visual language
* the system can do more than “pretty drifting particles”

### Primary substrates used

* **Zone** or **Timeline/Modulation**
* **Material**
* **Effect pipeline**
* **Event triggers**

### Suggested visuals

* mostly calm field
* occasional pulse through a threshold region
* brief electric-cyan / violet fracture accents
* short trails or arc flashes
* quick reset to calm

### Interactive controls

**Pulse**

* trigger pulse
* pulse interval
* pulse duration
* pulse amplitude

**Fracture**

* arc chance
* burst count
* instability amount
* trail amount
* cooldown

**Scene**

* calm background density
* contrast strength
* reset

### Debug toggles

* show trigger zone
* show event timeline
* show active fracture count
* show burst markers

### Success criteria

* feels sharp and exciting without being tacky
* remains sparse and intentional
* event/pipeline architecture handles bursts cleanly
* gives the system expressive range

## 12. Proper labeling system

Each experiment should have a structured label.

### 12.1 Visible label format

Use:

* experiment number
* title
* short concept line
* substrate tags

Example:

**Experiment 02 — Memory Zone**
*Zone / Event / Glow / Decay*

### 12.2 Status labels

Use one of:

* `draft`
* `stable`
* `promoted`

Meaning:

* **draft**: still exploratory
* **stable**: repeatable and coherent
* **promoted**: worthy of core library inclusion

### 12.3 Naming principles

Names should be:

* conceptual
* short
* memorable
* aligned with publication tone

Good:

* Ambient Drift
* Memory Zone
* Text Emergence
* Fracture Pulse

Bad:

* Particle Demo 1
* Glow Test
* Noise Experiment
* Effect Showcase

## 13. Distilled block design

The **Distilled** section should become a visual signature of the lab.

Purpose:

* reduce the experiment to its central thesis
* give it editorial weight
* avoid drowning the user in technical detail

Recommended design:

* bold heading: `DISTILLED`
* 1–3 lines only
* slightly larger type or framed callout
* designed like a “field note” or “editor’s note”

Example:

> Motion becomes meaningful when space changes its rules.

This section helps the lab feel like a publication artifact, not just a test harness.

---

## 14. Insights block design

The **Insights** block should be written in bullets.

Purpose:

* capture what the experiment is teaching
* document emerging rules of the runtime

Example bullet style:

* Low-density drift feels more premium than high-density drift.
* Warm transitions read better with longer decay than instant switch.
* Text-linked motion feels strongest when the source remains legible.

This will become valuable historical documentation as the system evolves.

## 15. Page-level layout design

## 15.1 Final layout decision

The first version should use a **three-column desktop layout**:

* **left rail**: experiment selector
* **center**: live stage
* **right rail**: explanation + controls + metrics

This is the best fit because it keeps:

* navigation visible
* stage dominant
* context and interaction close at hand

### Desktop layout priorities

1. stage is the hero
2. context is always visible
3. controls don’t bury the visual
4. experiment switching is effortless

## 18. Promotion logic

The lab must help decide what deserves promotion into the engine.

### 18.1 Promotion rule

A primitive or effect should be promoted from “experimental” into “core” only if:

* it works well in **at least two experiments**
* it performs acceptably
* it aligns with the brand
* it feels composable
* it survives parameter variation

### 18.2 Promotion examples

Likely early promotions:

* ambient drift
* zone-triggered glow
* text-bound emergence
* soft pulse modulation

## 20. Decision Summary

We will build the Animations Lab as a **public-facing but technically honest experimentation surface** for the gkoreli animation runtime.

The lab will:

* reflect the publication’s editorial and engineered identity
* use a **three-column desktop layout**
* present **4 initial experiments**
* give each experiment a clear explanatory structure
* expose meaningful interaction controls
* include performance and debug instrumentation
* function as the proving ground for which substrates and effects deserve a place in the library and, eventually, the museum

The first four experiments are:

1. **Ambient Drift**
2. **Memory Zone**
3. **Text Emergence**
4. **Fracture Pulse**

These are the right first experiments because they are:

* visually rich
* interactive
* conceptually distinct
* aligned with your brand
* foundational to the runtime
* strong enough to justify the library if executed well
