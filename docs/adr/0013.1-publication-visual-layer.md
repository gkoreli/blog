# ADR-0013.1: Publication Visual Layer — Front Page, Section Rooms, Frames

## Status

Proposed — 2026-04-19. Extends ADR-0013.

---

## Context

ADR-0013 shipped the foundation: `section` on every post, sidebar nav rail, four section archive pages, section label on every post page, co-located component CSS. The shell is stable.

But it is worth being explicit about what this site actually is, because that shapes every decision in this phase.

This is not an engineering blog. It started there — minimal, stripped-down, one feed, flat structure. That was a starting point, not a destination. Seven posts in and there were already three distinct voices: personal essays, OSS analysis, engineering deep-dives. A custom animation per post. A neural network canvas. A topology visualisation. A glass panel design language. Procrastination as literature. Each post already treated as a distinct art object.

**The right model is: a personal publication. A one-person magazine. A living museum.**

If this were run by a team of fifteen — a designer, editors, section leads — nobody would question the variety. They would call it "editorial range." The same is valid with one author. The number of people making something does not determine whether it is allowed to have sections, rooms, and editorial identity.

The law that says "a solo blog must be minimal and uniform" is not a law. It is an aesthetic inherited from startup culture and engineering minimalism pretending to be universal taste.

The actual design problem is not: *how do I limit this?*

The actual design problem is: **how do I make abundance feel intentional?**

That is what this ADR solves.

### The principle

**Stable shell, expressive interior.**

The publication shell — navigation, section labels, archive logic, metadata, wayfinding — is DRY infrastructure. It stays consistent. It orients the reader.

The post body is free. Every post can be its own art object: custom preamble, custom animation, custom layout, non-DRY visual language, its own atmosphere. This is not a problem to be engineered away. It is the point.

DRY applies to orientation. It does not apply to creative expression.

### What is still missing

| Layer | Current state | Missing |
|-------|--------------|---------|
| **Homepage** | Flat chronological feed | Publication front page: masthead, featured, section previews |
| **Section archive pages** | Functional but visually generic | Per-section room treatment — each section feels like its own department |
| **Section mood** | All sections share identical visual treatment | Subtle differentiation via `data-section` scoping |
| **Frames** | Section and archive exist, no posts yet | Image-first post layout, `images[]` rendering |
| **Featured post** | `featured: true` in `PostMeta`, never read | Selection logic, homepage spotlight slot |
| **Post pages** | `data-section` not yet on wrapper | Section mood scope missing at post level |

## Decision

### 1. `data-section` on the layout wrapper — every page, not just archives

Add `data-section` to the outermost layout div in `pageShell()` whenever a section is known:

```html
<!-- section archive page -->
<div class="layout" data-section="essays">

<!-- post page -->
<div class="layout layout-post" data-section="engineering">
```

This is the single mechanism for all section-specific CSS. No separate CSS file per section. No per-section TypeScript branching. The attribute is on every page where a section applies. Section mood CSS is authored under that attribute — in the relevant component's `.css` file, or in a standalone `src/styles/section-moods.css` for cross-component mood rules:

```css
[data-section="essays"] .post-content {
  /* more spacious, quieter, softer */
}
[data-section="oss-radar"] .section-archive {
  /* serialised, issue-number feel */
}
[data-section="frames"] .post-content {
  /* minimal text, image rhythm */
}
```

Post pages get `data-section` too. The sidebar nav is hidden on post layouts per existing CSS, but the attribute is present — so post body typography, spacing, and atmosphere can be tuned per section without any TypeScript changes.

### 2. Section accent tokens

Named design tokens, not magic values. Each section gets a CSS custom property in `tokens.css`:

```css
:root {
  --section-essays:      hsl(35, 70%, 55%);
  --section-engineering: hsl(210, 70%, 55%);
  --section-oss-radar:   hsl(155, 60%, 45%);
  --section-frames:      hsl(280, 40%, 55%);
}
```

Actual values are the designer's call — these are architectural placeholders. The decision is: named tokens at the root level, not literals scattered across scoped rules. Used by section labels, archive headings, section block accents on the homepage. Not used to retheme the shell.

### 3. Homepage — publication front page

The homepage is not a feed. It is the front page of a publication. A reader arriving for the first time should immediately understand: there are rooms here, here is what each room is, here is what is new.

**Structure:**

```
[ Masthead ]
  Publication name, authorial voice statement, inline project links

[ Featured ]
  One strong piece — manually flagged via `featured: true`, or most recent post as fallback

[ Essays ]         2 recent → "View all Essays →"
[ Engineering ]    2 recent → "View all Engineering →"
[ OSS Radar ]      Latest issue + issue number → "View all issues →"
[ Frames ]         Latest entry with lead image → "View all Frames →"
```

**Featured selection:**

```typescript
const featured = sortedPosts.find(p => p.featured) ?? sortedPosts[0]!;
```

One slot. Never empty. No CMS needed — a frontmatter flag and a redeploy is fine.

**Project links** move to inline text in the masthead. Not cards, not a sidebar. Present but understated — they do not compete with editorial content.

**Section blocks** are a new `HomeSectionBlock` component. Each block receives: section, posts (up to N), "view all" href. The TypeScript component API is minimal and stable. The designer controls everything visual via the co-located CSS — including whether Essays blocks feel spacious, OSS Radar blocks feel serialised, Frames blocks feel cinematic.

If a section has no posts yet (Frames at launch), the block renders nothing. No empty state, no placeholder — the section simply does not appear on the homepage until there is something to show.

### 4. Section archive rooms

Each archive page already has `data-section` and renders heading + description + post list. What changes is the post list treatment per section — pure CSS work, no TypeScript changes:

| Section | Room feel |
|---------|----------|
| **Essays** | Generous spacing, text-led, title + date + description |
| **Engineering** | Denser, tags inline, structured |
| **OSS Radar** | Issue badge + title + date, serialised rhythm |
| **Frames** | Lead image thumbnail, cinematic spacing |

The rooms are differentiated through CSS alone. The architecture (same HTML, same component, same route structure) stays consistent. The atmosphere is what changes.

### 5. Frames layout — `layout: 'frames'`

Frames posts use a new `'frames'` layout mode:

```typescript
layout: z.enum(['default', 'immersive', 'frames']).default('default'),
```

A Frames post is primarily visual. The `images[]` field from frontmatter renders as the primary content, before the article body. A new `FramesGallery` component handles the image sequence. The text body is minimal — impressionistic, caption-like, present-tense.

```
[ Lead image or image sequence ]
[ Captions ]
[ Short article text ]
```

Images live in `public/images/frames/` as static assets. No image transformation pipeline in this phase.

Interactive behaviour (lightbox, scroll-driven gallery) is deferred until the designer specifies. A `frames.js` client entry can be added to `ESBUILD_ENTRIES` at that point — the pattern is already established by `immersive.js`.

### 6. The post body is free

This is not just a consequence — it is an architectural decision worth stating explicitly.

The shell enforces: section identity, wayfinding, metadata, consistent nav. These are non-negotiable.

The post body enforces: nothing. Every post is allowed to have a unique preamble animation, a custom visual system, a non-standard layout, its own atmosphere, its own rhythm. Components can be used or not used. DRY does not apply inside the art. The `immersive` layout exists specifically to give individual posts a blank canvas. The `preamble()` export exists specifically to break the page open before the content begins.

This freedom is the point. The shell is what makes that freedom legible rather than chaotic.

### 7. Designer / engineer boundary

| Designer owns | Engineer owns |
|---------------|--------------|
| All `src/components/**/*.css` | All `src/components/**/*.ts` |
| Token values in `tokens.css` | Token names in `tokens.css` |
| Section mood rules under `[data-section]` | `data-section` attribute on the shell |
| Frames layout visual treatment | Frames layout mode + `FramesGallery` component structure |
| `HomeSectionBlock` visual design | `HomeSectionBlock` TypeScript API |
| Section room atmospheres | Section route and data structure |

The engineer builds structure. The designer builds atmosphere. They compose without blocking each other, because the CSS co-location architecture (ADR-0013 Phase 0) was built specifically for this handoff.

## Consequences

### What changes

| File | Change |
|------|--------|
| `src/templates/page.ts` | Add `data-section` to layout wrapper when section is known |
| `src/lib/frontmatter.ts` | Add `'frames'` to layout enum |
| `src/templates/index.ts` | Full rewrite — publication front page |
| `src/components/home-section-block/` | New component (TS + CSS) |
| `src/components/frames-gallery/` | New component (TS + CSS) |
| `src/styles/tokens.css` | Add `--section-*` accent tokens |
| `src/pipeline/build.ts` | `frames.js` entry if interactive Frames behaviour is added |

### What does not change

- The post body is free — this phase does not constrain it
- Post file format (`.md` and `.ts`)
- Custom preamble pattern
- `immersive` layout
- Animation and canvas system
- Section archive routes (already built)
- Section label component (already built)
- Co-located CSS architecture (already built)

### Risks

- **Frames at launch has no posts:** Homepage Frames block must render nothing gracefully. Not an error, not a placeholder — just absent.
- **Section mood CSS written against wrong HTML structure:** CSS that assumes markup the TypeScript component doesn't generate will silently do nothing. Mitigated by pairing `.ts` and `.css` review together.
- **Featured slot abuse:** If `featured: true` is set on multiple posts, `find()` returns the first match in sort order. That is fine — but there is only ever one spotlight.

---

## The principle in two sentences

The publication shell is the museum building: stable, orienting, consistent. The post body is the exhibition room: free, expressive, non-DRY, allowed to be a one-off every time.
