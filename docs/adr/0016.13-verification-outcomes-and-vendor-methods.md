# ADR-0016.13: Distinguish verification failures and documented vendor methods

## Status

Active implementation decision, October 27, 2026 UTC. Local acceptance passes; source delivery, activation and prospective production acceptance are separate. Extends [signature evidence](0016.11-signature-verification-evidence.md) and [classification uncertainty](0016.12-explicit-classification-uncertainty.md). [Research 20](../../packages/blog/drafts/research/analytics-retrospective/20-verification-outcomes-and-vendor-methods.md) owns sources, measurements and release status.

## Decision

Keep the legacy verified/unverified/absent contract and retain a separate closed local outcome: invalid input or cryptographic mismatch, unsupported feature, unavailable directory/key/deadline, local time/coverage policy rejection, outside-Web-Bot-Auth, or indeterminate. Crypto exceptions are indeterminate, not signature-invalid. Retain all distinct failed candidate reason codes; different failure categories are indeterminate rather than decided by signature label order. A successful candidate still establishes that at least one supported signature verified. No complete RFC validity, maliciousness or unique-request claim follows.

Map only reviewed reason codes into routine JSON; unknown/injected free text becomes an unrecognized-reason token. Preserve old evidence without inference from its earlier broad result. Collection, verifier profile and signature-evidence versions become `2026-10-27.3`; classifier remains `.2`. Reuse the existing 2,048-byte JSON column, without migration, raw diagnostics or historical rewriting. The public report/cache version changes and exposes both outcomes and unrecorded detail under the same exclusions.

Create a separate documented-signing-method registry. Initially ExaSearchBot and ExaUser share Exa's documented `https://crawler.exa.ai` key origin, supported by their separate official pages. Compare only locally verified origins; preserve no-declaration, unmapped, not-verified, matching and different-origin states. Injected test verdicts remain separate. Preserve whether the User-Agent is covered. A matching origin does not authenticate an unsigned client declaration, actual purpose, initiating user, downstream use or replay uniqueness. A different origin does not prove impersonation. Never derive verification trust from the public display-name catalogue.

Other vendors remain explicitly unmapped by this method. Official IP feeds and forward-confirmed reverse DNS are distinct future methods with their own source/version/freshness and unavailable states. Hosting ASN lists are not vendor verification. Request IPs should stay in memory for such comparisons; fetch public feed URLs, never send reader addresses to vendor lookups merely to verify membership.

## Acceptance and remaining limits

Exercise all emitted codes, unknown/private error canaries, multi-signature order, crypto exceptions, exact known-origin comparisons, coverage, unmapped declarations, JSON budget, history, all report exclusions and empty results. Run actual collection and report SQL through local D1; record Node crypto versus Worker runtime limits. Check code, activation and measured prospective writes separately. Keep organic signed acceptance and independently labelled error/abstention calibration open. The prepared broad production report exceeded its 50,000-read plan; preserve that failed budget check and use narrow indexed prospective acceptance instead of repeating it.
