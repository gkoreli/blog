# ADR-0016.15: Report client-form claims without inventing hardware

## Status

Active October 27, 2026 UTC. Migration 0015, source `63204dc`, 100% activation, actual Worker form controls and API/UI/article/cache acceptance are recorded separately in the release receipt. Local checks and dated experiments are linked from [research 22](../../packages/blog/drafts/research/analytics-retrospective/22-client-form-and-calibration.md). Human/device accuracy and production stage/beacon trials remain open. Extends [explicit classification uncertainty](0016.12-explicit-classification-uncertainty.md).

## Decision

Use a dedicated `client-form.ts` module for claims already present in request headers. Keep exact reviewed phone/tablet markers, the coarse browser-family claim and `Sec-CH-UA-Mobile` as mobile/non-mobile/absent/unsupported. Distinguish marker, preference-only, no-form-marker, conflicting-marker and unknown outcomes. An iPad's compatibility `Mobile` marker is not a phone/tablet conflict. Different preference/marker indicators are not proof of fraud or invalid requests.

Do not infer desktop hardware from missing markers, non-mobile preference or an unmatched User-Agent. Do not infer a tablet from Android without Mobile. Do not request additional hints, high-entropy values, model information, browser probes or persistent identifiers. Derived facts remain linked to existing observations and share their retention; this is not an anonymity or compliance determination.

Migration 0015 adds nullable valid JSON `client_form_evidence`, capped at 1,024 bytes. Earlier rows remain null. Keep the old constrained three-value `device_type` only as a deprecated compatibility heuristic; new evidence explicitly retains its value and whether desktop was the default. This avoids a table rebuild while making the replacement evidence canonical. The old column must not drive current physical-device reporting.

Replace public `byDevice` with `byClientForm: [{form, views}]`. This is an intentional API semantic change, with the dashboard and cache version updated together. Current records, earlier heuristic records and unrecognized evidence records partition the selected total. Historical desktop/default, mobile and tablet outputs remain labelled heuristics; neither backfill nor history rewrite manufactures missing proof. Unsupported hints and differing indicators are overlapping subsets, not extra events.

The dashboard shows client-form claims for every traffic filter, including bots and Unresolved. Use counts and explicit labels instead of desktop/mobile icons implying authenticated hardware. Update /privacy, package exports, direct report consumers and private legacy-output labels. Collection/classifier and public report profiles advance to `2026-10-27.5`; verifier profile remains independently versioned.

## Why and acceptance

MDN, Chromium's UA reduction documentation and the WICG draft distinguish compatibility markers/preferences from hardware. Pinned Matomo code exposes unknown devices and explicit inference rules; we borrow the unknown/assumption distinction without copying its LGPL corpus or adding a dependency. Replaying 381 retained R1 requests turns 355 desktop defaults into 181 non-mobile preferences and 174 browser claims without form markers. This does not identify R1 or establish a real-device distribution.

Accept exact marker/unsupported/conflict behavior, bounded private output, preserved migration history, canonical API partitions, report exclusions and native local D1 before production. Apply migration 0015 before publishing writers/readers. Verify actual Worker writes, public labels, cache reuse, article/disclosure and activation separately. Labelled automation trials measure their own decisions/abstentions and storage failures; human false-positive rates and physical-device accuracy require independent human/hardware controls.
