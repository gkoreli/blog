# ADR-0012.2: Animation Entities — Spawnable, Persistent Scene Objects

## Status

Design — 2026-04-16. Extends ADR-0012.1 (Signals). Implementation pending.

---

## Context

ADR-0012.1 introduced `Signal<T>` for continuous environmental inputs — cursor position, scroll velocity, clock. Signals are passive observers: they reflect external state that exists whether or not the animation is running.

This ADR addresses a different class of input: **user-created, persistent scene objects**. The motivating case — clicking the canvas to drop a permanent force field generator — doesn't fit the signal model cleanly:

- A signal reads from something that already exists (the cursor's position, the scroll offset). A force point *does not exist* until the user creates it.
- A signal's value changes continuously over time. A force point's existence is event-driven — it's born at a click and lives until explicitly destroyed.
- Multiple force points can coexist. A signal is a single value.
- Force points have their own internal physics — they oscillate, pulse, emit waves. They're not passive.

The interaction desired: click the canvas → a jittery repulsion field spawns at that point, permanently deflecting nearby animation points. Click the same spot again → it disappears. Multiple fields can coexist, each with independent phase and radius oscillation.

This is imperative event → declarative persistent state. It's not a signal. It's an **entity**.

---

## Core Distinction: Signals vs. Entities

```
Signal<T>          — passive, external, singular
                     reflects something that exists outside the animation
                     read once per frame, runner manages lifecycle

Entity<T>          — active, internal, plural
                     created and destroyed by user events
                     has its own state and physics that evolve each frame
                     lives in an EntityStore, consumed by effects
```

A `cursorSignal` reflects where the cursor is. A `ForcePoint` entity *is* something — it was created, it has a position, it has age, it pulses, it can die. The cursor doesn't "accumulate" over clicks; force points do.

---

## Decision

Introduce two new abstractions: `EntityStore<T>` and `Emitter`. Together they form the write path (events spawn entities) and the read path (effects consume entities). The existing `Signal` and `Effect` contracts are unchanged — entities slot into the pipeline as a special signal-like readable that effects can consume.

## EntityStore

```ts
interface Entity<T> {
  readonly id:      number;
  readonly data:    T;           // domain data (position, params)
  state:            EntityState; // 'alive' | 'dying' | 'dead'
  age:              number;      // frames since spawn
}

type EntityState = 'alive' | 'dying' | 'dead';

interface EntityStore<T> {
  /** Read all currently alive entities — called each frame by effects. */
  entities(): readonly Entity<T>[];

  /** Spawn a new entity. Returns its id. */
  spawn(data: T): number;

  /** Begin the dying transition for an entity. */
  kill(id: number): void;

  /** Immediately remove an entity. */
  destroy(id: number): void;

  /** Advance entity ages. Runner calls this once per frame before applyEffects(). */
  tick(): void;

  /** Remove all dead entities. Called by runner after tick(). */
  prune(): void;
}
```

`EntityStore` is **both** the write interface (spawn/kill/destroy) and the read interface (entities()). This is intentional — the caller holds the store and can pass it to both the emitter (writes) and the effect (reads). The store is the shared mutable state between the input side and the rendering side.

`tick()` and `prune()` are called by the runner each frame. The store doesn't have its own loop — it participates in the runner's loop. This is different from signals, which may have their own rAF loops for smoothing. Entity physics runs synchronously in the runner's frame.

### Entity lifecycle

```
spawn(data)
  → state: 'alive', age: 0

tick() called each frame
  → age++
  → if 'alive': entity is active, effects see it
  → if 'dying': entity is fading out (effect can read age to interpolate)

kill(id)
  → transitions 'alive' → 'dying'
  → entity stays in the store for DEATH_FRAMES frames (default: 30)
  → after DEATH_FRAMES, transitions 'dying' → 'dead'

prune()
  → removes all 'dead' entities
  → called after effects have had a chance to render the final dying frame
```

The `dying` state is important for smooth removal. When a force point is killed, the effect can lerp its strength from 1→0 over the dying frames rather than snapping to zero.

## Emitter

An emitter listens to DOM events and writes to an `EntityStore`. It's the bridge from the imperative event world into the declarative entity world.

```ts
interface Emitter {
  pause():   void;
  resume():  void;
  dispose(): void;
}
```

Emitters follow the same lifecycle protocol as signals — the runner calls `pause()`/`resume()`/`dispose()` on them via a new `.emit()` registration on `AnimationRunner`.

```ts
animate(caustic())
  .emit(clickForceEmitter(canvas, forcePoints))   // emitter → writes to store
  .pipe(forceFieldEffect({ store: forcePoints })) // effect  → reads from store
  .start(canvas, container)
```

The runner:
- Stores emitters separately from effects
- Calls `emitter.pause()` on off-screen (so clicks don't accumulate while invisible)
- Calls `emitter.resume()` on re-entry
- Calls `emitter.dispose()` on cleanup

### `clickForceEmitter`

```ts
interface ClickForceEmitterOptions {
  /** Radius in px within which a click kills the nearest existing point. Default 40. */
  killRadius?: number;
  /** Max simultaneous force points. Oldest is removed when exceeded. Default 8. */
  maxEntities?: number;
}

function clickForceEmitter(
  target: HTMLElement,
  store: EntityStore<ForcePointData>,
  options?: ClickForceEmitterOptions,
): Emitter
```

Behavior on click:
1. Convert click coordinates to normalized (0–1) within the canvas bounding rect
2. Check if any existing entity is within `killRadius` pixels
   - If yes: `store.kill(id)` — begin dying transition
   - If no: `store.spawn({ x, y, phase: Math.random() * Math.PI * 2 })` — create new
3. If `maxEntities` is exceeded, kill the oldest alive entity before spawning

This gives the toggle behavior: click to create, click near the same spot to remove.

## ForcePoint Entity

The concrete entity type for this use case.

```ts
interface ForcePointData {
  x:     number;   // normalized 0–1 within canvas
  y:     number;
  phase: number;   // random initial phase — prevents synchronized pulsing
}
```

The `ForcePointData` is the static data from spawn time. The dynamic state (current radius, strength oscillation, wave position) is computed each frame from `entity.age` and `data.phase` by the effect. No mutable physics state is stored in the entity itself — the frame derivation is:

```
oscillation = sin(age * PULSE_FREQ + phase)
radius      = BASE_RADIUS * (1 + oscillation * PULSE_AMPLITUDE)
strength    = lerp(0, 1, min(age / BORN_FRAMES, 1))          // born fade-in
            * lerp(1, 0, max((age - BORN_FRAMES) / 1, 0))   -- only when dying
jitter_x    = sin(age * JITTER_FREQ_X + phase) * JITTER_AMP
jitter_y    = cos(age * JITTER_FREQ_Y + phase * 1.3) * JITTER_AMP
```

The "jitter" is deterministic from `age` and `phase` — reproducible, no random state, zero allocation.

## ForceField Effect

The effect that reads `ForcePointData` entities and applies their force to the animation's points.

```ts
interface ForceFieldOptions {
  store:      EntityStore<ForcePointData>;
  radius?:    number;   // fraction of min(w, h), default 0.3
  magnitude?: number;   // px/frame at center, default 22
  damping?:   number;   // velocity damping, default 0.88
}

function forceFieldEffect(options: ForceFieldOptions): Effect
```

`apply()` iterates all alive + dying entities, computes their jitter-displaced center and oscillating radius, and accumulates velocity on each animation point — same quadratic falloff physics as `cursorRepulsion` but driven by the entity store instead of a cursor signal.

Multiple entities stack: a point inside two overlapping force fields gets both forces summed. The velocity accumulation handles this naturally.

### Per-frame derivation (inside `apply()`)

```ts
for (const entity of store.entities()) {
  const { data, age, state } = entity;

  // Jitter: deterministic oscillation around spawn position
  const jx = data.x + sin(age * 0.11 + data.phase)        * 0.015;
  const jy = data.y + cos(age * 0.09 + data.phase * 1.31) * 0.015;

  // Pulse: oscillating radius
  const pulse = sin(age * 0.07 + data.phase);
  const r = Math.min(w, h) * radius * (1 + pulse * 0.25);

  // Strength envelope: fade in on born, fade out on dying
  const bornT  = Math.min(age / 20, 1);                      // 20-frame fade in
  const dyingT = state === 'dying' ? Math.max(1 - entity.age / 30, 0) : 1;
  const envelope = bornT * dyingT;

  const cx = jx * w;
  const cy = jy * h;

  for (let i = 0; i < points.length; i++) {
    // ... same quadratic falloff as cursorRepulsion, multiplied by envelope
  }
}
```

The jitter is in normalized space (0.015 ≈ 1.5% of canvas width). At 900px wide, that's ±13px oscillation around the spawn point. The field visually breathes and wobbles rather than sitting still.

## Runner Integration

The `AnimationRunner` gains one new method:

```ts
class AnimationRunner {
  pipe(effect: Effect): this      // unchanged
  emit(emitter: Emitter): this    // new — registers an emitter
  start(canvas, container): () => void
}
```

And stores in the store list — stores need `tick()` and `prune()` called each frame.

The runner's internal changes:

```ts
// Collected at start() time:
const signals  = deduplicate(effects.flatMap(e => e.signals ?? []));
const emitters = [...this.emitters];
const stores   = deduplicate(effects.flatMap(e => e.stores ?? []));

// IntersectionObserver:
if (intersecting) {
  for (const s of signals)  s.resume();
  for (const e of emitters) e.resume();
  running = true; raf = requestAnimationFrame(frame);
} else {
  running = false; cancelAnimationFrame(raf);
  for (const s of signals)  s.pause();
  for (const e of emitters) e.pause();
}

// Per-frame (in frame()):
for (const store of stores) { store.tick(); }
const base   = mod.tick(t, w, h);
const points = applyEffects(base, effects, { w, h, t });
mod.draw(ctx, points, t, w, h);
for (const store of stores) { store.prune(); }
```

`stores` are auto-discovered from effects via `effect.stores?: EntityStore<unknown>[]` — same deduplication pattern as signals.

## Full Composition Example

```ts
const cursor      = cursorSignal(container);
const forcePoints = entityStore<ForcePointData>();

const stop = animate(caustic())
  .emit(clickForceEmitter(canvas, forcePoints, { killRadius: 40, maxEntities: 8 }))
  .pipe(forceFieldEffect({ store: forcePoints, magnitude: 22 }))
  .pipe(cursorRepulsion({ signal: cursor, magnitude: 18 }))
  .start(canvas, container);
```

Reading this aloud: animate a caustic pattern. Clicking the canvas spawns permanent jittery repulsion fields. The cursor also repels points while hovering. Everything pauses when scrolled away. Cleanup on `stop()`.

Each abstraction does exactly one thing:
- `caustic()` — produces the base orbital points
- `entityStore` — holds the list of active force points
- `clickForceEmitter` — listens for clicks, writes to the store
- `forceFieldEffect` — reads the store, accumulates velocity on points
- `cursorRepulsion` — reads the cursor signal, accumulates velocity on points
- `AnimationRunner` — owns rAF, observers, and all lifecycle calls

## The Taxonomy So Far

```
Animation Input
├── Signal<T>          — continuous, external, singular
│     cursorSignal()     position + strength + velocity
│     scrollSignal()     y + progress + velocity
│     clockSignal()      t + dt
│     mediaSignal()      boolean (prefers-reduced-motion, etc.)
│     derived()          transform a signal without new infrastructure
│     combinedSignal()   merge multiple signals
│
└── EntityStore<T>     — discrete, internal, plural
      spawn(data)        create an entity at runtime
      kill(id)           begin dying transition
      entities()         read current alive+dying set each frame
      tick() / prune()   advance age, remove dead (runner-driven)

Animation Transform
└── Effect             — reads Signal or EntityStore, transforms AnimationPoint[]
      apply(points, ctx)
      signals?[]         declared Signal dependencies (runner manages lifecycle)
      stores?[]          declared EntityStore dependencies (runner calls tick/prune)

Animation Input Source (DOM → Store)
└── Emitter            — listens to DOM events, writes to EntityStore
      clickForceEmitter(canvas, store)
      (future: dragEmitter, touchEmitter, keyEmitter...)

Animation Output
└── AnimationModule    — reads post-effects points, draws to canvas
      tick()   → AnimationPoint[]
      draw()   → canvas
```

## Physics Store (Future)

The `ForcePoint` entity is the first member of what will become a **physics store** — a catalog of entity types with defined physics behaviors:

- `ForcePoint` — radial repulsion field, jitter oscillation, pulse radius
- `AttractorPoint` — inverse: pulls points toward it
- `VortexPoint` — rotational force around the spawn point
- `WaveSource` — emits expanding circular pressure waves (the force falls off with ring radius, not distance from center)
- `BlackHole` — strong attraction with tidal forces (differential pull across the entity's radius)
- `Explosion` — single-frame blast that spawns with a large initial impulse and decays over N frames
- `Anchor` — pins specific animation points near a location (spring force toward fixed position)

All are `EntityStore<TheirData>` instances consumed by a corresponding effect. All are spawnable by any emitter (click, touch, scroll threshold, timer, external signal).

The **effect store** mirrors this at the transform layer — a catalog of named, composable effects:

```ts
import { forceFieldEffect }   from '@animations/effects/force-field';
import { cursorRepulsion }    from '@animations/effects/cursor-repulsion';
import { turbulence }         from '@animations/effects/turbulence';
import { waveDeformation }    from '@animations/effects/wave-deformation';
import { magneticField }      from '@animations/effects/magnetic-field';
```

Each is a pure function `(options) → Effect`. No shared state. Composable in any order. The pipeline contract is the only interface they need to satisfy.

## Open Questions

**Q: Should EntityStore itself be a Signal?**

`EntityStore<T>` could implement `Signal<readonly Entity<T>[]>` — then it plugs into the existing signal deduplication and lifecycle machinery without needing a separate `stores[]` field on effects or `.emit()` on the runner.

The problem: signals have no write side (`read()` only). Making the store a signal would require splitting the read and write interfaces — a `ReadonlyEntityStore<T>` for effects and the mutable `EntityStore<T>` for emitters. This is clean but adds a type layer. Deferred until the implementation demands it.

**Q: Per-entity velocity state vs. frame-derived physics?**

Current design: entity physics (jitter offset, pulse radius, strength envelope) is computed each frame from `age` and `phase` — deterministic, zero allocation. Alternative: store velocity state in the entity and integrate it each frame (like the per-point velocity array in cursorRepulsion).

Frame-derived is correct for periodic behavior (oscillation, pulsing). Per-entity velocity state is needed if entities should respond to forces applied to them (e.g., an entity that drifts over time). For the initial force-field use case, frame-derived is sufficient and simpler.

**Q: Touch support in `clickForceEmitter`?**

`pointerdown` with `e.pointerType === 'touch'` covers both click and touch in one listener. The emitter should use pointer events, not mouse events, so it works on mobile. The bounding rect normalization is identical.

**Q: Maximum entity count and performance budget?**

Each alive entity iterates all animation points in `apply()`. With 22 caustic points and 8 force entities, that's 176 force computations per frame — trivial. With 200 points and 20 entities it's 4,000 — still fine. The `maxEntities` cap in the emitter is a UX guard (too many overlapping fields becomes visually incoherent) more than a performance guard. Document this so future entity types with more expensive physics know where their budget is.
