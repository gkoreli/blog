# ADR-0016.24: Portable report delivery and public-key signature domains

## Status

Accepted engineering direction, November 13, 2026 Pacific. Implementation and acceptance are tracked in the [engineering worklist](../worklist/tools-product-opportunities/analytics-package-engineering.md). Extends [report responsibilities](0016.23-cold-report-projections.md) and the existing [analytics domain boundaries](0016-analytics-observation-semantics.md#domain-boundaries).

## Decision

Keep one analytics package. Observation and evidence policy, report queries, delivery application services and presentation adapters have explicit module boundaries inside it. Applications supply their cache, database, background-work lifetime and reporting admission policy; they do not reimplement analytics cache keys or evidence interpretation. The blog keeps its publication shell and bespoke charts. A standalone report uses semantic server-rendered HTML and no framework dependency.

Move the existing tested cache implementation into the package without changing its one-hour/midnight expiry, canonical validated selections, policy/version keys, optional-I/O deadlines, error behavior or local coalescing. Compose report generation with a durable cold-fill admission port. Daily fill admission is atomic across callers using the same database. Cumulative provider-returned reads are a circuit-breaker threshold, not a pre-execution SQL row limit; an admitted calculation and concurrent admitted work can cross it. Missing meters or settlement failures must not silently reopen admission. Cache hits and coalesced requests do not acquire another fill. Keep budget accounting separate from audience observations and report freshness.

Freeze the already-issued empty-install schema. Add ordered portable upgrades for new installations and for databases that already applied that baseline. Compare the complete portable chain to the historical blog migration chain; never replace an applied baseline as an upgrade. Site-specific historical backfills remain outside the portable chain.

The signature reporting extension changes the projection fingerprint. Its ordered migration promotes only facts with the reviewed predecessor fingerprint whose authoritative source has neither the new verifier profile nor the new coverage format. These rows have identical old/new interpretation: the SQL changes only add recognition of those two formats. Every other fact remains stale and uses the complete source fallback until rebuilt. Promotion changes only the fingerprint, with source/derived-value equality and negative controls required. This avoids reevaluating all historical envelopes for a format-only extension while preserving the normal stale-fact guard.

Extract public-key material, RFC 7638 identity, metadata admission, WebCrypto import and verification into a focused module. Support `ed25519`, `rsa-pss-sha512`, `rsa-v1_5-sha256`, `ecdsa-p256-sha256` and `ecdsa-p384-sha384` with fixed RFC parameters. Match declared signature algorithms to key family and advertised JWK constraints. Imported-key caches include the algorithm so one RSA key cannot reuse a CryptoKey imported for another algorithm. Preserve rejection of private key material, conflicting duplicate publications, demonstration keys and invalid validity windows.

Request verification continues to own message components, Web Bot Auth policy and bounded directory resolution. Directory-proof auditing reuses the public-key module rather than maintaining an Ed25519-only cryptographic path. Frozen historical profiles remain readable; new behavior receives new implementation/profile identifiers. The protocol facade exposes verification and explicit supplied-input audits without storage or blog dependencies.

## Standards and limits

[RFC 9421 section 3.3](https://www.rfc-editor.org/rfc/rfc9421.html#section-3.3) defines the fixed algorithms, including the 64-byte RSA-PSS salt and concatenated ECDSA signature representation. [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638.html) defines key thumbprints independently of permission metadata. [Web Bot Auth protocol-01](https://datatracker.ietf.org/doc/draft-ietf-webbotauth-httpsig-protocol/01/) remains a draft with both Ed25519 and RSA-PSS examples.

This is increased tested coverage, not a declaration of complete HTTP Message Signatures conformance. HMAC requires an independently provisioned secret and does not belong in public key-directory discovery. Trailers, original wire request targets and response/request associations require actual transport context. Request-body digest verification and nonce replay enforcement remain separate capabilities; signed-header coverage must not imply them.

## Consequences and acceptance

Prefer cohesive functions and typed ports over a class hierarchy. Dependencies point from application orchestration to domain policy and explicit adapters; presentation does not classify traffic or execute SQL. Preserve the existing public query contract and historical observations. New reporting budget tables do not change observed audience counts.

Require native interoperability and negative controls, durable admission races, ordered schema upgrades, a separate-project run, complete report/cache regressions, types, isolated build and scoped delivery. Independent operator value, production activation and measured live behavior require their own evidence.
