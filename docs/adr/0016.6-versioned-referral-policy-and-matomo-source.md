# ADR-0016.6: Version Referrer Exclusions and Retain Matomo Source Evidence

## Status

Accepted September 6, 2026 PDT; implementation verified September 7 UTC. Extends [ADR-0016.5](0016.5-referral-abuse-defense.md), replacing its local-only source policy. Tracked in [TASK-0121](../tasks/TASK-0121.md) and [FLDR-0009](../folders/FLDR-0009.md). Policy `2026-09-06.2` is deployed and verified. The [activation record and live evidence](../../packages/blog/drafts/research/readers-vs-bots/19-referral-policy-activation.md) identify the release separately from this decision.

## Decision and reason

Use a pinned Matomo referrer-spam snapshot as the default exclusion source, with reviewed local exceptions and a separate catalogue of names permitted in public reports. Retain collected referral evidence in D1. Evaluate inclusion at report time, exposing the active policy version, hash, source revision, and excluded count. This lets us remove suspected abuse from reports and later reverse a decision without deleting its evidence.

The distinction matters in the current case. The reviewed Matomo snapshot contains 2,348 hostnames but does not contain `uniuit.com`. Our local investigation supplies that exclusion; the community list broadens coverage. Neither establishes the sender's identity or whether a person initiated a request. A supplied referrer can be fabricated, as described in [Matomo's account of referrer spam](https://matomo.org/blog/2015/05/stopping-referrer-spam/) and the header's semantics in [RFC 9110 §10.1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.3).

## Domain model and boundaries

Referral reporting is a bounded part of analytics. Its decisions do not change the reader-kind classifier, authenticate a client, or block page access. Names in the code express the reporting decisions we actually make. This applies the model/language and implementation boundaries described in [Eric Evans' DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), without adding a framework or service.

| Concept | Meaning and ownership |
|---|---|
| Reported host | The bounded hostname retained from the request's referrer. It is supplied evidence, not authenticated attribution. Collection owns it. |
| Source snapshot | The exact upstream bytes, full Git revision, capture time, file hashes, count, and license declaration. Import tooling owns it. |
| Local rule | Stable ID, canonical host, exact-host or subtree scope, include/exclude action, reason, and evidence reference. The maintainer owns this decision. |
| Referral policy | A versioned definition combining source snapshot, local rules, evaluator version, and public display catalogue. Its canonical definition has a SHA-256 commitment. |
| Assessment | A derived action, matched rule and source, and display outcome under one policy. A match means the policy applies; it is not a bot identity. |
| Public report | Aggregates after owner, selection, and referral exclusions, with a separate count of excluded observations. |
| Saved report | The received response bytes, hash, URL/filters, report time, capture time, and policy commitment. This preserves what that response actually reported. |

The pure model is in `packages/analytics/src/referral-policy.ts`. `referral-sql.ts` translates it into a D1 predicate. `referrals.ts` handles input parsing and public names. `stats.ts` applies the predicate to every projection. Import, replay assessment, and report capture live in the blog's existing TypeScript script tooling. There is no source download on a request or ordinary production build.

## Matching and precedence

`host-suffix-v1` compares the parsed hostname to a rule's host or a suffix beginning at a DNS label boundary. An upstream entry applies to that host and its descendants, including entries for a specific subdomain. It does not apply to a parent, a lookalike such as `notsemalt.com`, or an unrelated URL whose path/query contains `semalt.com`.

New HTTP(S) inputs use the URL parser's hostname/IDNA handling. Retained host values receive ASCII case folding and removal of trailing DNS dots; both evaluators use those same operations. Values longer than 253 characters do not match rules. The `www` label is preserved for evidence matching. It is collapsed only for display and same-site comparison. Earlier ingestion stripped `www`; that lost label cannot be reconstructed, and an exact-subdomain rule cannot retroactively distinguish those rows.

Deterministic precedence is:

1. Local rules override upstream rules.
2. Within that priority, the most specific matching host wins.
3. At the same host, exact-host scope wins over subtree scope.
4. With no matching rule, include the observation. With no display approval, show only the generic other-referrer count.

For example, a local subtree include for `reader.semalt.com` overrides upstream `semalt.com`; a more specific local exclusion for `bad.reader.semalt.com` overrides that include. An exact-host include does not exempt descendants. Duplicate local IDs or duplicate host/scope pairs are rejected, including contradictory actions. Include rules require evidence just as exclusions do. A display approval never overrides an exclusion; the compiler rejects a directly conflicting approved name until resolved explicitly.

This deliberately differs from Matomo's inspected implementation. Its [pinned core matcher](https://github.com/matomo-org/matomo/blob/79c953a035723b8a7ee80b87074daf82976e954e/core/Tracker/Visit/ReferrerSpamFilter.php#L28-L45) searches the whole referrer string case-insensitively. We adopt the maintained source with narrower hostname semantics. Matomo's [updater](https://github.com/matomo-org/matomo/blob/79c953a035723b8a7ee80b87074daf82976e954e/plugins/CoreAdminHome/Tasks.php#L344-L368) follows `master`; ours requires a reviewed full revision and expected content hash.

## Source provenance and changes

The initial archive is `packages/analytics/data/referrer-sources/matomo/e65db652cade6882aa9a76bbb65c9bb17e079f4b/`. It retains `spammers.txt`, README, Composer metadata, and a manifest. The list's SHA-256 is `83d2f174807c72987e73611fd7b36776bab02ee85fccc7b705d3be1bfa2a80b5`. The pinned [README](https://github.com/matomo-org/referrer-spam-list/blob/e65db652cade6882aa9a76bbb65c9bb17e079f4b/README.md) calls it community-contributed and permits empty lines; the [package metadata](https://github.com/matomo-org/referrer-spam-list/blob/e65db652cade6882aa9a76bbb65c9bb17e079f4b/composer.json) declares CC0-1.0. Both license statements remain archived.

The importer refuses redirects, unexpected content hashes, invalid host entries, duplicate canonical names, unexpected list sizes, and overwriting an archive. It normalizes case and IDNA at this input boundary. A source update requires a new policy file; an existing version cannot be rebuilt, assessed, or captured with a different commitment. Source additions/removals and local/display changes are reviewable before activation. The production build checks the archived hashes and generated module offline.

Archive identity is an integrity commitment, not a signature by Matomo or proof that its judgments are correct. Local false-positive exceptions are first-class. A removed entry is a new reporting decision, not an instruction to erase the old snapshot. An evaluator change requires a new evaluator identifier and policy version; old evaluation code remains recoverable through the release's Git revision.

## Retention and historical meaning

This repair does not delete observations or rewrite their hostname, classification, or signature result. It adds no full referrer URL, raw IP, or full User-Agent storage. Our retained evidence is the existing bounded hostname and request fields, not every original header byte. Other audited migrations have changed classification fields; the whole `page_observations` table is not immutable.

Three questions require different evidence:

- **What was observed?** Read retained D1 evidence, subject to the collection method and fields available at that time.
- **What would policy P report over retained data now?** Load its archived definition and matching code and rerun the query. The internal `queryStats` policy argument supports this; arbitrary old policies are not selectable through the public API.
- **What did the published report say then?** Use a saved response or a database snapshot plus the exact code, filters, clock, owner exclusions, and policy. A policy version alone cannot reproduce this after late writes or other classification/owner changes.

`capture-report` records the received JSON bytes and their hash, checks the advertised policy against the archive, and refuses unapproved names. It creates a new private file and refuses overwrite. Its capture time is not the deployment activation time. Historical research artifacts retain their original populations and methods; newly recalculated counts must name the policy.

## D1 implementation and measured cost

D1 allows at most 100 bound parameters per statement. The adapter sends the entire rule set as one compact JSON value, plus two time bounds. It materializes the rules and distinct reported hosts in the selected time window, enumerates hostname suffixes, and joins by equality. Selection and owner predicates remain shared across all panels. This avoids a thousands-placeholder query and a separate host-discovery read that could miss new hosts arriving before aggregation. See [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 JSON support](https://developers.cloudflare.com/d1/sql-api/query-json/), and [SQLite CTE semantics](https://sqlite.org/lang_with.html).

At 2,349 effective rules, the predicate is 1,266 SQL bytes, with 61,161 JSON bytes and three bindings. Production EXPLAIN shows materialization and an automatic covering index for suffix matching. The nine report queries used 111.17 ms of summed database execution and reported 182,388 rows read in the inspected window. They were issued as separate read-only verification calls, so this is not Worker latency or a transaction benchmark.

Local full-report measurements were approximately 50 ms for 10,000 observations/100 hosts, 470–491 ms for 100,000/1,000, and 2.0–2.1 seconds for 100,000 distinct hosts. These synthetic measurements are not a D1 capacity guarantee. Host materialization repeats per panel and spans the time window even for narrow path/agent selections. Revisit a stored indexed policy or report materialization if measured latency/read budget becomes a problem; the current repair adds no database migration. Reproduction and raw plans are in [artifact 18](../../packages/blog/drafts/research/readers-vs-bots/18-matomo-referral-policy-verification.md).

## Validation, activation, and rollback

The release gates cover every upstream entry and adversarial variants in both evaluators, precedence and false-positive exceptions, source/commitment tampering, report provenance, all public metric/filter combinations, unknown-name suppression, and unchanged retained observations. The candidate production query returns 937 included plus 35 excluded observations for August 8–September 6 UTC, matching the pre-exclusion 972. Named 60 + other 7 + absent 870 = included 937. Matomo adds no further exclusion in this inspected population; the local rule accounts for the 35. This is policy impact, not measured human-count accuracy.

All 46 analytics and 19 blog tests, typechecks, and production build are required. The build itself enforces policy integrity. Browser verification remains unperformed because no browser is available in this session. At the September 7 00:09 UTC checkpoint, the live API had no referral policy field. Subsequent activation is documented in artifact 19.

Release code and assets together from reviewed changes. Append an activation record containing environment, actual deployment ID/time, source-code commit, policy version/hash, evaluator, and verification-artifact path/hash. Capture the live report with the command in the [policy maintenance guide](../../packages/analytics/policies/README.md). Keep earlier activation records when rolling back or correcting a mistaken entry. A rollback may restore a prior code release or activate a new policy correcting the rule; neither needs a D1 rollback. Do not create a fictitious activation time for an unshipped candidate.

## Limits

The policy prevents arbitrary hostnames from gaining public exposure and excludes matching traffic consistently. It cannot identify the sender from a referrer, stop clients omitting or changing the header, authenticate a familiar approved host, or guarantee that the remaining observations are human. Community-list exclusions can hide legitimate visits. Retained evidence, explicit reasons, and reversible versioned decisions make those limits inspectable.
