# ADR-0016.2: Browser Evidence and the Browsers Partition

## Status

Accepted — 2026-09-02. Extends ADR-0016 and stays inside the purpose and threshold set by ADR-0016.1. It changes the public meaning of the **Browsers** class, adds request-evidence fields to the observation model, and adds two public views that the existing data already supports.

## Context

ADR-0016 moved counting from a browser beacon to the Worker edge so that non-JavaScript automation became visible. It worked. It also removed the one signal the beacon had provided for free: proof that a real browser executed a page. Since the August 26, 2026 cutover, every successful HTML response whose User-Agent does not match a bot or AI rule is counted as a **Browser**. Most scrapers, headless fetchers, link-preview services, and security scanners send a Chrome or Safari User-Agent and no Referer. They are all Browsers now.

The consequence is a number that nobody believes. Evidence from production on 2026-09-02 (UTC), Browser class, owner rows excluded:

| Fact | Value |
|---|---|
| Daily clients on 2026-09-02 | 113 |
| Clients with exactly one page view | 100 |
| Clients with any referrer | 7 |
| Views with no referrer | 156 of 164 |
| One "mobile" client, 05:03 UTC | 31 distinct pages in the same second |
| Daily clients per day, Aug 19–25 (beacon era) | 2 to 12 |
| Daily clients per day, Aug 26–Sep 2 (edge era) | 52 to 124 |
| Views without a referrer, beacon era, August | 82% |
| Views without a referrer, edge era | 97% |

The step change coincides exactly with the collection-method change, not with any change in readership.

Cloudflare Web Analytics, a script-based counter that runs beside the first-party system, gives the independent check. Same 7-day window ending 2026-09-02, bots excluded:

| Source | Page views | Clients or visits |
|---|---:|---:|
| First-party D1, Browser class | 1,209 | 578 daily clients |
| Cloudflare Web Analytics | 113 | 52 visits |

The first-party Browser count is roughly ten times a script-verified count over the same week. The gap is not readers. It is automation carrying browser User-Agents.

Three reader questions fail as a result:

1. "How many people read the post I just published, and from where?" The Browsers number is not readers, and the dashboard has no per-page view even though the API already accepts a `path` parameter.
2. "Why do referrer views not add up to page views?" The referrer list drops the no-referrer bucket, which in the edge era is 97% of rows. The two panels cannot be reconciled by eye.
3. "What are the AI agents fetching?" Named-agent totals exist, but nothing scopes the page list to one agent.

ADR-0016.1's engineering threshold applies. All five conditions hold: the reader-count question recurs on every publish and cannot be answered from the existing response because the class is polluted at ingestion; the missing observations have precise definitions (fetch-metadata headers and network ASN on the request); the result changes a named action (whether to change distribution for a post); privacy and public wording are set out below; and one migration plus one predicate is cheaper than hand-running D1 queries after every post.

## Decision

Keep the edge as the only collection point. Record two kinds of request evidence that a real browser navigation carries and that most automation does not, and split the public Browser class on that evidence.

### Evidence recorded per edge observation

| Column | Source | Values |
|---|---|---|
| `asn` | `request.cf.asn` | integer or `NULL` |
| `as_org` | `request.cf.asOrganization` | short text or `NULL` |
| `sec_fetch_mode` | `Sec-Fetch-Mode` header | header value or `NULL` |
| `sec_fetch_dest` | `Sec-Fetch-Dest` header | header value or `NULL` |
| `sec_fetch_site` | `Sec-Fetch-Site` header | header value or `NULL` |
| `sec_fetch_user` | `Sec-Fetch-User` header | `1` when `?1`, else `0`; `NULL` when absent |
| `accepts_html` | `Accept` header | `1` when it lists `text/html` or `*/*`, else `0`; `NULL` when absent |
| `has_accept_language` | `Accept-Language` header | `1` when present, else `0` |

Raw header values are stored only for the four fetch-metadata headers, which are closed enumerations defined by the Fetch Metadata specification, and for the ASN and organization name, which identify a network, not a person. The raw `Accept`, `Accept-Language`, `User-Agent`, and IP are still not stored. The daily client identity is unchanged.

### Derived partition

The stored `traffic_class` remains the User-Agent verdict from ADR-0016. The public partition is derived at query time from that class plus the evidence:

| Public class | Rule |
|---|---|
| **Browsers** | `traffic_class = 'browser'` AND the row is `navigation-shaped` AND the row is not from a `hosting network` — OR the row is a legacy beacon observation (`observation_source = 'beacon'`), which executed JavaScript in a browser by construction. |
| **Browser-like** | `traffic_class = 'browser'` and not Browsers. This includes edge rows recorded before evidence collection began, because their shape is unknown. |
| **Bots** | `traffic_class = 'bot'` |
| **AI UAs** | `traffic_class = 'ai'` |
| **All** | every non-owner row |

Definitions:

- **navigation-shaped**: `sec_fetch_mode = 'navigate'` AND `sec_fetch_dest = 'document'` AND `accepts_html = 1` AND `has_accept_language = 1`. `sec_fetch_user` and `sec_fetch_site` are recorded for later analysis and are not required. Safari has never sent `Sec-Fetch-User` on any version, and other browsers omit it on non-user-activated navigations, so requiring it would demote every iPhone reader. Fetch metadata is sent by Chrome 80+, Firefox 90+, and Safari 16.4+; older browsers fall into Browser-like, which is acceptable in 2026 and is stated in the methodology. `curl`, `python-requests`, Go `net/http`, and Scrapy send none of these headers by default.
- **hosting network**: `asn` is in a short, versioned list of cloud and VPS providers kept in `packages/analytics/src/networks.ts`. The list contains only providers whose address space is overwhelmingly servers. It must not contain CDNs, consumer VPNs, or privacy relays. In particular it must never contain AS13335 (Cloudflare), AS36183 or AS20940 (Akamai), or AS54113 (Fastly), because Apple iCloud Private Relay egresses through those four networks and Cloudflare WARP through AS13335. Every entry carries the provider name and the date it was checked. The list is data, not a claim: a row from a hosting network is not proven automation, and a row from a residential network is not proven human.

Why both rules: headless Chrome, Playwright, and Puppeteer are real Chromium and send the full fetch-metadata set, so shape alone does not catch them; they usually run on cloud hosts, which the network rule catches. Generic HTTP clients send no fetch metadata, so the shape rule catches them wherever they run. What passes both is a browser navigation from a residential or mobile network, which is as close to a reader as the request itself can show.

The four public classes partition `All`. `Browsers + Browser-like` equals the old Browser class, so historical totals reconcile.

The predicate lives in one function in the analytics package and is the only place the rule is written. Because evidence is stored raw, the rule can be revised and the whole history recomputed without a data migration.

### Public words

- **Browsers** — requests that a browser User-Agent sent as a top-level document navigation from a network that is not a known hosting provider. This is not a verified-human claim. Headless browsers on residential connections pass.
- **Browser-like** — requests with a browser User-Agent that did not carry the request shape of a browser navigation, or came from a known hosting network, or were recorded before the site collected that evidence.
- **Bots**, **AI UAs**, **All** — unchanged from ADR-0016.

Do not use `Humans`, `Readers`, `Verified`, or `Real visitors`.

### Dashboard additions

Three additions, each answering one of the failing questions. Nothing else changes on `/stats`.

1. **Browser-like filter.** A fifth traffic pill between Browsers and Bots. Browsers stays the default.
2. **Per-page view.** Each row in Top pages links to the dashboard filtered by that path. The filtered state shows the path above the cards with a control to clear it, and every panel, including the chart, referrers, and countries, is scoped to it. URL state is `?path=/slug`. The API already accepts this parameter.
3. **No-referrer row and per-agent view.** The referrer list ends with a row labeled **No referrer** carrying the count of views without a Referer, so the referrer panel sums to page views. Each row in Matched User-Agent rules links to the dashboard filtered by that agent (`?agent=Name`), which scopes the page list to what that agent fetched. Country, device, and referrer panels behave as for any filter.

Filters compose: `traffic`, `range`, `path`, and `agent` all apply to every panel in one response. `agent` implies the matching traffic class and is rejected when combined with a conflicting `traffic` value.

### Method boundary

Evidence collection starts at the deployment of this ADR. The public Browsers series drops on that date because the preceding edge week moves to Browser-like. The methodology aside names both dates, August 26, 2026 for the edge cutover and the evidence date, in the same paragraph. Do not backfill or estimate evidence for rows that lack it.

### Calibration

Cloudflare Web Analytics remains the external reference. After deployment, compare its 7-day visits with the first-party Browsers daily clients over the same UTC-adjusted window. The expected outcome is the same order of magnitude. If Browsers still exceed the script-verified count by more than about three times after two weeks, the next candidate is a client confirmation signal, decided in a further ADR, not an ad hoc rule change.

## Alternatives rejected

### Bring back a JavaScript beacon as the reader signal

Rejected for now. It reintroduces a client-forgeable endpoint and a script on every page, and ADR-0016 removed exactly that. Request-shape and network evidence come free with the request. A beacon is the fallback if calibration fails.

### Use Cloudflare bot scores

Not available. `request.cf.botManagement`, bot scores, `verifiedBot`, and JA3/JA4 fields require the Enterprise Bot Management add-on. Bot Fight Mode on the free plan challenges at the edge and exposes no per-request field. The free plan populates `country`, `asn`, and `asOrganization` on `request.cf`. One free-plan signal may exist: the rules-language field `cf.client.bot` (known good crawlers, verified by reverse DNS) can reportedly be copied into a request header by a Transform Rule. It only identifies good bots, which the User-Agent rules already name, so it is not part of this decision. It can be revisited if named-bot classification ever proves unreliable.

### Drop the hosting-network rule and use fetch metadata only

Rejected. Headless Chrome, Playwright, and Puppeteer send the full fetch-metadata headers, and they are the tools scrapers use. The ASN rule is what catches datacenter-hosted browsers. Each rule covers the other's blind spot.

### Reclassify at write time and store the verdict

Rejected. Storing only a verdict freezes today's rule into history. Storing evidence lets one predicate change recompute every window and keeps the rule auditable.

### Filter datacenter traffic with a maintained third-party IP list

Rejected. The zero-dependency bias holds, and ASN from `request.cf` is coarser but free and stable. A short curated ASN list with a documented review date is sufficient for this site's scale.

### Add a "Readers" or "Humans" label

Rejected. ADR-0016.1 forbids verified-human wording. The evidence supports "a browser navigation from a non-hosting network," which is what the label says.

## Consequences

### Positive

- The default public number is defensible against an independent script-based count.
- Per-post launch questions are answered on the public page without D1 queries.
- Referrer and page panels reconcile.
- The AI-agent question has a public answer, scoped to what each agent fetched.
- The rule is one function, the evidence is raw, and the list is versioned; every past decision can be re-run.

### Negative

- Two method boundaries now sit in the public series, August 26 and the evidence date.
- Residential-proxy scrapers and headless browsers on home connections remain in Browsers. The methodology says so.
- The hosting ASN list needs a review date and will occasionally be wrong in both directions.
- Six more columns per row. At this site's volume the storage cost is negligible.

## Migration and deployment

1. Apply `0003_add_request_evidence.sql`: eight nullable columns, no index changes, no backfill.
2. Deploy the Worker. New rows carry evidence; old rows keep `NULL`.
3. Verify with a real browser, `curl`, and a headless browser: the first is Browsers, the second Browser-like on shape, the third Browser-like on network when run from a cloud host.
4. Verify the four classes partition All for one snapshot.
5. Update the privacy page and the stats methodology in the same deploy.

## Verification

Tests defend:

- evidence extraction from headers and `request.cf`, including absent values;
- the partition predicate: beacon rows are Browsers; edge rows without evidence are Browser-like; each failing signal alone demotes a row; hosting ASN alone demotes a row;
- `Browsers + Browser-like + Bots + AI UAs = All` for one seeded snapshot;
- `path` and `agent` filters scope every aggregate and reject conflicting combinations;
- the no-referrer count plus referrer rows equals total views;
- the migration applies to the existing schema and old rows read back with `NULL` evidence.
