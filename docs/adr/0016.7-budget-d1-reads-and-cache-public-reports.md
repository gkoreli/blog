## Problem and corrected assessment

The versioned referral filter preserved the reporting contract but repeated its rule and hostname assessment in nine aggregate statements. The measured full report consumed 182,388 D1 rows read. We recorded that number without converting it into the account's daily allowance: a five-million-read budget supports only 27 such reports before other work. Acceptable query duration did not establish acceptable operating cost.

The 182,388 is the sum of the nine statements' `meta.rows_read` values for one report. A row can contribute again when another statement reads it. The plan includes repeated observation/rule assessment and index access, but the aggregate does not provide a separate cost breakdown for each table, index, or intermediate result. It is neither the number of stored observations nor a count of report callers. Indexes influence the amount of work; the service meter establishes the measured total.

Cloudflare's account metrics subsequently showed 3,889,701 reads for September 7 UTC at the 05:11 capture, or 77.79% of the free daily allowance. The blog database accounted for 3,889,143. The separate adaptive query profile attributed 3,835,924 reads to queries containing our referral matcher, about 94% of its captured reads. Its 180 matching statement executions are consistent with twenty nine-statement reports; they do not identify callers. Agent verification, owner use, and external requests must not be conflated with referral spam. The datasets have different totals and are retained separately.

The browser requested reports with `cache: 'no-store'`. The Worker returned a sixty-second `Cache-Control` header only after querying D1 and did not use the Cache API. Initial loads, changed filters, history navigation, and retries could therefore repeat expensive reporting work. The client does not poll.

## Decision

Calculate a report in one statement from one materialized selection and one referral assessment. Cache successful public reports in Cloudflare's Cache API for at most one hour, ending no later than the next UTC day. Report generation time remains visible, and the dashboard discloses the freshness limit. Browser reuse is limited to sixty seconds and never extends the cached report's expiry.

Keep reporting decisions separate from their delivery:

| Concept | Responsibility |
|---|---|
| Observation | Retained collection evidence; this change makes no writes or schema changes. |
| Referral assessment | Apply the same archived policy and hostname precedence to the selected population once. |
| Report | Produce all panels from the same included population, with scoped exclusions and the existing all-time boundary. |
| Report cache | Reuse a public report for its validated filters, policy, report implementation, and UTC day. |
| Read budget | Account-level operating constraint, measured in scanned rows and shared with other D1 work. |

The analytics package owns selection and aggregation. The Worker owns HTTP caching, concurrent fill limits, and error responses. The public JSON contract, source archive, policy hash, display approvals, and retained observations remain unchanged. No new dependency, persistent table, or paid service is required for this correction.

The statement returns one JSON payload per report section through a `VALUES` section table and `CASE` projections. It avoids a long compound `SELECT` that production D1 rejected. Payload decoding rejects missing, duplicate, malformed, and unexpected sections instead of presenting partial data as a successful report. Each section remains subject to D1's two-megabyte value/row limit; future high-cardinality reports may require a different result shape. Current fixture parity and runtime checks do not establish unlimited report capacity.

## Cache behavior

- Parse and validate with the same function used by the report endpoint before cache access. Canonicalize defaults and recognized filter fields; irrelevant query parameters, incoming cookies, and cache-bypass headers do not produce distinct report entries.
- Include the UTC day, active policy hash, and a report implementation version in the internal cache key. Bump that implementation version when report semantics, storage binding, or public selection rules change. The all-time boundary remains independent of a narrow selection, as before.
- Cache only successful public responses without `Set-Cookie`. Never cache validation errors, database failures, or partial results. Return a generic retryable 503 when generation fails.
- Coalesce concurrent requests for the same report within a Worker isolate. Limit distinct pending fills to eight in that isolate; excess requests receive 503 with `Retry-After: 60`.
- Preserve report `updatedAt` on reuse. Expose `X-Stats-Cache: HIT`, `MISS`, or `COALESCED` for bounded verification. Do not provide a public refresh bypass.

Cloudflare documents the Cache API as local to a data center, without tiered caching. Eviction, multiple data centers, and independent isolates can cause additional fills. Different valid paths also produce distinct keys. This cache and concurrency limit reduce repeated work; they do not impose a global daily quota or prevent a determined distributed client from exhausting it. Owner-registration and newly collected data may take up to an hour to appear in reports. See [Cache API semantics](https://developers.cloudflare.com/workers/runtime-apis/cache/) and the [explicit match/put example](https://developers.cloudflare.com/workers/examples/cache-api/).

## Read-budget verification and operation

Use account metrics and query profiles before issuing investigative SQL. `wrangler d1 info` and `wrangler d1 insights` obtain service metadata; their rolling windows must not be presented as the current UTC day. Account GraphQL hourly metrics provide the daily view. Dashboard and CLI SQL are themselves metered, so a production investigation needs a query budget too. [D1 pricing and definitions](https://developers.cloudflare.com/d1/platform/pricing/), [metrics and query analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/).

Verify correctness on local fixtures across filters, owner exclusions, policy exceptions, date boundaries, and empty results. Then run a bounded production candidate and compare its output with the retained fixed-window report. Record `meta.rows_read`, writes, and statement count. A local runtime benchmark cannot substitute for these service measurements. Exercise the compiled Worker/D1 runtime as well as Node SQLite; they enforce different SQL limits. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [SQLite materialization semantics](https://sqlite.org/lang_with.html).

After deployment, verify one live report and one equivalent request with irrelevant parameters, preserving the received bytes and cache headers. Do not refresh every filter in production to repeat coverage already established locally. Use metadata to inspect subsequent account usage.

Assess future changes by `measured reads per cold report × observed cold fills`, alongside ingestion and other account activity. Cache locality means a theoretical hourly hit rate is insufficient. If ordinary observed use still threatens the allowance, evaluate stored report generation or an indexed policy assessment, then compare their write and maintenance costs with a paid plan. An upgrade is a separate owner decision. No implementation here automatically changes billing.

## Failure scope and rollback

The free cap applies to D1 operations, including the newsletter database work sharing this account. Cloudflare states that D1 queries fail after the free daily read/write allowance is exhausted, until the midnight UTC reset. Static article responses do not await the analytics write; database-backed operations can still fail while pages remain readable. This is an availability risk, not evidence that the reported views were fabricated.

Code and assets deploy together. Preserve the corrected cache when rolling back aggregation changes if possible: returning to the original nine uncached statements restores the measured budget problem. Neither correction nor rollback requires rewriting observations or the referral policy. Record actual activation and live acceptance separately from the implementation commit.
