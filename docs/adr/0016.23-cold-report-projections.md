# ADR-0016.23: Query-specific public report projections

## Status

Accepted design, November 11, 2026 Pacific. Implementation and measured production acceptance are tracked in [the cold-report worklist](../../packages/blog/drafts/research/d1-read-budget/06-cold-report-performance-2026-11-11.md). Extends [the report cost decision](0016.7-budget-d1-reads-and-cache-public-reports.md) and its engine-regression exception. The availability repair remains complete.

## Context

A warm cache hides the cost of generating a report. The six-statement regression workaround materializes the same wide event selection repeatedly, carrying unrelated JSON evidence into simple chart queries. It also evaluates evidence validators before collapsing repeated identical evidence. A local 4,500-event diagnostic fixture takes about 1.1 seconds without network transport; current production cold duration needs separate measurement.

[D1 batches execute sequentially in one transaction](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Concurrent JavaScript calls cannot parallelize its single database. [D1's performance guidance](https://developers.cloudflare.com/d1/platform/limits/#concurrency-and-throughput) makes query execution time a throughput constraint. [SQLite materialized CTEs](https://sqlite.org/lang_with.html#materialization_hints) form optimization fences and can copy intermediate data into memory or temporary storage. More fences, fields or declared dependencies are not free.

## Decision

Optimize the reporting read model in the existing analytics bounded context. Each prepared statement declares the event columns and derived evidence projections its report sections actually use. Read and carry only those columns. Build only required evidence CTEs and keep population dependencies shallow. Assess distinct referral hosts directly from the source predicate, independently of wide event projections, and reuse numbered prepared bindings across those identical predicates. This avoids repeatedly expanding or copying a wide parent CTE for every aggregate. Retain explicit materialization where a reused population or expensive derived fact needs one evaluation; let SQLite optimize simple scope filters.

Group identical evidence inputs before interpretation, preserving the exact event multiplicity. A signature cohort includes the stored envelope, top-level status and, for joint reports, reader kind and whether a scalar name was selected. A network cohort includes the entire stored network envelope. Do not discard timestamps, canonicalize unknown fields or group solely by a convenient output status. Those changes could merge inputs with different interpretations.

Apply the existing domain policy functions to each distinct cohort, then aggregate its event weight. Every complete partition must still reconcile with the headline. Boolean marginals preserve SQL NULL behavior. Daily-client counts continue to use `COUNT(DISTINCT daily_client_id)` over events for their requested scope; summing dimensional client counts is invalid. Referral exclusions, owner exclusions, outgoing transitions, public hostname approvals, historical profiles and the global all-time boundary retain their existing contracts.

Keep one transactional batch for the complete report. The storage adapter partitions sections by their input/evidence responsibilities and the affected engine's tested expansion budget. A storage statement is not a new domain aggregate or a separate freshness boundary. Missing, duplicate, malformed or contradictory sections still reject the whole report. A faster partial report must not silently mix populations or clocks.

## Responsibilities

| Component | Responsibility |
|---|---|
| Observation/evidence policies | Retained facts and their existing historical interpretation; no request re-verification during reporting |
| SQL reporting adapter | Fixed column dependencies, cohort multiplicities, native-compatible prepared query plan and transactional execution |
| Report application service | One query/window/policy, strict decoding, reconciliation and public response assembly |
| Worker delivery | Validated canonical caching, coalescing, capacity, expiry and HTTP error behavior |
| Presentation | Render the unchanged complete report contract |

Use explicit function composition. Separate SQL planning from report assembly instead of adding a class hierarchy or putting database expressions in HTTP/UI code. This follows the [existing domain boundaries](0016-analytics-observation-semantics.md#domain-boundaries).

## Versioned observation reporting facts

The first production gate records 1.588-second and 1.350-second regional misses. Network/metadata interpretation consumes 564–629 ms of 934–989 ms total SQL. A narrow network-state projection reduces that work but its measured seven-day miss still takes 1.661 seconds: 835 ms SQL, 920 ms binding wall time and 335,259 reads. Keeping a validation status while carrying full envelopes through report aggregation is insufficient. These two failed gates justify compact per-observation reporting facts.

Migration 0019 creates disposable `page_observation_report_facts`: retained reporting dimensions, compact interpreted device/client/signature/directory facts, ordered nullable Boolean metric arrays, and closed Fetch Metadata/cache cohorts. It stores neither raw envelopes nor a complete report. Shared policy expressions build both the source interpreter and projection; the SHA-256 fingerprint covers the complete projection SQL and metric ordering. A changed interpretation requires a fingerprint and bounded rebuild decision. Existing raw observations remain authoritative and unchanged.

The observation application service projects only after source persistence is acknowledged. The source repository remains independent. Projection failure preserves the acknowledged source without replaying ingestion. A foreign key cascades deletion; any source update invalidates its fact row, including dimension repairs. Rebuilds skip current facts. A frozen ID window and per-batch meters bound delivery. Migration 0018's earlier network-state table remains additive rollback support; new ingestion maintains the complete projection instead.

The reporting adapter reads compact facts in a single two-statement transactional batch. A source coverage guard in that same transaction verifies current-rule facts cover the whole non-owner time window, which also covers selected and outgoing paths. The global all-time boundary is read from authoritative source even for an empty audience filter. Owner-registry exclusion, public hostname approval, time/filter selection and exact daily-client sets remain live read-time policies. Referral decisions are accepted only for the current rule fingerprint, as described below. Evidence facts collapse with exact multiplicities before summation.

If coverage is incomplete, discard the entire projected result and generate the whole report from source in a new transactional batch. Do not combine those snapshots or expose a partial report. This fallback can be slower during projection failure or rebuild; correctness and availability do not require a healthy projection. Read-model and source-fallback calculation costs are logged separately. A fallback report can have a later source snapshot than its discarded projection attempt.

Metric arrays preserve each original SQL NULL rather than converting unknown Boolean inputs into false. Their order belongs to the versioned storage schema; the public response retains named fields and strict reconciliation. Reports contain no projection writes. This design moves stable evidence interpretation to one optional derived write, while event counts, audience sets and mutable policy remain request-time responsibilities. It follows [materialized-view lifecycle guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view); [D1 foreign-key enforcement](https://developers.cloudflare.com/d1/sql-api/foreign-keys/) supports the disposable row lifecycle.

## Versioned referral decisions and the engine expansion budget

The compact five-part production candidate still takes 1.141 seconds (472.8 ms SQL, 247,310 reads). Its policy/population CTEs are expanded repeatedly, and wider combined candidates exceed the affected engine's counter even with compact evidence. Migration 0020 therefore adds a separate referral rule fingerprint and nullable exclusion bit to the same disposable observation facts. This is a versioned application of the current referral policy, not a new source fact or a public hostname approval.

The fingerprint commits to the policy artifact SHA and the shared SQL evaluator. Ingestion uses the same pure domain assessor already compared against that evaluator over the full rule catalogue. The projection write guards both observation ID and acknowledged referrer host; a concurrent source repair cannot persist an exclusion derived from an earlier host. Both evidence and referral facts are written together. Any source update still deletes the whole disposable fact row.

A bounded policy-only rebuild reads retained hosts from the fact table and applies the shared SQL precedence evaluator in one atomic UPDATE per ID range. It rewrites neither source evidence nor the expensive stable interpretations. Evidence and referral rules have separate fingerprints and rebuild lifecycles. A policy change must update its fingerprint and rebuild; queries with different policy rules use the complete source interpreter. Public hostname approval and owner registry changes remain immediately effective without a fact rebuild.

The report's transactional coverage guard requires both current fingerprints and a present exclusion bit. Its two prepared statements read the fact table directly and avoid recursive policy dependencies. A single statement still fails the affected runtime locally, so two remain the proven minimum. The complete source fallback retains five statements. No projected result is published after a failed coverage check, and no report mutates or repairs facts.

## Covering core reads and cardinality coverage

The two-part production candidate passes seven-day latency at 690 ms but its default 30-day miss takes 1.133 seconds. Core SQL accounts for 752.8 ms of 882.4 ms. Its native query plan builds repeated automatic indexes over a wide assessed population. Materialize the already-included chart population once, and let context/transition queries read their narrow covered source dimensions directly. Preserve outgoing path selection and exclusions.

Migration 0021 adds a partial covering index for non-owner facts: rule/date predicates, referral fingerprint/exclusion, and the exact scalar dimensions needed by core panels. Evidence payloads stay outside that index. Keep the smaller all-owner window index for evidence reads and owner-inclusive rebuild operations. This adds one index entry for a projected non-owner row; creation/storage and later write costs are explicit tradeoffs. [SQLite's covering-index guidance](https://www.sqlite.org/queryplanner.html#covering_indexes) explains avoiding base-row lookups; [D1 recommends checking plans and updating statistics](https://developers.cloudflare.com/d1/best-practices/use-indexes/).

Coverage uses two index-only counts in the same transaction: authoritative non-owner observations in the full window, and current evidence/referral facts in that same window. Fact rows form a one-to-one subset of observations: foreign keys prevent orphans, copied dimensions define the same window, and any source update invalidates its fact. Equal cardinalities therefore prove complete window coverage under that lifecycle. This is more conservative than the requested filter: missing registry-owner or otherwise excluded facts can also trigger the safe source fallback. Owner registry and public hostname policy still apply live when generating the report. No distinct-client count is replaced with a sum.

Verify covering searches for both counts and core source reads using native `EXPLAIN QUERY PLAN`. Compare identical reports with and without the covering index on the same populated fixture, separately from earlier query changes. The lookup/IO improvement does not imply an unlimited-scale bound; source fallback and larger populations remain separately observable.

## Alternatives and consequences

A durable materialized report could make common lookups cheap, but it requires refresh scheduling, invalidation, retention and initial/backfill behavior for every filter. [Materialized-view guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view) calls out those consistency and maintenance costs. [Fowler's CQRS guidance](https://martinfowler.com/bliki/CQRS.html) supports different read models within a bounded context while warning against unearned complexity. The measured query-side correction improves latency but misses the target; compact observation facts above are the measured follow-up.

Longer cache TTLs, public refresh bypasses, stale responses and cosmetic loading changes do not satisfy the cold-generation requirement. Keep the existing one-hour/midnight freshness bound. The initial query-only phase adds no projection table or ingestion write; the measured follow-up adds the disposable interpretations described above. No scheduled job or dependency is added. Add the missing `(is_owner, observed_at)` index through migration 0017 and keep the fresh-install schema equivalent. The existing owner/path and owner/traffic indexes do not provide the same owner-and-time range search when their middle key is unconstrained. Index creation and `PRAGMA optimize` are separate deployment steps; retained event values remain unchanged. The report remains proportional to the selected event population; these measurements are not an unlimited-scale guarantee. Wider windows and entirely distinct evidence need explicit scale controls.

Record per-statement SQL duration alongside row reads/writes, and distinguish database execution from request end-to-end time. Missing timing metadata stays unknown. Diagnostics must remain closed and omit raw SQL, parameters, private hosts and provider messages. [D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/) defines these counters and timings.

## Acceptance and rollback

Compare exact reports with a frozen pre-change implementation across selectors and mixed valid/invalid/historical records. Test repeated and distinct evidence at meaningful sizes through native D1, including the affected Workerd runtime. Run types, analytics/site suites, validation, isolated build and Worker dry-run. Then join deployed source/version and measure a bounded cold request plus a cache repeat; local runtime numbers do not prove production latency.

Version the report cache for the implementation change. Rollback restores the earlier query adapter and its matching cache namespace; it must preserve the engine workaround and complete-result checks. Retained observations are preserved. Rollback can retain the additive projection schema; old code ignores it.
