# ADR-0016.23: Query-specific public report projections

## Status

Accepted design, November 11, 2026 Pacific. Implementation and measured production acceptance are tracked in [the cold-report worklist](../../packages/blog/drafts/research/d1-read-budget/06-cold-report-performance-2026-11-11.md). Extends [the report cost decision](0016.7-budget-d1-reads-and-cache-public-reports.md) and its engine-regression exception. The availability repair remains complete.

## Context

A warm cache hides the cost of generating a report. The six-statement regression workaround materializes the same wide event selection repeatedly, carrying unrelated JSON evidence into simple chart queries. It also evaluates evidence validators before collapsing repeated identical evidence. A local 4,500-event diagnostic fixture takes about 1.1 seconds without network transport; current production cold duration needs separate measurement.

[D1 batches execute sequentially in one transaction](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). Concurrent JavaScript calls cannot parallelize its single database. [D1's performance guidance](https://developers.cloudflare.com/d1/platform/limits/#concurrency-and-throughput) makes query execution time a throughput constraint. [SQLite materialized CTEs](https://sqlite.org/lang_with.html#materialization_hints) form optimization fences and can copy intermediate data into memory or temporary storage. More fences, fields or declared dependencies are not free.

## Decision

Optimize the reporting read model in the existing analytics bounded context. Each prepared statement declares the event columns and derived evidence projections its report sections actually use. Read and carry only those columns. Build only required evidence CTEs and keep population dependencies shallow. Assess distinct referral hosts directly from the source predicate, independently of wide event projections, and reuse numbered prepared bindings across those identical predicates. This avoids repeatedly expanding or copying a wide parent CTE for every aggregate. Retain explicit materialization where a reused population or expensive derived fact needs one evaluation; let SQLite optimize simple scope filters.

Group identical evidence inputs before interpretation, preserving the exact event multiplicity. A signature cohort includes the stored envelope, top-level status and, for joint reports, reader kind and whether a scalar name was selected. A network cohort includes the entire stored network envelope. Do not discard timestamps, canonicalize unknown fields or group solely by a convenient output status. Those changes could merge inputs with different interpretations.

Apply the existing domain policy functions to each distinct cohort, then aggregate its event weight. Every complete partition must still reconcile with the headline. Boolean marginals preserve SQL NULL behavior. Daily-client counts continue to use `COUNT(DISTINCT daily_client_id)` over events for their requested scope; summing dimensional client counts is invalid. Referral exclusions, owner exclusions, outgoing transitions, public hostname approvals, historical profiles and the global all-time boundary retain their existing contracts.

Keep one transactional batch for the complete report. The storage adapter partitions sections by their input/evidence responsibilities and the affected engine's tested expansion budget. A storage statement is not a new domain aggregate or a separate freshness boundary. Missing, duplicate, malformed or contradictory sections still reject the whole report. A faster partial report must not silently mix populations or clocks.

## Responsibilities

| Component | Responsibility |
|---|---|
| Observation/evidence policies | Retained facts and their existing historical interpretation; no request re-verification during reporting |
| SQL reporting adapter | Fixed column dependencies, cohort multiplicities, native-compatible prepared query plan and transactional execution |
| Report application service | One query/window/policy, strict decoding, reconciliation and public response assembly |
| Worker delivery | Validated canonical caching, coalescing, capacity, expiry and HTTP error behavior |
| Presentation | Render the unchanged complete report contract |

Use explicit function composition. Separate SQL planning from report assembly instead of adding a class hierarchy or putting database expressions in HTTP/UI code. This follows the [existing domain boundaries](0016-analytics-observation-semantics.md#domain-boundaries).

## Versioned network interpretation projection

The first production gate records 1.588-second and 1.350-second regional misses. Their network/metadata statement takes 564–629 ms of 934–989 ms total SQL. This fails the sub-second goal and justifies persisting the narrow network interpretation under the materialized-view gate.

Keep one disposable `page_observation_network_facts` row per observation with a non-null network envelope: its observation ID, the SHA-256 fingerprint of the reporting rule, and its closed interpretation state. The original envelope remains in `page_observations`; reports continue to apply owner, referral, time and audience predicates there. The read projection does not authenticate a vendor or recheck addresses.

The observation application service invokes the projector after source persistence is acknowledged. The source repository remains independent. Projection failure preserves the acknowledged source without retrying ingestion. A foreign key cascades source deletion, and a trigger invalidates the projection on any network-envelope update. Reports join only the current rule fingerprint and lazily run the exact validator for missing/stale facts. No unknown or invalid evidence becomes a recognized record through absence of a projection.

A test pins the fingerprint to the exact SQL interpreter, making interpretation changes require an explicit version/rebuild decision. Backfill a frozen observation-ID range in bounded primary-key chunks, recording every read/write meter and source high-water mark. Migration 0018 creates only this table and invalidation trigger; it updates no retained observation. Apply schema before activation and backfill before accepting cold latency. New writes project forward, while any concurrent unprojected rows retain the correct fallback.

This moves expensive structural interpretation to the projection write path while preserving request-time cohort counts and cache-policy summaries. It adds one optional derived write for acknowledged observations and a small rebuild lifecycle; these costs require measured acceptance. SQLite documents [lazy CASE evaluation](https://sqlite.org/lang_expr.html#the_case_expression), and [D1 enforces foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/) within queries/migrations.

## Alternatives and consequences

A durable materialized report could make common lookups cheap, but it requires refresh scheduling, invalidation, retention and initial/backfill behavior for every filter. [Materialized-view guidance](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view) calls out those consistency and maintenance costs. [Fowler's CQRS guidance](https://martinfowler.com/bliki/CQRS.html) supports different read models within a bounded context while warning against unearned complexity. The measured query-side correction improves latency but misses the target; the network interpretation projection above is the bounded next step.

Longer cache TTLs, public refresh bypasses, stale responses and cosmetic loading changes do not satisfy the cold-generation requirement. Keep the existing one-hour/midnight freshness bound. The initial query-only phase adds no projection table or ingestion write; the measured follow-up adds only the network interpretation projection described above. No scheduled job or dependency is added. Add the missing `(is_owner, observed_at)` index through migration 0017 and keep the fresh-install schema equivalent. The existing owner/path and owner/traffic indexes do not provide the same owner-and-time range search when their middle key is unconstrained. Index creation and `PRAGMA optimize` are separate deployment steps; retained event values remain unchanged. The report remains proportional to the selected event population; these measurements are not an unlimited-scale guarantee. Wider windows and entirely distinct evidence need explicit scale controls.

Record per-statement SQL duration alongside row reads/writes, and distinguish database execution from request end-to-end time. Missing timing metadata stays unknown. Diagnostics must remain closed and omit raw SQL, parameters, private hosts and provider messages. [D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/) defines these counters and timings.

## Acceptance and rollback

Compare exact reports with a frozen pre-change implementation across selectors and mixed valid/invalid/historical records. Test repeated and distinct evidence at meaningful sizes through native D1, including the affected Workerd runtime. Run types, analytics/site suites, validation, isolated build and Worker dry-run. Then join deployed source/version and measure a bounded cold request plus a cache repeat; local runtime numbers do not prove production latency.

Version the report cache for the implementation change. Rollback restores the earlier query adapter and its matching cache namespace; it must preserve the engine workaround and complete-result checks. Retained observations are preserved. Rollback can retain the additive projection schema; old code ignores it.
