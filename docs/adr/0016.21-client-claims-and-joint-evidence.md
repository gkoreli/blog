# ADR-0016.21: Improve client detection without inventing identities

## Status

Implementation and local acceptance in progress, November 5, 2026 Pacific / November 6 UTC. Source delivery, deployment activation and production acceptance are separate gates in the [worklist](../../packages/blog/drafts/research/analytics-retrospective/128-detection-improvement-worklist.md). Extends [classification uncertainty](0016.12-explicit-classification-uncertainty.md), [versioned observations](0016.9-observation-provenance-and-referrer-boundaries.md), [identity methods](0016.13-verification-outcomes-and-vendor-methods.md), [joint signature reporting](0016.17-joint-classification-and-signature-report.md) and [provider-method provenance](0016.20-provider-method-updates-and-receipt-display-provenance.md).

## Problem and evidence

The dated [seven-day public report](../../packages/blog/drafts/research/analytics-retrospective/127-current-unidentified-and-unsigned-traffic.md) contains 3,960 included events, with 2,810 lacking a selected scalar client name and 3,250 explicitly unsigned. Those are different dimensions. [A joined production aggregate](../../packages/blog/drafts/research/analytics-retrospective/132-joined-client-evidence-and-retained-headers.md) finds exactly eight generic-token, unnamed, unsigned events carrying provider `AI Crawler` category and two with `AI Search`. Its 85,639 reads exceed the planned 50,000-read review threshold; the result is complete, but the cost gate fails and is not retried.

Three reproducible cases in [the domain audit](../../packages/blog/drafts/research/analytics-retrospective/130-detection-domain-audit.md) show why adding more regular expressions is insufficient:

- A URL ending in `/robot` creates a generic bot result even when the software products are unchanged. CUBOT phone-brand and Phantom-wallet strings also match the broad fallback.
- Independent parsers recognize Chromium-family names but disagree about Chrome, Chromium and lowercase browser-version support. This changes the explanation for missing context without authenticating any browser.
- Two compatible known client names intentionally select no scalar name. Subtracting the named table from the headline therefore cannot universally mean zero recognized declarations.

The [pinned OSS source review](../../packages/blog/drafts/research/analytics-retrospective/129-oss-detection-source-review.md) and [source ledger](../../packages/blog/drafts/research/analytics-retrospective/2026-11-06-oss-detection-source-ledger.json) inspect ten public repositories. They separate source inspection, supplied fixture execution, first-party role documentation and production observations. Upstream test labels and overlapping datasets are not independent operator labels or population accuracy measurements.

## Distilled source lessons

| Source evidence | Useful lesson | Boundary retained here |
|---|---|---|
| Matomo's ordered bot parser and separate browser/library parsers | Model client software and declared roles explicitly; use parser precedence deliberately | First-match selection can hide multiple claims; retain all candidates |
| isbot's cached matcher, update tooling and CUBOT/Phantom browser controls | Cache current rule structures and test plausible false positives against public corpora | A boolean match and a publisher URL do not authenticate an operator; correlated datasets do not corroborate one another independently |
| crawler-user-agents' versioned regex data, examples and updater | Use pinned external data to discover candidates and create a reviewable refresh diff | Do not silently import the entire rule set or promote its labels into verified identity |
| GoatCounter's filtering boundary and bot dependency | Understand what a product excludes before comparing its totals | Exclusion-oriented tools answer a different question from an all-audience evidence report |
| Plausible's separate parser/library and data pins | Version implementation, catalogue and retained evidence independently | An application dependency declaration does not establish uninspected dependency behavior |
| Primary vendor docs and HTTP-library defaults | Recognize documented exact product aliases and distinguish SEO, AI crawling and HTTP software | Defaults can be overridden; a name, library or vendor association does not establish purpose or human initiation |

The source review links each claim to pinned files and line ranges. It records licence declarations without copying competitor implementation code or introducing a runtime detector dependency. Unresolved first-party roles remain deferred rather than inferred from a name.

## Decision

### Keep domain claims and identity checks separate

Use one current [client registry](../../packages/analytics/src/client-registry.ts) for canonical names, exact product aliases, coarse compatibility class, declared reader kind and source/review basis. Derive name types, match lookup and role lookup from it. Existing signatures, published-IP checks, provider categories and publisher-directory assessments keep their distinct domain contracts and method scopes. Tests require every configured method's declaration names to exist in the registry, without turning a reviewed key directory into a promise that every product signs.

The first profile contains 63 names and 74 aliases, preserving the original 52 clients' declared roles. Added entries have source-reviewed scopes: SEO clients, AI2Bot, three HTTP libraries and the documented Checkly product marker. An absent method means unconfigured locally, not impossible to verify. Historical declaration/network snapshots remain frozen; append a new supported profile and reviewed pair instead of deriving past records from today's registry.

### Share lexical claim boundaries

The [shared lexical value](../../packages/analytics/src/user-agent-products.ts) owns product-name/version boundaries for declared names, browser support and optional detailed browser evidence. Generic automation matching uses lexical products rather than the whole header. Preserve bare bot/spider/crawler conventions, with narrow source-backed CUBOT phone/model and Phantom-wallet exceptions that do not hide a separately appended bot product. Keep iOS capability distinct from desktop Chrome/Firefox claims, and abstain on malformed or conflicting major/minor versions of one claimed engine.

Later article review reproduced a remaining semicolon escape: `https://example.test/path;UnknownBot/1.0` still supplied a generic product, and a contiguous URI could supply a named GPTBot. Mask recognized absolute-URI spans before product matching. An ASCII scheme starts the span; semicolons, userinfo, query and fragment data stay within it. Whitespace or an unmatched close parenthesis ends it; balanced parentheses and backslash-escaped non-whitespace characters stay inside. Use a non-boundary placeholder so masking cannot manufacture a valid product from a malformed prefix. Preserve real products before a URI or after a genuine separator. This is a bounded lexical contract: schemeless references, complete URI validity and full User-Agent/comment grammar remain unsupported. No hostname establishes a role, no URI is fetched and no arbitrary prefix truncation is introduced.

The same URI-excluded claim text supplies iOS capability and optional OS parsing. Optional browser family/version uses the shared exact products, retaining its Edge/Opera/Firefox/Chromium/Safari vocabulary. Thus a URI path containing `Chrome/150.0` cannot become an optional browser claim, and an iOS phrase cannot borrow its first word from a masked URI. These repairs change derived interpretation, not raw capture scope.

One shared conflict rule rejects selection between Firefox/FxiOS and Chrome/Chromium/CriOS/Edg/EdgA/EdgiOS/OPR claims. The routine browser family becomes unrecognized, the optional selected family/version becomes unknown/null, and capability is not positively claimed. Known named crawler or HTTP-software roles remain independent. Normal Chrome+Safari and Chrome+Edge/Opera combinations survive. This rule does not independently reject Edge+Opera or mixed iOS/desktop spellings outside that explicit conflict; it is not a complete engine detector or browser-execution test.

Modern client-form evidence uses URI-excluded lexical markers under profile `2026-11-06.1`; reports also recognize the unchanged earlier `2026-10-27.1` profile. The envelope shape is unchanged. Preserve `classifyDevice`'s deprecated raw-UA compatibility heuristic, including its URL substring behavior: a URI mentioning iPad can retain legacy tablet while the modern form stays unknown. That counterfactual is labelled legacy evidence, not a hardware claim. Optional request evidence uses its prospective `2026-11-06.1` version; collection/classifier provenance also dates the new interpretation. No historical value is recalculated.

Reject the attempted rule that requires every unknown bot suffix to have a version. It reduces existing matches too broadly in the supplied corpora. The [audit's comparison](../../packages/blog/drafts/research/analytics-retrospective/130-detection-domain-audit.md#local-lexical-candidate-and-rejected-recall-tradeoff) records the rejected and retained outcomes and the remaining URL/malformed-token losses. Those changed strings are visible tradeoffs, not measured false-positive/negative rates. Removing a weak bot match must not directly create a human verdict; ordinary context/network rules still apply.

### Store complete evidence inside the existing budget

The expanded complete declaration set produces 2,378 bytes under the old repeated-array format, exceeding the database's 2,048-byte classification-evidence constraint. Do not truncate candidates, discard aliases, weaken the check or rebuild the production table merely to enlarge the allowance.

Use a [frozen product profile and hexadecimal bitset](../../packages/analytics/src/retained-client-products.ts) for matched product aliases. Retain candidate names, status and browser family. Bit positions belong to an explicit immutable historical ordering; a future catalogue change requires a new profile. The decoder preserves old array formats and returns unknown for unsupported schemas/profiles, mixed encodings, malformed values and out-of-range bits. It decodes a field, not the complete record's authenticity or coherence.

The conservative all-name/all-alias fixture is 1,355 bytes, leaving 693 bytes under the existing limit. Actual local workerd D1 insertion/readback and oversized-JSON rejection pass. Collection, classifier and classification-schema profiles become `2026-11-06.1`; the cryptographic verifier profile is unchanged. Fetch Metadata recognition requires the explicit new schema/classifier pair while retaining earlier supported pairs. No old row is rewritten and no database migration is needed.

### Report names, provider roles and signatures on the same events

Add `clientNameCoverage` and `byKindClientEvidence` under the existing selected/excluded population. Name selection is explicitly **one selected name** versus **no single selected name**; the second includes no match, multiple matches and missing earlier detail. It is not an unknown-person or unsigned-client counter.

The joint table crosses stored kind, name-selection state, provider category, signature basis and verifier profile. A shared materialized relation supplies the joint table and existing category/signature tables. Each included event appears once. Server and client validate complete counts, unique rows, name totals and exact category/signature marginals; malformed facts do not become plausible zeros. Aggregated marginals cannot independently prove an arbitrary event correlation; the SQL and native supplied-record controls establish that join within their test scope.

The blog presents two plain-language name-coverage counts and an optional, horizontally scrollable detailed table. A software name is a claim; a provider category supplies independent role evidence; signatures authenticate covered components. An unsigned request may still match a published vendor address range elsewhere in the report. No ordinary-browser signature requirement is introduced.

### Reuse existing logs before expanding collection

Authenticated retained Worker logs already expose the original UA for immediate catalogue leads. The bounded dashboard review finds additional product strings but does not establish their operator, purpose, completeness or exact D1 correlation. Do not enable new raw diagnostics to solve a question those existing sources can answer. This release changes derived parsing/catalogue facts and their lossless representation; it adds no raw header/address fields or retained identifiers. Optional request-evidence form semantics receive their own prospective version; existing raw-capture settings remain unchanged.

## Alternatives considered

| Alternative | Decision and rationale |
|---|---|
| Adopt isbot's boolean as the final classification | Reject: useful candidates and fixtures, insufficient identity/role distinctions and different false-positive tradeoffs |
| Import Matomo's entire parser/data stack | Defer: broader device/library taxonomy is useful prior art, but PHP runtime, ordered first-match behavior and unreviewed scope do not fit this Worker evidence contract |
| Ship all crawler-user-agents patterns | Reject automatic adoption: improve candidate discovery offline and review exact supported products before production |
| Let provider categories overwrite local classifications | Reject: preserves neither independent evidence nor historical rule provenance; categories also have missing/empty states |
| Require a version on every unknown bot suffix | Reject after corpus comparison: loses too many supported bare lexical conventions |
| Add raw UA logging now | Reject for this release: already-retained operational sources answer immediate leads; no new data field is justified |
| Increase storage allowance or truncate candidate lists | Reject: a versioned lossless codec preserves complete facts inside the existing constraint |
| Merge all identity methods into one verified flag | Reject: method coverage, missingness, signed components and provider/network attribution answer different questions |

## Acceptance and remaining limits

Earlier integrated acceptance had **419 passing analytics tests** and workspace typechecks in an isolated checkout. The subsequent **427-test** baseline passes before the cross-family conflict repair. A fresh isolated compilation and **50 focused tests** pass after that repair, covering the lexer, registry, optional evidence, modern/legacy forms, classification producer and codec/history. Another 6,048 local unordered named-client-pair × injected-signature cases preserve role/ambiguity invariants; those injected verdicts do not verify cryptographic proofs. These are successive scopes, not additive test counts or final whole-suite acceptance. The shared joint table's missing/duplicate/corrupted-record controls include an independently found duplicate-marginal acceptance defect repaired before release. Final integrated checks and release receipts will be linked separately.

The earlier native harness compares thirteen selectors over the same 512 synthetic records in Node SQLite and actual local workerd D1. All values agree, and all common baseline report values agree after unordered table comparison. The first all-audience selection costs **36,847 baseline reads → 38,169 candidate reads**, a 1,322-read / approximately 3.6% increase with zero writes. This is a measured local cost for the added joint information, not production savings or a global read bound. It does not stand for final composed acceptance of the later URI, optional-evidence and browser-conflict repairs. The earlier production aggregate's failed cost gate remains visible. Initial sandbox loopback denial and two schema-loader mistakes belong to the harness record; they are not production failures.

Before release, complete the isolated site tests/validation/build, actual composed-Worker collector/storage/report controls, desktop/mobile/error/recovery checks, exact source delivery, activation association and bounded served/API/cache acceptance. Record new observations under their actual versions. Existing provider booleans remain unavailable in the measured production scope; no native oracle or human-accuracy claim follows.

Catalogue expansion does not recover original unknown tokens from historical zero-candidate records or identify browser operators. Checkly plus a separately declared headless engine can remain a multiple-category ambiguity. Corpus matches do not prove software execution, intent, benign behavior, training, indexing, reading or citation. The broader TASK-0119 retains its separate measurement questions.
