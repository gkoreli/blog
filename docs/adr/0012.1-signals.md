# ADR-0012.1: Animation Signals — Inverting Input Ownership

## Status

Design — 2026-04-16. Supersedes the input-tracking section of ADR-0012. Implementation pending.

---

## Context

ADR-0012 established the pipeline contract: `tick() → effects → draw()`. The pipeline correctly decouples animations from effects. But there is a remaining coupling that the pipeline contract doesn't address: **effects own their input sources**.

In the current implementation, `cursorRepulsion` calls `createCursorForce(container)` internally. The effect creates, owns, and disposes its own cursor tracking:

```
cursorRepulsion
  └── createCursorForce()
        ├── document.addEventListener('mousemove')
        └── requestAnimationFrame(smooth)   ← its own rAF loop
```

This is fine for one effect. It breaks down immediately when you try to share:

```ts
animate(caustic())
  .pipe(cursorRepulsion(host))   // creates cursorForce #1 → rAF loop #1, listener #1
  .pipe(cursorAttraction(host))  // creates cursorForce #2 → rAF loop #2, listener #2
  .start(canvas, container)
```

Two effects with the same input need create two independent tracking instances. N effects on the same signal = N listeners, N rAF loops, N separate smoothed state objects that diverge by a frame from each other.

There are also effects that would naturally combine multiple inputs — a `magneticField` effect might respond to both cursor position and scroll velocity simultaneously. In the current model it would have to own both tracking instances internally. The effect becomes responsible for orchestrating its inputs rather than just transforming points.

The underlying problem: **input tracking is infrastructure, not domain logic.** An effect's domain is transforming `AnimationPoint[]`. Cursor tracking, scroll observation, clock ticking — these are plumbing. Conflating them with the effect means effects can't be composed freely, can't be shared, and can't be tested in isolation.

The signal design inverts this: **callers create inputs, effects receive them.**

---

## Decision

Introduce a `Signal<T>` abstraction as the standard way to represent time-varying input to the animation pipeline. Effects declare which signals they depend on. The runner discovers those dependencies, deduplicates them, and owns their lifecycle.

### Signal Contract

```ts
interface Signal<T> {
  /** Read the current value — called once per frame by effects. Pull model. */
  read(): T;

  /** Called by runner when canvas goes off-screen. Stop background work. */
  pause(): void;

  /** Called by runner when canvas returns to view. Resume background work. */
  resume(): void;

  /** Called by runner on final cleanup. Release all resources. */
  dispose(): void;
}
```

Pull, not push. At 60fps you're sampling every frame regardless — push notifications add subscription management overhead for zero benefit over continuous signals. `read()` returns the latest smoothed value at call time.

### Effect v2 Contract

Effects gain a `signals` field that declares dependencies:

```ts
interface Effect {
  /** Declared signal dependencies — runner uses these for lifecycle management. */
  signals?: Signal<unknown>[];

  apply(points: AnimationPoint[], ctx: EffectContext): AnimationPoint[];
  dispose?(): void;
  // pause/resume removed from Effect — runner drives signals directly
}
```

`pause` and `resume` are removed from `Effect`. They were only there to forward lifecycle events to embedded tracking instances. With signals extracted, effects no longer have background work to pause. Only signals do.

### Runner Changes

The runner collects signals from all effects at `start()` time, deduplicates by reference identity, and owns their lifecycle:

```ts
// Inside AnimationRunner.start():
const signals = [...new Set(effects.flatMap(e => e.signals ?? []))];

// IntersectionObserver:
if (intersecting) {
  for (const s of signals) s.resume();
  running = true; raf = requestAnimationFrame(frame);
} else {
  running = false; cancelAnimationFrame(raf);
  for (const s of signals) s.pause();
}

// Cleanup:
return () => {
  for (const s of signals) s.dispose();
  for (const e of effects) e.dispose?.();
  mod.dispose?.();
  // disconnect observers...
};
```

Deduplication by reference means two effects sharing the same signal instance get exactly one lifecycle call. The signal is paused once, resumed once.

### Call Site

```ts
const cursor = cursorSignal(container);
const time   = clockSignal();

const stop = animate(caustic())
  .pipe(cursorRepulsion({ signal: cursor, magnitude: 18 }))
  .pipe(cursorAttraction({ signal: cursor, radius: 0.2 }))  // same signal, one rAF loop
  .pipe(turbulence({ signal: time, frequency: 0.4 }))
  .start(canvas, container);
```

Two effects read the same `cursor` signal. One `mousemove` listener. One smoothing loop. One lifecycle. The runner sees `cursor` twice in the deduplicated set and manages it once.

## Signal Types

### `cursorSignal(container)`

```ts
interface CursorValue {
  x:        number;   // normalized 0–1 within container
  y:        number;
  strength: number;   // 0 off-screen, smoothly rises to 1 on enter
  vx:       number;   // frame-over-frame velocity (normalized)
  vy:       number;
}

function cursorSignal(container: HTMLElement): Signal<CursorValue>
```

Wraps `createCursorForce()`. Document-level `mousemove`, bounding rect test, dual lerp rates. The rAF smoothing loop is driven by `resume()`/`pause()` rather than auto-starting. `read()` returns the current `CursorForce` object — zero-copy, no allocation.

### `clockSignal()`

```ts
interface ClockValue {
  t:  number;   // frame counter — same t as the runner's
  dt: number;   // ms since last frame — actual elapsed, not TARGET_MS
}

function clockSignal(): Signal<ClockValue>
```

Provided by the runner itself. The runner calls `clock.tick(now, t)` at the top of each frame before `applyEffects`. Effects that want time-based behavior use this rather than relying on the `EffectContext.t` integer — `dt` enables frame-rate-independent physics.

The runner creates one `clockSignal` internally and exposes it to effects via `EffectContext`:

```ts
interface EffectContext {
  w:     number;
  h:     number;
  t:     number;
  clock: ClockValue;   // added in v2
}
```

`clockSignal()` as a standalone factory is for effects that want to be wired explicitly (useful for testing or for effects used outside the runner).

### `scrollSignal()`

```ts
interface ScrollValue {
  y:        number;   // scrollY in px
  progress: number;   // 0–1 through document height
  velocity: number;   // px/frame — smoothed
  direction: 1 | -1 | 0;
}

function scrollSignal(): Signal<ScrollValue>
```

`window.addEventListener('scroll', ..., { passive: true })`. Velocity computed as a lerped delta between frames. Used for effects that should respond to page scroll — a `parallaxShift` effect, or a `scrollTurbulence` that increases noise amplitude while the user is scrolling.

### `mediaSignal(query)`

```ts
function mediaSignal(query: string): Signal<boolean>
// e.g. mediaSignal('(prefers-reduced-motion: reduce)')
```

Wraps `window.matchMedia(query)`. `read()` returns the current boolean. The `change` event updates it. No rAF loop needed — `pause()`/`resume()`/`dispose()` just add/remove the change listener.

This is the right gate for accessibility: an effect can check `motionSignal.read()` in `apply()` and return `points` unchanged when motion is reduced, without baking that logic into every animation module.

### `derived(source, transform)`

```ts
function derived<A, B>(
  source: Signal<A>,
  transform: (value: A) => B,
): Signal<B>
```

Creates a new signal that reads from `source` and applies `transform` synchronously. No memoization needed in the pull model — the transform runs at `read()` time once per frame.

```ts
// Half-strength cursor for a subtler effect
const gentleCursor = derived(cursor, v => ({ ...v, strength: v.strength * 0.5 }));

// Cursor signal with coordinate system flipped
const invertedCursor = derived(cursor, v => ({ ...v, x: 1 - v.x, y: 1 - v.y }));
```

`derived` forwards `pause()`/`resume()`/`dispose()` to its source. It is transparent to the runner's deduplication: if two derived signals share the same source, the runner will call `pause()` on each derived signal, which each forward to the source — the source gets `pause()` called twice. The source must therefore be **idempotent on pause/resume** (no-op if already paused, no-op if already running). The cursor-force implementation already satisfies this (`if (active) return` guard).

### `combinedSignal(signals, combine)`

```ts
function combinedSignal<T>(
  sources: Signal<unknown>[],
  combine: (...values: unknown[]) => T,
): Signal<T>
```

Reads multiple signals and combines their values. Used for effects that depend on more than one input:

```ts
const magnetism = combinedSignal(
  [cursor, scroll],
  (c: CursorValue, s: ScrollValue) => ({
    x: c.x,
    y: c.y + s.velocity * 0.001,   // scroll nudges the field
    strength: c.strength,
  })
);

animate(caustic())
  .pipe(cursorRepulsion({ signal: magnetism }))
  .start(canvas, container)
```

`combinedSignal` exposes its sources in its own `signals` field so the runner can discover and deduplicate them.

## Effect v2 Implementation Pattern

Before (v1 — effect owns source):

```ts
export function cursorRepulsion(container: HTMLElement, opts = {}): Effect {
  const { force, pause, resume, cleanup } = createCursorForce(container);
  // ...
  return {
    apply(points, { w, h }) { /* reads force.x, force.y */ },
    pause()   { pause(); },
    resume()  { resume(); },
    dispose() { cleanup(); },
  };
}
```

After (v2 — effect receives signal):

```ts
export function cursorRepulsion(
  opts: { signal: Signal<CursorValue>; magnitude?: number; damping?: number; radius?: number }
): Effect {
  const { signal, magnitude = 18, damping = 0.88, radius = 0.38 } = opts;
  const vel: { vx: number; vy: number }[] = [];

  return {
    signals: [signal],   // declare dependency — runner owns lifecycle

    apply(points, { w, h }) {
      const { x, y, strength } = signal.read();   // pull once per frame
      // ...same physics as before...
    },
    // no pause, resume, or dispose — nothing left to own
  };
}
```

The effect shrinks to pure domain logic. It declares what it reads, does its transform, returns the result. No lifecycle management.

## What Stays the Same

The pipeline contract (`AnimationModule`, `Effect`, `applyEffects`, `AnimationRunner`) is unchanged at the call site and inside modules. v1 effects continue working — `signals` is optional, `pause`/`resume` on `Effect` remain accepted (for any effect that genuinely needs its own background work separate from a signal).

The migration path for existing effects is mechanical:

1. Extract the `createCursorForce()` call to a signal
2. Change the function signature to accept `Signal<CursorValue>` instead of `HTMLElement`
3. Replace `force.x` with `signal.read().x`
4. Remove `pause`, `resume`, `dispose` from the effect return
5. Add `signals: [signal]`

The caller gets one new line: `const cursor = cursorSignal(container)`.

## Alternatives Considered

### Push / Observable model (RxJS-style)

Signals emit values, effects subscribe. Rejected for continuous animation inputs: at 60fps you pull every frame regardless — subscriptions add overhead (call stack, subscription tracking) for no benefit. Push is the right model for discrete events (clicks, keystrokes). For continuous values sampled every frame, pull is correct.

If the engine later needs to handle discrete events (e.g., an effect that triggers on click), those can be modeled as a `Signal<boolean>` that reads `true` for one frame after the event, then returns to `false`. Pull handles it cleanly.

### Context injection (pass signals through `EffectContext`)

Add a `signals` map to `EffectContext` that the runner populates before calling `apply()`. Effects pull from `ctx.signals.cursor` rather than from a captured reference.

Rejected because: it loses type safety (effects would need to cast), it couples the runner to a known set of signal names, and it makes effect dependencies invisible (you can't see what an effect reads without reading its implementation). Explicit argument injection (`{ signal: cursor }`) is self-documenting.

### Signal-less sharing via singleton registry

A global registry keyed by container element, so multiple effects requesting `cursorSignal(container)` return the same instance. Rejected: global state, implicit sharing, difficult to reason about lifetime. Explicit sharing (`const cursor = cursorSignal(container); pipe(repulsion(cursor)); pipe(attraction(cursor))`) is always clear.

### `use()` on the runner for explicit signal registration

```ts
const cursor = cursorSignal(container);
animate(caustic()).use(cursor).pipe(repulsion({ signal: cursor })).start(...)
```

Rejected in favor of auto-discovery via `effect.signals[]`. Requiring `.use()` is redundant — if an effect depends on a signal, the declaration is already in `effect.signals`. Making callers also register it manually is a double-declaration invariant that will drift.

## Open Questions

**Q: Should `clockSignal` be implicit or explicit?**

Option A — implicit: runner provides `clock` in `EffectContext` always. Effects that want `dt` just read `ctx.clock.dt`. No signal instance, no registration.

Option B — explicit: `clockSignal()` factory, effects declare `signals: [time]`, same pattern as cursor.

Leaning toward implicit for `clock` since it's universal infrastructure (every frame has a time), but explicit for all external inputs (cursor, scroll, media). The `EffectContext` already carries `t` and `w`/`h` — `dt` is a natural addition, not a signal.

**Q: Should `derived` participate in deduplication?**

If two derived signals share a source, `pause()` is called on the source twice. Source must be idempotent. Currently cursor-force satisfies this but it's an informal contract. v2 should make it explicit — either document the requirement or add a ref-count wrapper.

**Q: `AnimationPoint` metadata for non-positional signals?**

Some effects want to carry per-point data through the pipeline that isn't position — color tint, opacity, scale. Currently there's no channel for this. An optional `meta?: Record<string, number>` field on `AnimationPoint` would let effects communicate downstream without breaking the positional contract. Deferred — the current use cases don't require it, and adding untyped metadata to every point adds overhead.
