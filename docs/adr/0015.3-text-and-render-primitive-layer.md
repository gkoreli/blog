# ADR-0015.3: Text semantics and renderer primitive layer for the animation runtime

* **Status:** Proposed
* **Date:** 2026-04-20
* **Owner:** Goga Koreli
* **Decision Type:** Runtime architecture / renderer vocabulary / product correction
* **Related:**

  * **ADR-0015**: Adopt a Pixi-backed custom animation runtime for gkoreli.com
  * **ADR-0015.1**: Initial substrates, authoring model, and event/pipeline runtime architecture
  * **ADR-0015.2**: Animations Lab design for gkoreli.com

---

## 1. Context

The animation package now has a useful runtime core:

* scene declarations
* compilation into runtime plans
* particle stores
* field influence
* zone occupancy
* event hooks
* effect pipelines
* material channels
* Pixi-backed mounting and rendering

That work is real.

However, the visible output does not yet reflect the architecture underneath.

The current renderer surface is still effectively:

* particles
* circles
* small alpha / color / radius changes
* field-driven motion

This creates a major mismatch:

> the runtime is semantically richer than the renderer.

As a result, lab concepts such as **Text Emergence**, **Memory Zone**, and **Fracture Pulse** collapse visually into "dots appearing and moving randomly."

That is not a failure of the runtime core. It is a missing visual primitive layer.

---

## 2. Problem Statement

The current system can author concepts that the renderer cannot express.

Examples:

| Concept | Current authoring meaning | Current visible result |
| --- | --- | --- |
| Text source | Text-box emitter / editorial source region | Particles spawn from a rectangle |
| Semantic zone | Spatial region with occupancy and events | Mostly invisible math or weak overlay |
| Material identity | Glow, electric, ghost, trail, emissive hints | Mostly circle color / alpha / radius |
| Fracture event | Burst / instability / rupture semantics | Electric-colored dots |
| Text emergence | Language becomes source of motion | Text is not actually part of the runtime |

The abstraction tree has outrun the visual language.

The package must now shift from **simulation-first architecture** to **visual primitive architecture**, without throwing away the runtime core.

---

## 3. Decision

We will introduce a renderer-neutral visual primitive layer for `@gkoreli/animation`.

The next milestone is not "finish the Animations Lab."

The next milestone is:

> make one experiment visually undeniable.

The chosen first experiment is:

> **Text Emergence**

This forces the renderer to grow beyond particles while keeping the work aligned with the publication.

---

## 4. What Pixi Owns

Pixi already provides low-level scene objects and rendering capabilities.

For text, Pixi provides:

* `Text`
* `BitmapText`
* `HTMLText`
* `SplitText` / `SplitBitmapText` for line, word, and character-level animation

We will use Pixi for low-level text rendering.

We will not build:

* a font rasterizer
* a text layout engine
* glyph rendering from scratch
* a replacement for Pixi scene objects

Pixi is the rendering backend. It is not the authoring model.

References:

| Pixi capability | Reference |
| --- | --- |
| Text scene objects | https://pixijs.com/8.x/guides/components/scene-objects/text |
| Split text scene objects | https://pixijs.com/8.x/guides/components/scene-objects/text/split-text |

---

## 5. What The Animation Runtime Owns

The runtime owns the meaning of text inside the publication animation system.

It must define:

* text as a semantic source
* text as an emitter anchor
* text bounds and layout binding
* text-to-particle behavior
* text-linked timelines
* text-linked effect pipelines
* text source visibility and dissolve behavior
* text return / reform behavior
* renderer-neutral primitive contracts

The runtime should answer questions Pixi does not answer:

* where do particles spawn from on text?
* do they emit from bounds, glyph pixels, glyph edges, words, or characters?
* do they peel away, drift, dissolve, return, or reform?
* how is text tied to article sections and scroll?
* how does text participate in zones, events, and material channels?

This is the product layer.

---

## 6. New Renderer Primitive Vocabulary

We will add renderer-neutral primitives before expanding the lab.

Initial target vocabulary:

```ts
type RenderPrimitive =
  | TextPrimitive
  | ZonePrimitive
  | ParticlePrimitive
  | TrailPrimitive
  | PolylinePrimitive;
```

The exact TypeScript names may evolve, but the separation is required.

### 6.1 `TextPrimitive`

Purpose:

* render visible publication text
* provide a semantic anchor for emitters
* expose source visibility, alpha, glow, bounds, and debug options

Initial properties:

* `id`
* `text`
* `bounds`
* `anchor`
* `font`
* `color`
* `alpha`
* `glow`
* `visible`
* optional debug bounds

Pixi mapping:

* `Text` for v1
* optional `SplitText` later for per-character behavior

### 6.2 `ZonePrimitive`

Purpose:

* make semantic space visible
* show the difference between a zone as math and a zone as authored visual territory

Initial properties:

* `id`
* `shape`
* `fill`
* `fillAlpha`
* `stroke`
* `strokeAlpha`
* `softEdge`
* optional label
* optional debug occupancy display

Pixi mapping:

* `Graphics`
* later, shader/filter or render texture edge treatment if needed

### 6.3 `TrailPrimitive`

Purpose:

* add temporal richness
* make motion feel continuous rather than like dots being redrawn

Initial implementation options:

* short per-particle velocity trails
* render texture feedback layer
* ghost persistence layer

The first implementation should be simple and measurable.

### 6.4 `PolylinePrimitive`

Purpose:

* render fracture lines
* render arcs
* render connectors
* render field vectors and debug flow

This is required before **Fracture Pulse** can be considered real.

## 7. Text Emergence V1

The first real experiment will be **Text Emergence V1**.

It must not be "particles near text."

It must contain:

* visible Pixi-rendered text
* particles emitted from that text source
* source text remains legible
* particles peel away from the text
* particles drift into a field
* optional source glow
* optional debug text bounds
* basic trails / persistence

### 7.1 Initial behavior

The v1 behavior can use text bounds instead of true glyph sampling.

That is acceptable only if:

* the source text is visibly rendered by the runtime
* emission is clearly attached to the text
* the visual reads as language dissolving into atmosphere

True glyph sampling can be a later milestone.

### 7.2 Future behavior

Later versions may add:

* sampled glyph pixels
* sampled glyph edges
* per-character emission
* return / reform behavior
* scroll-linked dissolve / reassembly
* SplitText-backed character motion

## 8. Corrected Lab Strategy

The current lab work should be treated as **runtime smoke testing**, not finished experiments.

Do not keep elaborating four experiments while the renderer can only express dots.

Correct sequence:

1. Build `TextPrimitive`.
2. Render visible Pixi text through the runtime.
3. Attach emitter behavior to text.
4. Add trail / persistence support.
5. Rebuild **Text Emergence** until it no longer reads as random dots.
6. Then return to **Memory Zone** with real `ZonePrimitive`.
7. Then return to **Fracture Pulse** with `PolylinePrimitive`.
8. Then keep **Ambient Drift** as the baseline register.

The lab should show fewer real experiments rather than more fake experiments.

---

## 9. Consumption Model

The consumption model remains lazy and article-local.

The corrected flow:

1. Article or lab page declares an animation mount point.
2. Page-specific client entry lazy-loads `@gkoreli/animation` and `@gkoreli/animation/renderer-pixi`.
3. Authoring code declares semantic scene objects:
   * fields
   * zones
   * materials
   * timelines
   * text sources
   * emitters
   * effect pipelines
4. `compileScene(...)` produces:
   * simulation stores
   * effect pipelines
   * event queues
   * renderer-neutral primitives
5. `mountScene(...)` owns:
   * frame loop
   * resize
   * visibility
   * reduced motion
   * disposal
6. Pixi renderer maps renderer-neutral primitives to Pixi objects:
   * `TextPrimitive` -> Pixi `Text`
   * `ZonePrimitive` -> Pixi `Graphics`
   * particle batches -> Pixi `Graphics` or future particle renderer
   * trails -> short line segments or render texture feedback
   * polylines -> Pixi `Graphics`

Pixi objects must remain inside the renderer adapter.

Authoring code must not import Pixi.

---

## 10. Consequences

### Positive consequences

* The runtime can finally express concepts beyond particles.
* Text Emergence becomes a real publication-native experiment.
* Pixi remains useful plumbing instead of becoming the public API.
* The lab becomes an honest proving ground.
* Renderer capabilities become explicit and inspectable.

### Negative consequences

* More architecture is needed before the lab can look impressive.
* The first lab release must narrow scope.
* Some existing lab UI/code should be treated as temporary smoke-test work.
* The renderer adapter becomes more complex.

### Neutral consequences

* The runtime remains Pixi-backed for now.
* True glyph sampling is deferred.
* SplitText is useful but should not become a hard dependency in the public authoring model yet.

---

## 11. Anti-Goals

Do not:

* build a custom text renderer
* leak Pixi objects into authoring APIs
* add more lab experiment labels before one experiment is real
* hide renderer limits behind copywriting
* treat DOM overlays as a substitute for runtime primitives
* build a generic scene graph before article scenes demand it

---

## 12. Decision Summary

The animation package has a valid runtime core, but its renderer vocabulary is too narrow.

The next architectural step is a renderer-neutral visual primitive layer.

Pixi should render low-level text and graphics. The animation runtime should own semantic text participation, emitter binding, effect composition, and publication-specific behavior.

The next product milestone is **Text Emergence V1**, not a four-experiment lab.

The goal is to make one experiment visually undeniable before expanding the Animations Lab.

---

## 13. Guiding Statement

> Do not let the runtime's semantic vocabulary outrun its visual vocabulary. Make text real first, then let the rest of the lab earn its place.
