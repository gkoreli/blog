Scope: read-only review of packages/blog stats client/page/style/privacy/template and ADR-0016 presentation/disclosure contract. Analytics SQL was not reviewed.

Acceptance verdict: CHANGES REQUIRED. No P0 defects. The source template cleanly removes the legacy /api/event beacon, and loading/request-race/error/theme/URL-selected-state handling is generally sound, but the current empty state, hourly client units, and reader-facing identity claims do not meet ADR-0016.

P1 — Empty is not a whole-dashboard state (behavior/contract)
Evidence: packages/blog/src/client/stats.ts:323-338 always calls setDashboardVisible(true), renders totals/chart/all dimensions, and only changes the status text when totals.views === 0. packages/blog/src/client/stats.ts:249-297 can consequently render a zero-filled chart while every ranked section separately says “No data.” ADR docs/adr/0016-analytics-observation-semantics.md:197 requires loading, empty, and failure to be whole-dashboard states.
Impact: a no-data selection produces a populated dashboard shell rather than one coherent empty result, contradicting the declared state model and creating repetitive/misleading zero visuals.
Focused fix/check: branch on totals.views === 0 before rendering the dashboard; destroy/hide the dashboard and expose one selection-specific empty status (or a dedicated single empty panel). Exercise a zero-result traffic/range selection and confirm cards/chart/dimensions are not shown, while changing filters can recover normally.

P1 — Hourly chart/table do not name the actual client unit or its non-additivity (metric trust/accessibility)
Evidence: packages/blog/src/client/stats.ts:256-280 captions the table “Hourly values in UTC” but labels its column only “Daily clients”; lines 283-318 likewise label the hourly series/accessible image “Daily clients.” The only caveat is later prose at packages/blog/src/pages/stats.ts:94. ADR docs/adr/0016-analytics-observation-semantics.md:180 says the UI must not imply that daily-client bucket values are additive.
Impact: the 7d hourly series conventionally reads as values that can be totaled, although the same daily ID can appear in many hourly buckets. The table is the non-pointer/accessibility alternative, so the unit boundary must be present there, not only in methodology below the dashboard.
Focused fix/check: for hourly granularity label the series/table column as “Daily IDs seen in hour” (or equivalently precise language), and put “values can repeat across hours / are not additive” in the chart aria-label or table caption. Keep the card definition separate as selected-window Daily clients. Inspect 7d and 30d renderings: hourly disclosure appears only for 7d; daily UTC labels remain exact.

P1 — Reader-facing automation names still sound like identified agents (trust/disclosure)
Evidence: packages/blog/src/pages/stats.ts:84-86 headings the dimension “Named automation agents”; packages/blog/src/client/stats.ts:332 renders “<agentName> · AI UA/Bot”; packages/blog/src/pages/privacy.ts:13 says a “matched automation agent name” is recorded. Although packages/blog/src/pages/stats.ts:93 later disclaims verified identity, these labels still name the requester rather than the matched sender-asserted rule. ADR docs/adr/0016-analytics-observation-semantics.md:41 and 184 define AgentName as a matched rule that does not upgrade identity.
Impact: skimming readers can interpret rows as verified OpenAI/Anthropic/etc. traffic, the exact inference the cutover is intended to prevent.
Focused fix/check: rename the section to “Matched automation signatures” or “Matched User-Agent rules”; render rows as “<name> UA rule · AI/Bot”; change privacy copy to “matched User-Agent rule name.” Verify bot, AI, and all segments never call a match an identified/verified agent.

P1 — Privacy copy claims Turnstile verifies a human (trust/accessibility language)
Evidence: packages/blog/src/pages/privacy.ts:25-27 says Turnstile analyzes signals “to verify requests are made by a human.” This is a categorical person-verification claim and conflicts with the review acceptance rule that reader-facing terms cannot imply people or verified identities.
Impact: an anti-abuse signal/challenge cannot establish that a request was made by a human; automation can pass and people can fail. This weakens the otherwise careful distinction between traffic evidence and identity.
Focused fix/check: replace with bounded language such as “assesses signup requests for automated abuse” or “helps distinguish likely legitimate signup traffic,” preserving the Cloudflare-processing disclosure. Search the rendered stats/privacy pages for Humans/human, verified agents, reads, attention, and equivalent identity claims.

P2 — Fixed 300px chart width can overflow narrow viewports (responsive behavior)
Evidence: packages/blog/src/client/stats.ts:304-306 and 397-399 force width >= 300px. packages/blog/src/styles/layout.css:267 leaves 32px horizontal content padding on mobile, so viewports below 332px cannot contain the plot even though packages/blog/src/styles/stats.css:85-93 otherwise provides mobile overflow handling only for controls/table.
Impact: narrow phones/zoomed layouts can acquire page-level horizontal scrolling and clip the chart.
Focused fix/check: size to the actual positive container width (do not impose 300px), letting ResizeObserver expand later; optionally cap the uPlot root/canvas to 100%. Check 280px, 320px, and resize/orientation transitions for no document overflow and a correctly redrawn plot.

P2 — Loading shimmer ignores reduced-motion preference (accessibility)
Evidence: packages/blog/src/styles/stats.css:77-79 runs an infinite 1.5s shimmer; no stats reduced-motion override exists.
Impact: users requesting reduced motion still receive perpetual motion during the initial/loading state.
Focused fix/check: under @media (prefers-reduced-motion: reduce), disable .skeleton::after animation (a static skeleton is sufficient). Confirm loading remains visually identifiable in both themes.
