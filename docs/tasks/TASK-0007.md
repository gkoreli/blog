Assigned investigation: TASK-0001 supplement.

# High-severity trust mismatch

The live Privacy page says: `Page views are recorded server-side (path and referrer only)` and `No third-party scripts involved in analytics.` The live product contradicts both claims:

- `/api/stats` publicly exposes country and device aggregates, so the first-party system necessarily derives and stores/query-aggregates more than path and referrer. ADR-0004 schema includes country, city, continent, visitor_hash, visitor_type, device_type, is_owner, and created_at.
- The live /stats page loaded `https://static.cloudflareinsights.com/beacon.min.js` and posted to `/cdn-cgi/rum`, while also posting the first-party `/api/event`. ADR-0004 explicitly retains Cloudflare Web Analytics as a supplementary performance monitor. Whatever the intended meaning of third-party, the absolute disclosure `No third-party scripts involved in analytics` is false to a reader inspecting the page.

# ADR integrity issues

ADR-0004 acknowledges that its daily salt is the public date string and that an attacker can brute-force IPv4 candidates, then later claims `Nothing reversible — SHA-256 is one-way; you cannot derive the IP from the hash.` Those statements cannot both stand. A hash can be one-way while low-entropy inputs remain enumerable; a public deterministic date is not a cryptographic salt. The ADR also calls the 16-hex-character truncation a privacy safeguard, but truncation mainly increases collision probability and does not fix offline dictionary enumeration.

# Decision input

Before changing metrics, the next ADR must settle the data/trust contract: exact collected/derived/stored fields; visitor hash threat model and retention; whether Cloudflare Web Analytics remains enabled; and public wording that distinguishes no cookies from no tracking and daily unique devices from unique people. This is a correctness issue, not copy polish.
