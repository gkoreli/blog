## Primary-source landscape

### 1. Cloudflare Web Analytics and RUM

**Observed in primary docs:** Cloudflare Web Analytics is a JavaScript beacon that uses browser Performance APIs to report page views, visitors, and page performance; Cloudflare calls the displayed data RUM. The FAQ says the beacon is blocked by ad blockers, may lose the last payload under compatibility/network conditions, fires on every pageview, only appears in valid HTML, cannot measure Worker subrequests, and displays only client-side analytics. In contrast, Cloudflare edge analytics can measure every request Cloudflare receives.

**What this proves:** a browser beacon and an edge request counter observe different events. A beacon can be correct within its boundary while being an invalid source for claims about all requests, bots that do not execute it, Worker subrequests, or non-HTML resources.

**What it does not prove:** a beacon equals “human,” or edge requests equal meaningful page views. Some humans block the beacon; some automation can execute JavaScript; edge logs include assets, probes, bots, and retries.

Sources: [Cloudflare Web Analytics — About](https://developers.cloudflare.com/web-analytics/about/) (updated 2026-04-17); [Cloudflare Web Analytics — FAQ](https://developers.cloudflare.com/web-analytics/faq/) (updated 2026-07-14).

### 2. Cloudflare AI Crawl Control and AEO

**Observed in primary docs/posts:** AI Crawl Control is available on all plans and reports AI crawler requests by crawler/operator, response status, path, bandwidth, requested `Accept` format, served `Content-Type`, and (paid plans) referrals. Its content-format chart explicitly compares what a client requested with what the origin served. Cloudflare’s 2026-08-06 AEO launch says old human clicks and pageviews are incomplete, then separates diagnostics, synthetic recommendation/citation measures, real crawl activity, and referrals.

**Overlap:** the feature set already covers much of “source-aware AI edge analytics.” The article cannot credibly claim to invent crawler/operator/path/content-format/referral analytics.

**Gap:** Cloudflare sells visibility and action. It does not tell the small-site story of a correctly incremented but wrongly named legacy event, preserve a 2,564-row history across a semantic cutover, or expose the author’s live uncertainty. Its AEO piece also makes larger product claims than an HTTP request can support; this article can be more rigorous about request, delivery, use, citation, and referral as separate stages.

Sources: [AI Crawl Control overview](https://developers.cloudflare.com/ai-crawl-control/) (updated 2026-08-14); [Analyze AI traffic](https://developers.cloudflare.com/ai-crawl-control/features/analyze-ai-traffic/) (updated 2026-04-23); [From ranking to recommended](https://blog.cloudflare.com/aeo/) (published 2026-08-06).

### 3. Cloudflare Markdown for Agents and content-format analytics

**Observed in primary post:** Cloudflare’s Markdown for Agents uses `Accept: text/markdown` content negotiation, serves converted Markdown, and tracks response MIME type for AI bot/crawler traffic. The post reports one page shrinking from 16,180 HTML tokens to 3,150 Markdown tokens, but that is a representation-cost example, not proof of retrieval, use, citation, or answer quality.

**Overlap:** the HTML-versus-Markdown resource distinction is current and already productized at internet scale. A generic “agents want Markdown” section would repeat existing material and overlap the prior `does-llms-txt-work` article.

**Gap:** the immediate article can show why the old beacon could never observe non-HTML `llms.txt`/Markdown requests, and why the new edge event must record resource/representation separately from actor/source. A Markdown request is not proof that the requester is AI; an AI crawler may request HTML.

Source: [Introducing Markdown for Agents](https://blog.cloudflare.com/markdown-for-agents/) (published 2026-02-12; modified 2026-07-15).

### 4. Crawler purpose and identity are already multi-dimensional

**Observed in primary sources:** Cloudflare Radar classifies crawler purpose as training, search, user action, or undeclared and computes crawl-to-refer ratios from HTML crawler requests and referred HTML page requests. OpenAI documents distinct agents: `GPTBot` for possible training use, `OAI-SearchBot` for ChatGPT search, and `ChatGPT-User` for certain user-triggered actions. OpenAI also warns that one crawl may serve multiple use cases and that `ChatGPT-User` is not an automatic web crawler.

**Implication:** “AI read” is not a valid primitive. Even verified operator identity and documented purpose do not prove that a specific response influenced a model output. The durable vocabulary is request → successful delivery → possible selection/use → citation/mention → referral/outcome.

Sources: [A deeper look at AI crawlers: breaking down traffic by purpose and industry](https://blog.cloudflare.com/ai-crawler-traffic-by-purpose-and-industry/) (published 2025-08-28; modified 2026-07-15); [Overview of OpenAI Crawlers](https://developers.openai.com/api/docs/bots) (checked 2026-08-26).

### 5. Profound Agent Analytics

**Observed in primary launch post:** Profound argued in February 2025 that conventional browser analytics misses AI crawlers because they rarely execute client JavaScript. Its proposed solution is server-side request logging, official-IP verification, crawler categorization, per-page activity, and referral tracking.

**Overlap:** this directly preempts the thesis “I moved analytics server-side so I can see AI.”

**Gap:** Profound is an enterprise AEO product launch. It does not examine a legacy event whose public label exceeded its evidence, a low-volume personal-site migration, historical continuity, privacy minimization, or the difference between observing an HTTP request and proving an AI system used content.

Source: [Introducing Agent Analytics](https://www.tryprofound.com/blog/introducing-agent-analytics) (published 2025-02-05).

### 6. Privacy-first analytics and the client/server accuracy debate

**Observed in primary Plausible material:** Plausible’s 2020 empirical comparison found 16.8k browser pageviews versus 305.5k AWStats “page views” on one site in one month; the server-log number was dominated by automated/back-end requests. Plausible’s 2026 accuracy page argues that consent, blockers, bot filtering, attribution, sampling, and modeling all change reported numbers. This is vendor-authored evidence and marketing, not an independent population estimate, but the concrete 2020 comparison is valuable counterevidence to “edge is more accurate.”

**Implication:** neither client nor edge data is “the truth.” Each sensor is accurate only for a named event and filtering policy. Browser analytics is useful for real-user observation/RUM; edge analytics is required for request/source/resource analysis. The system may need both views, but it must not merge their semantics.

**Privacy implication:** “edge” is not inherently more private. Edge requests expose fields a minimal browser beacon may never store. A privacy-first claim must name collection, transformations, discarded fields, retention, aggregation, and whether IP/user-agent data survives storage.

Sources: [Client side vs server side analytics: What’s the gap in data?](https://plausible.io/blog/server-log-analysis) (published 2020-06-30); [Plausible: The more accurate alternative to Google Analytics](https://plausible.io/most-accurate-web-analytics) (published 2026-08-26).

### 7. Publisher control and monetization

**Observed in primary product post:** Fastly and TollBit frame AI bot traffic as a publisher control/compensation problem: detect/classify at the edge, verify access, apply policy, and optionally charge.

**Overlap:** confirms that publisher telemetry is a live commercial category.

**Gap:** monetization, bot blocking, and “content taken without compensation” would distract from the owned measurement failure unless the author has direct evidence. Keep them in the dated landscape or glossary, not the spine.

Source: [How to Control and Monetize AI Bot Traffic Using Fastly and TollBit](https://www.fastly.com/blog/how-to-control-and-monetize-ai-bot-traffic-using-fastly-and-tollbit) (published 2025-07-01).

### 8. Durable measurement model

Google’s HEART/GSM paper describes a process for mapping goals to signals and then to metrics. Its relevance here is structural: a metric should be downstream of an explicit goal and observable signal, rather than inheriting meaning from a convenient counter.

Source: Rodden, Hutchinson, and Fu, [Measuring the User Experience on a Large Scale: User-Centered Metrics for Web Applications](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/) (CHI 2010).

## Trend versus evergreen

### Trendy and volatile — date and bound these claims

- “Agents are the new audience,” AEO/agent-readiness scores, and pay-per-crawl.
- Current crawler names, user-agent strings, IP ranges, robots policies, and provider purpose labels.
- Global percentages for bot traffic, crawl-to-refer ratios, or content-format adoption.
- Markdown token-reduction examples and claims that agents prefer a representation.
- Current Cloudflare/Profound/Fastly product availability, plan limits, and feature names.
- Claims that AI referrals are rising/falling or that a provider is a “top crawler.”

These can establish timing, but they should not carry the article. Recheck them near publication and label the date/population.

### Durable and evergreen — make these the reader value

- Name the event before choosing or relabeling a counter.
- State the sensor boundary: who can trigger it, which resources can carry it, and where loss/filtering occurs.
- Separate actor/source, requested resource, served representation, response status, and downstream outcome.
- Separate request, delivery, selection/use, citation, referral, and business outcome.
- A 2xx response proves successful HTTP delivery, not comprehension, training, recommendation, or citation.
- Content format is not actor identity: AI can request HTML; non-AI tools can request Markdown.
- “Server-side is more accurate” and “browser analytics is human truth” are both category errors without an event definition.
- Privacy comes from minimizing and aggregating fields at collection/storage, not from moving code to the edge.
- Historical continuity requires versioned semantics or a visible cutover; never silently reinterpret legacy rows.
- Preserve unresolved state when the result is not yet observed.

## Evidence that gives the piece defensible differentiation

The article should put these concrete artifacts near the claims they support:

1. **The old event contract:** exact trigger, endpoint, eligible representations, and fields recorded. Show that the browser beacon observed a browser page event/RUM event, not every HTTP request.
2. **The misleading label/claim:** quote the public wording that turned the narrower event into “page requests,” “AI reads,” or equivalent. The admission is essential.
3. **The 2,564-row ledger:** date range, schema, what each legacy row can and cannot mean, and whether the count is rows, requests, or aggregates. Preserve the number; do not retrofit new semantics.
4. **The new event contract:** where the edge observation occurs; eligibility rules; source/actor classification; page/resource/representation distinctions; status policy; deduplication/retry behavior; and retained fields.
5. **The cutover boundary:** timestamp/version separating legacy beacon observations from new edge request observations, plus how the public surface prevents comparison as if they were one homogeneous series.
6. **Two worked requests:** one HTML page observation from a browser and one non-HTML `llms.txt`/Markdown resource request. Show which layer sees each and which claim each permits.
7. **Classification limits:** whether AI identity is user-agent-only, verified against published IP ranges, Cloudflare-classified, or unknown. State spoofing and undeclared-client limits.
8. **Privacy ledger:** fields seen at the edge, fields discarded before persistence, stored granularity, aggregation, and retention.
9. **Open questions at publication:** what share/type of traffic the new stream will reveal, what may break, and what the 30-day sequel will test. Do not forecast the answer.

## Claim gaps and red lines

- **Do not claim novelty as “first” or imply the product capability is new.** Cloudflare and Profound already cover it.
- **Do not call an HTTP request an “AI read.”** A verified request is a request; 2xx is delivery. Use/citation needs separate evidence.
- **Do not infer identity from `.md`, `llms.txt`, or `Accept: text/markdown`.** Representation and actor are independent dimensions.
- **Do not call browser beacons “human traffic.”** Say browser/RUM observations and state blocker, network-loss, and JS-capable-bot limits.
- **Do not call edge counts “pageviews.”** Define eligible HTML document requests and distinguish assets, APIs, probes, and non-HTML resources.
- **Do not say edge analytics is inherently more accurate or more private.** It is more complete for received requests and potentially more invasive unless minimized.
- **Do not use Cloudflare global statistics as evidence about gkoreli.com.** They establish context only.
- **Do not use the 2,564 legacy rows as a pre-cutover AI baseline unless actor identity and event eligibility support that claim.**
- **Do not turn the piece into a verdict on `llms.txt` or Markdown efficacy.** The new value is observability semantics, not another discoverability experiment.
- **Do not promise a 30-day result in this article’s conclusion as if the current piece is incomplete.** State it as a separate continuation with its own question.
