# TASK-0005 — Public stats information-design diagnostic

## Scope and method

This artifact evaluates the product meaning and interaction design of the public /stats page, not the correctness of SQL or aggregation code. No repository files were changed.

Evidence came from the live page on desktop and at 375 px mobile width, the accessibility tree, all visitor filters and representative time ranges, pointer interaction with the chart, and deliberately delayed and failed stats requests. Numeric values are a volatile snapshot; structural findings are durable.

- **[Observed]** directly exercised on the live page.
- **[Documented]** stated by a linked public document or live client asset.
- **[Peer evidence]** directly established by the parallel live/semantic audits and supplied to this task.
- **[Inference]** product interpretation following from evidence but not declared by the page.
- **[Open question]** decision input the interface cannot settle.

## Compressed diagnosis

**[Inference]** The page mixes two unnamed products: a transparency page for readers and a lightweight operator dashboard. It answers “roughly how much traffic did this site receive, and to which URLs?” for an operator who already knows the data model. It does not reliably answer the reader questions “what do these numbers mean?”, “what changed?”, “why should I care?”, or “what are the limits of collection?”

The central failure is not visual polish. It is an absent metric contract and audience hierarchy. Raw paths, referrers, countries, devices, human/bot/AI filters, and top-line counts are given equal authority while their units, denominators, overlap, observable population, time boundaries, and caveats remain implicit. A mathematically correct dashboard can therefore still produce a false reader conclusion.

## Evidence snapshot

### Defaults, controls, and responsive behavior

- **[Observed]** Default is **Humans · 30d**. At observation it showed 209 Views, 121 Visitors, and 17 AI Reads.
- **[Observed]** Scope is shareable in the URL. Human 30d uses /stats?days=30; other segments add visitor=bot, visitor=ai, or visitor=all. All-time uses days=0.
- **[Observed]** Visitor and time pills have no visible titles, roles, or accessible group labels. Both groups contain “All.”
- **[Observed]** Selection uses only an active CSS class; buttons have neither aria-pressed nor aria-current. Keyboard focus remains visible through the browser default outline.
- **[Observed]** At 375 px there is no horizontal overflow. Controls wrap, the third KPI becomes full width, and long paths/referrers truncate.
- **[Observed]** AI Reads stayed 17 under Humans, Bots, and All in the same 30-day window while Views/Visitors changed. Under AI, Views, Visitors, and AI Reads were all 17. This proves an unexplained scope relationship, not by itself a calculation bug.

### Metrics, chart, and ranked rows

- **[Observed]** KPI order is Views, Visitors, AI Reads. Cards have no definition, explicit dates, comparison, or freshness time.
- **[Observed]** Device percentages omit their denominator. The live client computes them from views.
- **[Observed]** The chart compares Views and Visitors. Pointer hover reveals exact dates/values; the hover affordance is not explained and is not keyboard-focusable.
- **[Observed]** Assistive technology receives an image name containing only period totals. The embedded legend table reports Time, Views, and Visitors as “--” until pointer hover, so the daily trend lacks a non-pointer data alternative.
- **[Observed]** Top Pages, Referrers, and Countries show ten rows with unlabeled numbers. The client maps all rows from views.
- **[Observed]** Bars are normalized to the leading row, not total traffic; no scale or legend explains that.
- **[Observed]** Page paths are plain text rather than links. This supports operator inspection but not reader discovery.
- **[Observed]** Referrers are raw domains/paths; one host can fragment into separate rows. Direct or unavailable attribution is not explained.

### Loading, empty, and failure

- **[Observed]** Initial load shows 14 skeletons, no stats-specific aria-busy/live announcement, and enabled filters.
- **[Observed]** An empty section says only “No data for this period.” It does not identify the section/segment or distinguish zero events from unavailable attribution. AI 30d had empty Referrers while other data existed.
- **[Observed]** On API 500, only the chart says “Unable to load stats. Try refreshing.” Six KPI/device skeletons remain, three empty headings remain, the error is not announced as an alert, and no retry button exists.
- **[Inference]** Failure reads as indefinite partial loading rather than one coherent dashboard error.

### Collection coverage and disclosure

- **[Observed]** Inline copy says “Analytics collected without cookies, tracking, or fingerprinting,” then sends readers to a long GitHub engineering ADR.
- **[Documented]** The ADR describes a client beacon, path/referrer/user-agent and Cloudflare-derived fields, a daily hash of IP + user-agent, human/bot/AI classification, and inability to recognize returning visitors across days.
- **[Documented]** Privacy says analytics records “path and referrer only,” while Stats visibly publishes country/device aggregates and Visitors.
- **[Peer evidence]** The live page loads Cloudflare Insights alongside the first-party /api/event beacon, while Privacy says “No third-party scripts involved in analytics.”
- **[Peer evidence]** Static article HTML bypasses the Worker; bot/AI classification happens only when client JavaScript posts /api/event. Non-JavaScript crawlers that fetch articles never enter the displayed dataset.
- **[Inference]** Bots and AI Reads therefore describe only beacon-capable requests that match classifiers, not total bot traffic, total AI traffic, or all article fetches. Even perfectly counted rows cannot support the broader labels.
- **[Inference]** Trust placement is architectural, not copy polish. Readers must currently reconcile an inline promise, Privacy, a developer ADR, parallel beacons, and an undisclosed coverage boundary.

## Ambiguity inventory

### Critical

1. **Visitors.** **[Documented]** Daily identifier rotation means the same person on two days counts twice. **Risk:** the unqualified 30d label implies unique people across 30 days.
2. **AI Reads.** **[Observed]** It does not visibly follow segment scope like other KPIs. **[Peer evidence]** Non-JS AI crawlers are absent. **Risk:** “read” implies coverage and consumption that the beacon cannot observe.
3. **Human/Bot/AI taxonomy.** Peer controls imply mutually exclusive complete classes; no definition says whether AI is a bot subset, what unknown automation does, or which clients can appear.
4. **Measurement universe.** The page never says “JavaScript beacon events.” **Risk:** Bots/AI appear to quantify all automated fetches while systematically excluding non-JS fetchers.
5. **Ranked-row unit.** Pages, Referrers, Countries, and Devices omit measure/denominator; all are view-based.
6. **Time semantics.** 7d/30d/90d/All omit visible boundaries; All has no start date; requests use browser timezone; no updated time appears.
7. **Trust boundary.** Stats, Privacy, ADR, and actual beacon set describe different scopes; “first-party,” “third-party,” “tracking,” and “analytics” are not tied to named collection surfaces.

### Significant

8. **Views versus reads:** collection records page loads; “read” implies engagement.
9. **Countries:** no IP-geolocation disclosure, VPN/proxy/Tor/unknown caveat, or denominator.
10. **Devices:** view-weighted UA inference is styled as an audience characteristic.
11. **Referrers:** missing does not necessarily mean direct; redirector paths fragment sources.
12. **Bars:** half-width means half the leader, not 50% of traffic.
13. **Two All buttons:** duplicate accessible names without group labels.
14. **Freshness:** final-looking totals lack update cadence and partial-day signal.
15. **Owner exclusion:** a documented core goal not disclosed on the page.
16. **Top Pages audience:** raw non-link slugs are operator keys, not reader-facing discovery.
17. **Parallel analytics:** no distinction between public first-party metrics and Cloudflare Insights, their purposes, or which stream supports displayed values.

## Calculation bug versus information-design failure

A calculation bug violates a declared contract. An information-design failure withholds the contract or overstates what the measurement can support.

| Symptom | Calculation/semantic bug if… | Already an information-design failure because… |
|---|---|---|
| AI Reads constant under Humans/Bots/All | Every KPI is intended to obey segment filter | No exception/separation declares different scope |
| 30d Visitors exceeds intuition about unique people | Contract promises range-unique people | Daily rotation is hidden behind “Visitors” |
| Device shares differ from visitor mix | Intended denominator is visitors | No denominator is shown |
| Dimension rows do not sum to KPI | Sections promise exhaustive partitions | Top ten/unknown/direct omissions and unit are unstated |
| Chart/card differ | Same dates/segment are promised | Dates, timezone, partial day, freshness are hidden |
| Referrers empty while views exist | Direct/unknown is contractually required and omitted | Empty copy conflates zero traffic with unattributed traffic |
| Bots/AI undercount non-JS crawlers | Product contract promises all bot/AI fetches | Current labels make that promise implicitly even if stored events are counted correctly |
| Privacy conflicts with beacons/dimensions | Collection violates adopted disclosure contract | Disclosure ownership/scope is not coherent in the IA |

**Follow-up rule:** define metric, observable population, and disclosure contract in plain language first; then test queries/network behavior. Do not relabel a calculation defect, and do not rewrite a correct calculation merely because the label invites the wrong interpretation.

## Chart/table coherence and affordances

**Coherent:** cards/chart share Views/Visitors; hover gives exact daily values; filters update shareable URLs; mobile reflows without overflow.

**Incoherent:** ranked rows and Devices silently use Views; accessible chart summary omits the trend and its table requires pointer hover; no hint announces chart interaction; totals look final without freshness; reader-facing cards transition directly into operator raw dimensions without a mode or narrative boundary.

## Evidence-ranked information architecture alternatives

These are decision inputs, not an ADR recommendation.

### Rank 1 — Reader-first transparency brief, methodology adjacent

**Structure:** explicit scope/update line; two defined primary measures with prior-period comparison; trend plus readable daily data; linked post titles and shares; normalized acquisition including Direct/unknown; secondary Automation and Methodology section naming observable population, collection surfaces, exclusions, and limits.

**Evidence: strong.** Public metadata, human default, and declared transparency/content goals support a reader-first job. Current failures are mainly missing definitions/context.

**Trade-off:** operator detail becomes secondary/expandable.

**Falsifiable hypothesis:** four of five readers can state segment, dates, visitor definition, trend, top post, and key limitation after ten seconds without leaving the page.

### Rank 2 — Split public summary from operator explorer

**Structure:** Reader Summary plus explicit Explore Traffic view/route for raw filters, paths, referrers, countries, devices, and diagnostics, sharing one metric/disclosure dictionary.

**Evidence: strong-to-moderate.** The current page demonstrably combines two audiences.

**Trade-off:** adds mode/navigation; a public explorer still requires purpose/privacy framing.

**Falsifiable hypothesis:** operators diagnose a spike faster in Explorer while readers answer trust/social-proof questions faster in Summary than today.

### Rank 3 — Automation-first traffic composition story

**Structure:** defined Human/Traditional Bot/AI observed-beacon composition, then human content interest and automated fetches separately. Rename AI Reads to the actual observable event unless reading is measured.

**Evidence: moderate/conditional.** AI/bot publication is distinctive, but the non-JS blind spot means the story must explicitly be “observed beacon-capable automation,” not total automation.

**Trade-off:** compelling only if coverage/classifier limits are central; otherwise it amplifies the least defensible metric.

**Falsifiable hypothesis:** readers correctly distinguish observed AI beacon events, non-observed crawler fetches, bot events, human views, and AI referrals.

### Rank 4 — Preserve order; repair labels, states, accessibility

**Structure:** group labels, aria-pressed, definitions, row headings, denominators, updated time, comparisons, normalized sources, title links, inline disclosure, coherent loading/empty/error.

**Evidence: moderate for risk reduction, weak as complete IA.** Fixes map to observations but audience competition remains.

**Falsifiable hypothesis:** misinterpretation drops, but task completion remains worse than Rank 1/2 if audience mixing is root cause.

## Minimum decisions a future ADR must resolve

1. **Primary audience/job:** reader transparency, operator console, or explicit split; name the opening question.
2. **Metric dictionary:** define View, Visitor, AI event, Bot event, referrer, country, device; for each state source, uniqueness window, denominator, exclusions, and whether “read” is justified.
3. **Measurement universe:** explicitly decide whether automation metrics claim all requests, JS beacon events, or another observable set. Non-JS crawler exclusion must be part of the metric name/definition, not a remote footnote.
4. **Visitor taxonomy:** mutual exclusivity, AI meaning, unknown automation, AI referrals, classifier limits.
5. **Filter scope:** which components obey visitor/time; whether AI Reads is segment-scoped, time-only, or separately framed.
6. **Time/freshness:** timezone, inclusive bounds, current-day treatment, all-time start, cadence, updated-through.
7. **Comparison:** prior-period/equal-length baseline or explicitly context-free snapshot.
8. **Dimension IA:** public versus operator dimensions; titles/links versus paths; referrer normalization; Direct/unknown; top-ten omissions; views/visitors/shares.
9. **Trust/disclosure architecture:** inventory first-party beacon, Cloudflare Insights, and infrastructure-derived fields; assign purpose and displayed metrics; define first/third-party and tracking/fingerprinting claims; reconcile Stats, Privacy, and ADR.
10. **Limitations placement:** returning-visitor behavior, owner exclusion, collection start, blocked/failed/non-JS beacon undercount, classifier error, referrer loss, UA device inference, IP geolocation limits adjacent to affected metrics.
11. **State/accessibility:** whole-dashboard loading, section-specific empty, retryable failure, live announcements, selected/group semantics, and non-pointer trend alternative.
12. **Interaction:** shareable URLs, hover/keyboard/touch, navigable ranked pages, unambiguous All controls.

## Decision inputs and falsifiable hypotheses

| Hypothesis | Why plausible | Evidence needed |
|---|---|---|
| Readers value trend/top content over device/country diagnostics | Reader context; device/country lack narrative | Reader interviews/task ranking |
| Visitors means unique people across 30d to readers | Conventional label, no qualifier | Ask readers to paraphrase before revealing method |
| AI Reads appears governed by active segment | Same KPI row/presence | Prediction test before switching; compare separate framing |
| Readers assume Bots/AI include non-JS crawlers | Ordinary meaning of traffic/read/fetch | Ask users what population they expect; reveal beacon boundary |
| Raw paths/referrers mainly serve operator | Non-navigable, truncated, fragmented | Operator vs reader task test |
| Comparisons matter more than device/country | Page cannot answer “is it changing?” | Prototype and measure decisions/comprehension |
| Inline limitations improve trust over GitHub alone | Broad claim, remote inconsistent detail | Trust/comprehension A/B |
| Naming both analytics surfaces prevents trust erosion | Public claims and network behavior differ | Expectations test with coherent collection map |
| Split surfaces beat adding labels to one | Current page changes audience silently | Rank 2 vs Rank 4 usability test |

## Open questions

- Is the public outcome social proof, radical transparency, content discovery, analytics case study, or privacy accountability?
- Is operator use intentional or incidental?
- Does Visitors mean sum of daily uniques, or should the range use another definition/name?
- Is AI Reads time-only, AI-filtered Views, or a distinct event? What earns “read”?
- Are AI and traditional bots mutually exclusive, and how are unknowns/referrals treated?
- Is the desired claim all bot/AI article requests or only beacon-capable classified clients?
- Which rows are omitted: owner, unknown, direct, non-content, beyond top ten?
- What is the all-time start date and are historical classifier changes comparable?
- What does Cloudflare Insights do relative to public metrics, and which stream supports each value?
- Which collection facts/limits must be adjacent to metrics rather than delegated to policy/engineering docs?

## Conclusion

**[Inference]** The visual system is restrained, responsive, and consistent; the failure is upstream of styling. The page treats every number as self-explanatory and every dimension as equally public-facing. Trust placement is part of the product architecture because metrics, collection surfaces, and coverage must tell one coherent story. Before an engineering ADR, the owner must choose audience/job, metric/disclosure contracts, and whether automation analytics is supporting context or the central story. Only then can correctness be tested against stable meanings.
