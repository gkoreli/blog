# Decision

Replace the browser-beacon model with one edge-observed HTML-response model. Build the analytics package around domain terms and composed policies, not UI labels or transport handlers. The public dashboard becomes a reader-first transparency surface backed by explicit metric definitions.

# Domain model

- `PageObservation`: one successful, non-prefetch GET whose served response is HTML. It proves an eligible page response, not attention or reading.
- `TrafficClass`: `browser`, `bot`, or `ai`; derived from the request User-Agent. These are claimed/heuristic classes, never verified identity.
- `DailyClientId`: site-scoped, UTC-day-scoped HMAC of IP and User-Agent using a required Worker secret. It estimates daily clients; it is pseudonymous and cannot mean people or range-unique visitors.
- `AgentName`: the matched named automation rule, nullable. It supports explainable classification and future per-agent aggregates without storing raw User-Agent.
- `StatsWindow`: one UTC reporting contract. 7/30/90 mean exactly that many UTC calendar dates including today; 7d groups hourly, longer windows daily; missing buckets are zero-filled.

# Architectural cutover

1. Change Worker routing to observe static responses before returning `env.ASSETS.fetch(request)`. Remove `/api/event` and the inline browser beacon. This captures non-JS crawlers and removes forge/replay of client-supplied paths.
2. Persist into a new constrained `page_observations` table. Preserve the old `page_views` table as a clearly named legacy beacon dataset; do not mix old and new semantics. New stats start at the first edge observation.
3. Store only path, referrer hostname, country, daily client ID, traffic class, matched agent name, device class, owner flag, and UTC observation time. Stop collecting city, continent, raw referrer paths, raw IP, and raw User-Agent.
4. Query raw UTC timestamp ranges so the time index remains usable. Apply owner exclusion to every public segment. `All` must equal Browser + Bot + AI for a single atomic snapshot.
5. Remove the filter-independent `ai_fetches` card. Use shared exported response types in the blog client. Rename public terms to Page views, Daily clients, Browsers, Bots, and AI UAs; place the observation/classification limits beside the controls.
6. Keep Cloudflare Web Analytics explicitly separate from the public first-party dataset until the owner disables it in Cloudflare. Privacy copy must name both collection surfaces and the stored/derived first-party fields.

# Design principles and patterns

- Composition root in the Worker: API routes first, asset fetch second, analytics observation as a side effect of the served response.
- Pure policy functions for eligibility, traffic classification, daily identity, reporting windows, and bucket filling.
- Repository boundary for D1 writes and a query service for public aggregates.
- Shared domain types across analytics and dashboard; no hand-copied API interface.
- No class hierarchy: these behaviors vary independently and compose cleanly. Inheritance would couple transport, policy, and persistence without a stable subtype relationship.
- Clean cutover: no compatibility endpoint, alias, or mixed historical series.

# Explicit non-goals

No sessions, cross-day people identity, engagement/read measurement, verified-bot claim, funnel tracking, or private operator console. No raw-IP/User-Agent retention. No retrospective reclassification of the legacy beacon dataset.

# Verification contracts

- Non-JS AI/bot HTML GETs create observations; prefetch, failed, non-HTML, HEAD, API, and `/stats` self-traffic do not.
- Daily IDs are stable only for the same site/day/IP/UA/key and are 128-bit HMAC tags.
- 7/30/90 windows contain exactly 7/30/90 dates; UTC boundaries and zero buckets are deterministic.
- Public class partitions reconcile and every card/list/chart uses the active class and period.
- Build output contains no `/api/event` beacon. Privacy and methodology match stored fields and known limits.
