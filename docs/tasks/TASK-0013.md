# TASK-0004 — Primary-source integrity research for public analytics

**Scope.** External/platform research only; no repository implementation review. Sources checked 2026-08-25. This is decision input, not an ADR or legal advice. One deployed-pipeline fact supplied by the parent from the parallel semantics investigation is analyzed below and clearly marked.

## Compressed conclusion

A cookieless system can count recorded events, but cannot identify people without an identifier. The honest low-identity metrics are **recorded browser-beacon events** or **entrances**, not people. A rotating, site-scoped IP+User-Agent digest can estimate **daily unique clients**, but not unique people, cross-day uniques, or cross-device uniques; it also processes identifying inputs and is pseudonymisation, not automatic anonymisation.

The supplied pipeline fact is decisive: static articles bypass the Worker, and D1 receives only client-JavaScript beacon POSTs. Therefore the present measurement universe excludes non-JavaScript crawlers that fetch articles. “Bots/AI Reads” can only mean beacon events from beacon-capable clients that also match the classifier; it cannot mean bot/AI traffic, article fetches, or a complete crawler count.

Bot and AI numbers need narrow names. A User-Agent rule counts requests **claiming** an identity, not verified bots. “AI traffic” must not collapse (1) Search/Training crawlers, (2) user-directed Agents, and (3) people arriving via an AI-service referrer. Cloudflare’s current behavior taxonomy allows one bot to have multiple behaviors, so categories are not inherently additive.

D1 is suitable for aggregate counters, but one database instance is single-threaded; writes serialize and may fail under overload/transient errors. Public totals can only mean successfully recorded events. Date windows must declare a timezone and use half-open instant boundaries. “All time” means since collection began, not since the site began.

## Observation supplied by the parallel semantics layer (not independently re-reviewed here)

Static HTML bypasses the Worker (`run_worker_first` applies only to `/api/*`); classification occurs on the client-JavaScript beacon POST to `/api/event`; non-JavaScript crawlers fetching articles never enter D1. External-source implications:

- The source event is not an edge request or an HTML response. It is a successfully delivered/accepted browser beacon. Cloudflare documents that JavaScript analytics beacons are blockable while edge analytics see every request received [S7].
- Any “view” excludes clients that do not run or successfully send the beacon. It is closer to “recorded client page-load event” than “HTTP view,” but still does not prove attention or reading.
- A bot/AI value is the intersection `beacon-capable client ∩ delivered beacon ∩ classifier match`. Conventional non-JS crawlers—including many Search/Training crawlers—are outside the denominator. Zero means “no matching beacon recorded,” not “no bot/AI article fetches.”
- A User-Agent observed on the beacon POST describes the client that executed the beacon. It cannot retrospectively classify static HTML fetches the Worker never observed.
- Cloudflare bot metadata on `/api/event`, if entitled, classifies the beacon request/client only. It does not recover excluded article-fetch traffic.
- “AI referral” remains a separate concept: a normal browser arriving from an AI service may send a beacon while using an ordinary browser UA. It is not an AI crawler.

These are terminology constraints, not an implementation proposal.

## Observations and evidence

### 1. Cloudflare/D1 behavior

| Evidence-backed fact | Integrity consequence | Constraint vs choice |
|---|---|---|
| D1 has SQLite SQL semantics [S1]. SQLite has no dedicated date/time type; it stores ISO-like text, Julian days, or Unix timestamps. `now` is UTC and stable within one `sqlite3_step()` [S5]. | Timestamp representation and query boundaries are application-defined. A bare date has no timezone. | **Hard constraint:** no native timezone-aware column. **Choice:** UTC representation/reporting zone. |
| Each D1 database instance is single-threaded and processes queries one at a time. Excess work queues, then may return overload [S2]. | Writes serialize. Failed/dropped beacon writes undercount. “Every view” is not guaranteed without durable-recording evidence. | **Hard constraint.** Aggregation/indexing are choices. |
| Cloudflare recommends retrying transient writes; read-only queries are automatically retried up to twice [S4]. | Blind retry of a non-idempotent increment after an ambiguous outcome may overcount; no retry may undercount. Exact-once needs idempotency/dedup, not merely retry. | Failures are **hard reality**; exactness policy is a **choice**. Overcount is a falsifiable inference. |
| Read replication uses async replicas only through Sessions. Without Sessions, queries continue to primary. `first-unconstrained` may start at any available version; `first-primary` starts at latest primary; bookmarks guarantee at least the bookmarked version [S3]. | D1 reads are not inherently eventually consistent. Staleness is introduced only by opting into unconstrained replica reads. | **Hard behavior;** freshness/latency policy is a choice. |
| Current limits include 10 GB paid/500 MB free per database, 30 seconds/query, and 1,000 paid/50 free D1 queries per Worker invocation [S2]. | Raw retention and scans have bounded cost/latency. | **Hard ceilings;** model/retention are choices. |

### 2. What the traffic words can truthfully mean

Cloudflare Web Analytics defines **page views** as successful HTTP responses with HTML content type, and **visits** as page views whose Referer hostname differs (or a direct link); one visit can contain multiple page views [S6]. Cloudflare’s privacy-first approach rejects cookies/localStorage and cross-time IP/UA fingerprinting, then counts cross-site/direct entrances as visits rather than unique people [S8].

Plausible chooses a daily identifier `hash(daily_salt + website_domain + ip_address + user_agent)`, rotates/deletes the salt every 24 hours, and does not store raw IP/UA [S9]. Its docs explicitly say one person on multiple devices or days is counted separately; within one day, multiple sessions count as one unique visitor [S10]. Plausible defines a session by 30 minutes of inactivity, unlike Cloudflare’s Referer-based “visit” [S10]. **Observation:** these are vendor-defined metrics, not universal facts.

| Public term | Minimum observable definition | Truthful here without cookies/fingerprints? | Invariant / guardrail |
|---|---|---|---|
| **Request** | One HTTP request satisfying a published predicate. | Yes only for `/api/event` requests observed by the Worker; not article requests under the supplied pipeline. | State method/host/path/status and retries. |
| **HTML response** | Eligible successful HTML response. | Not observable in current D1 pipeline. | Does not prove rendering, attention, or human. |
| **Recorded view / beacon event** | Accepted browser beacon under a stated trigger/dedup rule. | Yes; strongest current term. | Beacon may be blocked, never sent, duplicated, or sent without attention. |
| **Page view** | A defined response or beacon event, with method shown beside it. | Yes if explicitly defined as recorded beacon, not all article fetches. | Same window/segment: entrances and unique-client estimate must not exceed recorded views. |
| **Entrance** | Eligible view with absent/external Referer under host rule. | Yes, no identifier required. | RFC 9110 says not all requests contain Referer and allows privacy omission/truncation [S16]. “Direct” means “no attributable referrer.” |
| **Visit/session** | Published grouping rule, e.g. entrance or 30-minute inactivity. | Timeout session needs same-client linkage; entrance does not. | Never use without rule: Cloudflare/Plausible definitions conflict [S6][S10]. |
| **Visitor/person/reader** | Natural person. | **No**, not directly observable. | Prefer “client” or “recorded view”; unclassified is not human. |
| **Daily unique client (estimated)** | Distinct ephemeral site/day identifiers with exact inputs/rotation disclosed. | Yes as estimate if transient IP/UA use is accepted. | `daily unique clients <= recorded views`; NAT merges, address/UA change splits. |
| **Unique visitor** | Scope-qualified estimate with identity/window caveats. | Not an exact people count. | Daily rotation cannot dedupe across days; monthly sum is sum of daily clients, not monthly unique people. |
| **Bot request** | Request classified by named/versioned detector/threshold. | Only within the beacon universe here. | Publish detector, threshold, not-computed handling, error limits. |
| **Verified bot request** | Cloudflare identity validated via signature/IP/reverse DNS. | Only if signal is entitled and client sent beacon. | “Verified” means transparent/non-abusive identity, not all automation [S11]. |
| **Claimed bot/AI client** | User-Agent matches published list. | Yes, with “claimed” or “UA-matched.” | UA is sender-provided metadata [S15], not authentication. |
| **AI crawler: Search/Training** | Verified behavior in named taxonomy. | Not comprehensively measurable in a JS-beacon-only pipeline. | A bot can have multiple behaviors; categories require request-level dedup [S11]. |
| **AI Agent** | User-directed automated client. | Beacon-capable agents may be observed; non-beacon agents are absent. | Keep separate from Search/Training [S11]. |
| **AI referral** | Recorded browser view whose Referer maps to AI service. | Yes as attributed beacon referrals. | Not crawler traffic; Referer omission makes it a lower bound [S13][S16]. |

### 3. Deterministic public-date hash assessment

Proposed form: `truncate64(SHA-256(date : IP : User-Agent))`, where `date` is public and deterministic.

**Evidence-based assessment.** SHA-256 is a one-way hash, but one-wayness does not make a low-entropy, guessable input anonymous. An observer with a 64-bit digest, known date, and plausible UA list can compute candidate values offline; the public date offers no secret unknown. IPv4 contributes at most 32 bits before narrowing by known networks, while real UA strings come from a much smaller, structured dictionary. Enumeration cost is governed by that candidate space, not SHA-256’s 256-bit preimage bound. The date usefully namespaces equal inputs by day and prevents direct equality across days, but it is not a cryptographic salt against per-day dictionary enumeration. EDPB/CNIL treat pseudonymisation as reduced linkability, not anonymisation [S17][S19].

**64-bit truncation.** It caps identifier output/security at 64 bits and creates birthday collisions. Approximate probability of at least one accidental collision among `n` daily IDs is `1 - exp(-n(n-1)/(2·2^64))`: about `2.7×10^-8` at one million/day, `2.7×10^-4` at 100 million/day, and 2.7% at one billion/day. At blog scale the collision error is likely negligible, but 64 bits is not a strong cryptographic tag: RFC 2104’s HMAC guidance recommends truncated authentication tags not be below 80 bits [S20]. This use is deduplication, not authentication, so 64 bits may be an operational storage choice, never an anonymity claim.

**Contract with a secret pepper/random rotating salt.**

- A **public date** only gives domain separation/rotation. It does not stop offline guessing.
- A **random salt stored or published beside the digest** prevents reusable precomputed tables, but an attacker can still enumerate candidates for that day. It changes collision/linkability shape, not the fundamental pseudonymous contract.
- A **secret pepper/key** blocks outsider enumeration while secret. Prefer the defined construction `HMAC-SHA-256(daily_secret, site_id || date || canonical_ip || user_agent)` over ad-hoc concatenation; RFC 2104 specifies HMAC and recommends random keys plus refresh [S20].
- A **fresh random daily secret, never persisted with event rows and irreversibly deleted after the dedup window**, limits retrospective recomputation/linkage if later data leaks. A long-lived pepper protects against outsiders but compromise enables recomputation for every date it covered. If the “random salt” is kept secret, it is functionally an ephemeral key/pepper.
- None of these removes transient IP/UA processing or the within-day fingerprint/linkage. The honest contract remains **cookieless daily pseudonymous client estimation**, not “anonymous visitors” or “no fingerprinting.” Key/raw-input logs, backups, or retained salts weaken the claimed deletion boundary.

**Hard invariant:** canonicalize unambiguously (length-prefix fields or a structured encoding). Delimiter concatenation can collide semantically if fields contain the delimiter. Scope by site and day, rotate at the declared reporting-zone boundary, and do not claim range-wide uniqueness. These are integrity requirements if this method is chosen, not a recommendation that it must be chosen.

### 4. Privacy-safe cookieless counting

**Evidence.** Cloudflare’s strict low-linkability model rejects cookies and cross-time IP/UA fingerprinting, reporting entrances instead [S8]. Plausible is a mature alternative using a site-scoped daily digest with explicit cross-day/device limits [S9][S10]. EDPB distinguishes anonymisation from pseudonymisation; only truly anonymised data falls outside EU data-protection law [S17].

**Hard truths.**

1. “No cookies” does not imply “no personal-data processing,” “anonymous,” or “no fingerprinting.”
2. Cross-day/device unique-person measurement requires persistent linkage or authenticated identity. Reject both and the metric is unknowable.
3. Browser beacons can be blocked [S7]. The current pipeline therefore cannot claim every page fetch.
4. Cloudflare Bot Management’s probabilistic score uses a `__cf_bm` cookie to smooth scores/reduce false positives [S14]. It is security infrastructure, not an analytics unique ID, but “this site uses no cookies” would still be false when present. Narrow the claim to analytics identification unless the whole surface is verified cookie-free.
5. Aggregate-only counters provide the lowest linkage; per-event rows/dimensions add disclosure and retention risk. Plausible drops most query parameters and raw IP/UA while retaining coarse derived dimensions [S9], a mature precedent rather than a mandate.

### 5. Bot and AI classification integrity

Cloudflare’s July 2026 behavior taxonomy is Search, Agent, Training, Transact, Data Collection, Security Testing, SEO, Ads Verification, Social/Link Preview, Feed Fetching, and Monitoring/Operations. A bot can have multiple behaviors. Old “AI Search” is backward compatibility; new AI and traditional search crawlers are both Search [S11]. A headline “AI traffic” is therefore unstable/overloaded.

Verification requires deterministic identity (Web Bot Auth, stable UA plus published IP list, or reverse DNS) and non-abusive behavior [S11]. Web Bot Auth signs HTTP messages cryptographically [S12]. `request.cf.botManagement` is populated only when Bot Management is used [S13]. Granular 1–99 scores require Enterprise Bot Management; 1 is automated, 2–29 likely automated, 30–99 likely human, and 0 is not computed—not human [S14].

**Inference to validate:** absent an entitled Bot Management signal, a UA list supports only “claimed/UA-matched beacon clients.” It cannot support “verified bot,” complete bot traffic, or human-only totals. Even with Bot Management, the current beacon-only observation universe excludes non-beacon crawlers and the score remains probabilistic.

### 6. Timezone and date-window semantics

SQLite normalizes supported date-time inputs internally to UTC; `now` is UTC, but there is no timezone-aware type [S5]. Product decisions/public metadata must define:

- canonical UTC instant storage; never mix local date strings and instants;
- one reporting zone (`UTC` or named IANA zone), not per-visitor `request.cf.timezone`;
- calendar boundaries converted to instants and queried half-open `[start, end)`;
- whether “last 7 days” is seven calendar dates or rolling 168 hours, and whether today is included;
- partial current periods and “updated at”;
- `collection_started_at` beside “all time”;
- methodology/backfill effective dates.

**Invariants.** Daily buckets partition totals only with the identical event predicate/timezone/boundaries. Additive view/event daily sums can equal range totals; daily distinct-client counts are non-additive, especially with a rotating ID.

### 7. Public analytics disclosure baseline

Plausible shared dashboards can use password protection and immutable base segments; viewers can see included filters and cannot widen beyond them [S18]. This is a useful integrity precedent: public viewers should see the scope/filter. At minimum show a **Methodology** panel with:

1. Collection source: browser beacon; trigger, eligible hosts/paths, acceptance/dedup, blockers and excluded static fetches.
2. Definitions: recorded view, entrance/visit, daily client estimate, bot, AI Agent/Search/Training/referral.
3. Scope: production domains, exclusions (own traffic, health checks, preview, `/stats`), collection start, retention.
4. Privacy: cookies/localStorage used by analytics; transient inputs; persisted fields; public-date vs secret daily key; rotation/deletion/log policy; security cookies; privacy-notice link.
5. Bot method: Cloudflare signal or UA list, entitlement, threshold, not-computed handling, category dedup, taxonomy/effective date; explicit beacon-only coverage.
6. Time: reporting timezone, preset meaning, partial periods.
7. Quality: update time, cache/lag, retry/drop policy, approximation/sampling, backfill/method changes.
8. Publication safety: strip query/fragment/credentials from page/referrer dimensions; suppress risky low-count geography/referrer cells; show base filter.
9. Version the methodology and date changes.

A public aggregate page does not replace a privacy notice; a privacy notice does not fix misleading metric names.

## Known limitations and falsifiable hypotheses

| Hypothesis / limitation | How to falsify or bound later |
|---|---|
| Beacon views miss blocked, failed, and non-JS traffic. | Reconcile with independent Cloudflare edge request data for eligible HTML responses. |
| “Bots/AI Reads” misses non-JS crawlers by construction. | Compare article edge logs/verified bot IDs with `/api/event`; non-beacon crawler fetches should have no D1 event. |
| UA AI list is spoofable/incomplete. | Replay ordinary beacon with listed UA; it classifies unless verification is required. Compare detection IDs. |
| AI referrals are a lower bound. | Compare Referer attribution with tagged links/platform reports; quantify missing Referer. |
| Public-date SHA digest permits offline enumeration. | Enumerate a bounded IPv4 range and plausible UA dictionary for a known day; measure candidate recovery/ambiguity. Repeat with unknown HMAC daily key. |
| Daily digest is not a people count. | Controlled tests across devices, NAT/VPN, address changes and UA changes bound merges/splits; exactness is unprovable without identity. |
| Summed daily uniques inflate multi-day “unique visitors.” | One controlled client crossing reporting midnight contributes two daily IDs. |
| D1 failures/unsafe retries under- or overcount. | Inject retryable failure around non-idempotent increment; reconcile to independent source. |
| Replica-backed stats can lag. | Check Sessions mode; compare `served_by_primary` and sentinel using `first-unconstrained` vs `first-primary`. |
| Date labels fail near midnight/DST. | Boundary fixtures before/at/after midnight and DST transition. |
| Public dimensions leak URL/referrer query data or people through tiny cells. | Canonicalization and small-cell disclosure audit. |

## Concrete ADR questions

1. Is the source of truth an accepted beacon only? What exact trigger, inclusion, duplicate, and failure predicate defines it?
2. Will the UI say “beacon events,” “recorded views,” or “page views”? What evidence would justify “visitor,” “reader,” or article “fetch”?
3. Must the page explicitly state static/non-JS crawler requests are outside measurement?
4. Is strict no-linkage invariant (entrances, no uniques), or may raw IP+UA be transiently processed into a site/day digest?
5. If digest allowed, why is public-date SHA acceptable despite enumeration? Will it use HMAC with a random daily secret? How are key deletion, logs/backups, canonicalization and output length defined?
6. Is the public label “estimated daily unique clients,” and is cross-day/range-wide uniqueness explicitly rejected?
7. Does “cookieless” cover analytics only or whole site? Is `__cf_bm` enabled?
8. Which bot signal is entitled in production? What happens when absent/0? How is beacon-only coverage named?
9. Are Search, Training, Agent, ordinary automation and AI referrals separate? How are multi-behavior classifications deduplicated?
10. Are counters best-effort or reconciled? What makes retries idempotent and what error bound is disclosed?
11. Is read replication enabled? Is primary freshness, bookmark consistency, or possibly stale lower latency chosen?
12. Reporting timezone? Calendar days or rolling hours? Today included?
13. Cache/update lag, retention, collection start and backfill rules?
14. Which public dimensions are safe; are queries stripped and small cells suppressed?
15. Where are definitions, filter scope, limitations and methodology version visible?
16. What independent edge source periodically detects drift/missing D1 beacons?
